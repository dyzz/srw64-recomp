# SRW64 多语言与内容 Mod 架构建议

2026-09-12：产品阶段、默认设置、安全节点保存和语言/画质验收以
[内置 MOD 路线图](mod-roadmap.md)为准。当前仅将我们自己的功能按 MOD 模块组织，直接编译进宿主；不接入外部 MOD。本文的语义接口、内容分层和保存边界可复用；外部包加载、`.nrm` 接入、社区分发与公开 SDK 属于暂缓的架构研究，不是当前任务或 blocker。

日期：2026-09-10；实施状态更新：2026-09-11。已开始第一批重构：统一 JP 运行基线、独立语言目录、纯美术包与原图/高清运行中切换。详见 [第一批实现](../native/native-content-foundation.md)。其余章节继续作为目标架构，不代表已发布 SDK。

目标是在同一原生程序中支持原版日文与中文，允许其他贡献者增加语言包，并逐步支持机体、人物、武器、资源及关卡 Mod。本文区分已有能力与拟议接口；示例路径、命名空间和数据格式均不是已经可用的 SDK。

## 1. 核心决定

1. 以已锁定的原始日版 ROM 为一个统一运行基线。语言、高清资源、模型替换和玩法 Mod 分别选择；同一玩法配置可以使用不同显示语言。
2. 游戏对象 ID、显示名称和资源定位分开。翻译名称不会改变单位身份，替换头像不会改变驾驶员数据。
3. 普通语言、美术和已支持字段的数值修改使用数据包；需要新逻辑时再使用代码 Mod。
4. 原游戏地址、字节序、overlay 身份及内部结构集中到游戏适配层。公开接口使用稳定 ID、值对象、带世代的实例句柄与明确生命周期。
5. 先支持原对象的已知字段覆盖，再支持新增对象与关卡；新增 ID 需要核验原数组、索引和存档容量。

## 2. 值得参考的代码架构

### N64ModernRuntime：复用 Mod 基础设施

本地固定依赖与本次核查上游均为 `cdf5abbd5026fef5c364c676e4667c45e42b6863`。`librecomp` 已包含 Mod 清单、依赖、函数替换/钩子/事件、导入导出与内容类型注册。`ModContentType` 提供启用、禁用、排序变化和能否运行时切换的回调；适合在相同包管理机制中注册 SRW64 自己的语言、数据与资源内容。

参考：[内容类型与 Mod 接口](https://github.com/N64Recomp/N64ModernRuntime/blob/cdf5abbd5026fef5c364c676e4667c45e42b6863/librecomp/include/librecomp/mods.hpp) · [Mod 编写说明](https://hackmd.io/fMDiGEJ9TBSjomuZZOgzNg) · [牧场 Mod 模板](https://github.com/HarvestMoon64Recomp/HM64RecompModTemplate)。

建议继续使用上游 `.nrm` 代码 Mod 工具链，补充 SRW64 版本化导出和符号模板。语言/数据 schema、合并规则、存档语义仍需自行实现；上游识别函数替换冲突不等于能够识别两个包同时修改同一机体的 HP。

### RecompFrontend：借用菜单与输入模块

核查提交 `b1a1477c6556aeb7ed45defbfb5924f721efebc1`。其 `recompinput` 管键盘、鼠标、手柄与映射；`recompui` 管设置、Mod 菜单和 Mod 自建 UI，内部使用 RmlUi 和 RT64/plume。[项目说明](https://github.com/N64Recomp/RecompFrontend/blob/b1a1477c6556aeb7ed45defbfb5924f721efebc1/README.md)

它适合作为启动器、输入和管理菜单的集成候选。当前 SRW64 的对话排版（跨平台文字引擎）及 Metal 合成应保留在平台后端中，通过统一的多语言服务供给文字。本次检查没有找到现成的完整多语言目录服务，不能把接入 RecompFrontend 当作日中切换已实现。集成原型需验证两个 UI 层的输入消费、呈现顺序和语言更新。

### Wesnoth：借鉴战棋内容与语言的分离

Wesnoth 不是 recomp，但它将单位唯一 ID、可翻译名称、图像、能力和武器分别定义；关卡通过 ID、地图、阵营、事件与下一关关系连接，附加内容可有独立翻译域。这与 SRW64 的“机体/人物数据 + 关卡 + 多语言扩展”目标相近。

参考：[单位定义](https://wiki.wesnoth.org/UnitTypeWML) · [关卡定义](https://wiki.wesnoth.org/ScenarioWML) · [附加内容翻译](https://wiki.wesnoth.org/GettextForWesnothDevelopers)。

借鉴其内容分层和翻译域思路，首版继续用本项目已有的 JSON 工具链，避免为了配置文件引入整套 WML 引擎。

## 3. 已拆出的边界与剩余工作

2026-09-12 已移除旧 ROM 汉化管线。原始解析位于 `src/srw64_rom/`，
日文字形映射有独立来源锁，语言目录、TextKey 与统一 JP profile 位于
`src/srw64_native/`。原生姓名页使用原游戏姓名编码，不再依赖补丁 ROM 的字形分配。

仍需继续分离文字排版与平台绘制，恢复其他游戏文字消费者，并将内部
`SRW64GameHooks` 转换为可供 Mod 使用的语义事件。当前槽位与 RDRAM 接口
继续属于内部适配层；不可直接作为公开 SDK。实际责任见[原生开发指南](../guide/native-development.md)。

## 4. 建议模块边界

拟议目录，仅用于表达责任：

```text
src/native/
  app/                 启动、PlayProfile、设置、模块生命周期
  game_adapter/        日版资源/地址映射、overlay、数据读写与原脚本桥接
  content/             包解析、schema、内容注册表、合并和来源记录
  localization/        TextKey、目录、回退、格式参数、语言配置
  presentation/        对话与界面模型、资源解析、模型替换接口
  platform/macos/      Metal 合成与菜单栏
  mod_api/             版本化导出、语义事件与命令
tools/content/         提取、校验、导入导出、打包、差异报告
```

宿主内部继续使用 C++ 值类型和不可变快照。需要跨 `.nrm` 或动态库边界的接口使用定宽类型、明确长度与版本，不导出 C++ STL 容器或原游戏内存结构。

数据流：ROM 经适配层生成基础内容；包管理器合并内容覆盖；适配层在已验证的加载时机将有效字段送回原游戏。UI 从同一有效内容与运行快照读取，语言服务最后解析显示文字。必须验证数值改动被战斗逻辑消费，不能只更新资料面板。

## 5. 多语言设计

### 5.1 语言与呈现互相独立

- 首版 locale 为 `ja` 与 `zh-Hans`；以后可增加 `zh-Hant`、`en` 等。语言标签作为数据，不为每种语言建立 C++ 分支。
- `ja` 的原游戏文本从用户本地原 ROM 导出为目录；新增原生 UI 的日文和中文字符串由项目维护。未知字形保留原字形身份和回退能力。
- 原版字图与原生排版是单独的呈现选择。选择日文时也可以使用高清地图、现代模型和原生字体。
- 图片内烘焙文字归语言资源。无文字头像/地图可共用；中文标签贴图与中文字体图集不能在日文模式下无条件启用。
- 字体、回退、断行、书写方向由语言配置与文字后端处理。第一版验证日中；未来语言不等于所有复杂书写系统已经验收。

### 5.2 稳定文本键与控制流

原版文本键保留表与记录 ID，如 `base:t00_17412`；新 Mod 使用自有命名空间，如 `example.campaign:dialogue.intro.001`。名称、菜单、系统提示也使用同一个 TextKey 概念，分目录维护。

原文段落转换为结构化消息：文本片段、具名参数、专用字形及脚本屏障分开。STOP/END 与原解释器推进属于程序元数据；翻译作者只修改对应片段和允许的参数位置。自动换行/阅读分页可以增加，不能越过原脚本屏障。新增或删除剧情事件属于关卡 Mod。

翻译导出应包含原文、TextKey、片段号、说话者/场景（已识别时）、参数说明、源版本摘要、译文和审校状态；可补截图关联。首版使用 JSON，提供 PO 导入导出作为后续贡献工具，所有格式统一编译进同一种运行时目录。

### 5.3 回退与社区语言包

基础游戏缺译时回退到对应日文源记录；新增 Mod 缺译时回退到内容作者声明的源语言。第三方可以发布单独翻译包，声明翻译哪个内容包及适用版本，无需复制其机体或关卡数据。

解析次序是“确定内容所属包和最终源记录 → 选择该记录对应语言的已生效覆盖 → 该包的源语言”。基础文本最终源语言为日文；自定义战役可自选。源文本或控制结构变化时，旧译文标记待更新；无效片段回退源文并报告，不能无声改变脚本。

首版在启动/标题阶段选择语言，启动时建立不可变目录。游戏中热切换留到对白等待、分页和场景失效策略验证后；不能只清空纹理而保留旧语言分页。

默认人物显示名跟随 locale；用户改过的名字保持原输入。原存档难以识别姓名是否默认时保留原值，不能靠“恰好等于默认字符串”推断。任意 Unicode 姓名输入及其持久化单独设计，第一版语言切换不要求改变原姓名存储格式。

2026-09-11 已增加[原生姓名输入原型](../native/native-name-entry.md)：开场姓名编辑由系统输入框接管，支持原 ROM 字形内的直接键入，保留原姓名字段和校验。任意 Unicode 姓名与扩展存档仍是后续工作。

## 6. 内容 Mod：从已知字段到完整关卡

### 6.1 统一内容注册表

建立明确类型：`UnitDef`、`PilotDef`、`WeaponDef`、`StageDef`、`AssetRef` 和 `TextKey`。定义与运行实例分开：机体基础 HP 属于 UnitDef；本次关卡当前 HP、气力和行动状态属于实例。

原对象保留稳定基线 ID，新对象使用作者命名空间。底层可转换为紧凑整数索引，但映射需可保存、校验，不能随包扫描顺序改变。尚未识别语义的字段保留 opaque 数据与来源，禁止猜测名称或允许随意重排。

修改既有对象优先使用字段覆盖，附带可选旧值/源记录摘要断言。示意：

```json
{
  "target": "base:unit/<verified-id>",
  "expect": { "hp": 8000 },
  "set": { "hp": 9000 }
}
```

上例仅表达拟议接口，ID 与字段映射需经验证。底层适配负责范围、布局、派生值及应用时机；修改最大 HP 时还需规定对已生成单位/旧存档当前 HP 的处理，不能隐式当作治疗。

两个包改不同字段可以合并；改同一字段时要求明确的覆盖关系或报告冲突。每个最终值记录来源包与变更链。不要把目录顺序或任意“最后加载者获胜”变成默认规则。

### 6.2 包结构

拟议内容包：

```text
example.campaign/
  manifest.json
  data/units.json
  data/pilots.json
  data/weapons.json
  stages/intro.json
  locales/ja.json
  locales/zh-Hans.json
  assets/
```

清单复用上游支持的包 ID、版本、目标游戏和依赖字段；项目附加元数据表达 schema、源语言、内容能力与基线兼容性。一个包可以只有 `locales/`，也可以只有资产。包命名空间是逻辑所有权，不依赖其磁盘文件名。

第一版注册数据内容类型、目录开发模式与打包入口即可。代码 Mod 继续走上游 `.nrm`，避免维护第二套函数补丁加载器。对于只改语言/数值的作者，不要求安装 C++ 编译器。

### 6.3 关卡逐层开放

1. **原关卡参数覆盖**：已核验的出击单位、阵营、初始位置、增援和奖励字段。
2. **结构化事件编辑**：地图、部署、条件、行动、对白引用和胜败关系分开，转换为已理解的原脚本操作或已验证原生桥接调用。
3. **新增关卡/战役**：补齐 stage ID 分配、关卡流转、队伍继承、事件状态、保存和资源生命周期后开放。

保留原脚本解释器运行语义。提取器先完成无修改往返；含未知 opcode、未解析跳转或重定位依赖的区域作为不透明块保留，限制其可编辑操作。第一版不引入通用 Lua 解释器替代原剧情系统。2026-09-12 起，原脚本的指令、条件块、上下文标记与触发类型已能静态读全（见[关卡脚本完整解析](../script/stage-script-exploration.md)）；写回与运行比对仍未开始。

新增机体也同样分阶段：改变既有数据最早开放；新增条目必须检查数组上限、武器/人物引用、AI、列表循环和存档索引。recomp 允许修改这些限制，但 JSON 注册表本身不会自动扩大它们。

## 7. Mod API 与游戏生命周期

内部适配层统一读写游戏状态，公开只读快照和明确命令。拟议事件包括 `stage_entered`、`unit_selected`、`dialogue_segment_ready`、`battle_resolved`；定义触发阶段、顺序、参数寿命和是否允许提交命令。

第一版开放加载阶段的数据覆盖及只读观察事件。UI 回调只能提交请求，游戏线程在已定义时机应用；渲染线程不直接改 RDRAM。对伤害等核心规则的替换后续通过单独版本化接口开放，不通过任意顺序的多个事件回调重复结算。

公开实例句柄带世代，切关、读档、退出后失效。存档操作、内容加载和场景初始化有明确先后顺序；同一事件的多订阅者由适配层管理，不能让新 Mod 覆盖掉已有的原生对白钩子。

Mod API 版本、数据 schema 版本和游戏基线版本分别记录。底层直接函数补丁仍可作为高级扩展，但其地址/符号兼容要求明确绑定版本；普通内容作者使用稳定 ID 与字段。

## 8. 存档与包配置

语言和纯显示资源属于呈现配置，目标是切换语言不改变关卡状态、随机数或原版保存内容。玩法数据与关卡包形成内容配置，记录 ID、版本、有效内容摘要及实例 ID 映射。

原版兼容保存继续保留原 SRAM 数据；扩展状态可放在版本化 sidecar/容器中，与原保存代次及哈希绑定，原子地组成一个保存集合。代码或内容 Mod 如果改了会持久化的状态，不能自行宣称只影响显示。

加载时核对玩法包与映射。缺少新增单位或关卡包时提供清楚的缺失报告及恢复配置入口，不能把未知 ID 当作另一个单位继续执行。旧 stage1 中文实验存档涉及专用字形和姓名路径，迁移到统一 JP 基线需要专门验证；不得自动视作可互换。

## 9. 实施顺序与验收

1. **语言基础**：提取 TextKey、独立日文源目录与 zh-Hans 目录；移除字体/locale 硬编码；在原日版 ROM 上跑通同一场景日中选择、缺译回退和原生字体布局。把已有中文样片作为迁移输入，保留原验收证据。
2. **包与配置**：接入既有 Mod 内容类型机制，建立一个语言包、一个纯资源包和统一 PlayProfile。新增第三种语言样例只改数据，不重编译宿主。
3. **机体/人物/武器 schema 与工具**：先提取、校验和差异报告，再对一个已知字段做加载覆盖，证明原菜单、实际战斗与存读档一致。编辑器使用同一 schema 和校验器。
4. **关卡与公开 SDK**：先验证原关卡部署/事件往返，再做最小关卡覆盖样例；当接口实际被两个独立样例使用后，发布 SDK、模板和兼容声明。

关键检查：日中在相同操作下的控制事件一致；语言切换不改变玩法数据；同名 text ID 位于不同表时不冲突；模板参数和 STOP/END 校验；译文过期与缺字回退；包排序确定性和字段冲突；UI 数值与结算一致；缺 Mod/旧存档处理。新增内容的验收必须包含实际游戏，静态 schema 通过只证明格式合法。

2026-09-11 已落地第 1 步及第 2 步中的开发用配置/资源切换基础；内容类型注册、玩法字段覆盖、关卡和公开 SDK 尚未实现。精确可用范围与验收见 [第一批实现](../native/native-content-foundation.md)。
