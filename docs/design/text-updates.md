# 文本单独更新

2026-10-30 规划，同日实现（工具、官网数据、桌面／安卓／Switch 客户端），Mac 开发会话、安卓 Seeker、Switch、Windows 实测通过（见文末）。同日改为所有版本共用一份全量清单（见「更新清单」），新格式 Mac 实测通过，其他平台待测。目标：从下一版起，台词、数据文本（机体／驾驶员／武器名、系统讯息）和界面文字的修正不必等发新版程序，放在官网上，游戏自己下载、套用。

## 现状（为什么可行）

| 文本 | 在哪 | 运行时怎么用 |
| --- | --- | --- |
| 台词（剧情、战斗、序章、结局、制作人员） | `content/dialogue/<语言>/`，393 个文件／语言，随包放在 `dialogue/` | `native_dialogue.cpp` 按「随包目录 → 用户覆盖目录」两层读，`with_translations()` 叠到目录上；F5 热重载（`request_reload()`）已有 |
| 数据文本词条 `entries`（4674 条／语言） | `content/locales/<语言>.json`，`build_import_spec.py` 编进程序（`srw64_import_spec.hpp`），首次运行由导入器写进准备好的数据 | `localization::Catalog` |
| 界面文字 `ui`（935 键） | 同上 | `catalog.ui(key)`，缺键回落日文 |
| 图鉴名 | `content/locales/library-names.json` | `library.cpp` |

大小（2026-10-30 实测）：台词每种语言约 10 MB，xz 后约 1.6 MB；三个 `locales/*.json` xz 后共 0.28 MB。台词文件里译文只占约三成，其余是日文原文对照、注释和条目标题（玩家改文本时看的，原样保留）。全部文本按文件 zlib 压缩后约 9.5 MB；一次修正通常只动几个文件，每个几 KB 到十几 KB。放官网（CDN）完全没问题，不用走 GitHub／网盘。

文本都绑在固定的日版 ROM 上：台词键、词条键、`source_sha256` 不会因为程序升级而变，所以文本可以脱离程序单独发。

## 更新清单

一份全量清单服务所有版本，不按版本比较、不按版本出包（2026-10-30 用户定：「搞成一个更新包」「包里是分散文件的 hash」「hash 也可以很短」「不需要依赖版本，直接全量文本」）。

- `tools/release/build_text_update.py` 把当前提交（默认 `HEAD`）的**全部**文本逐个文件列进清单，不管哪个版本带过什么。
- 游戏逐个文件比 hash：和随包台词相同的不要（叠加是按条目的，随包那层本来就在），和已装更新相同的复制，其余下载。更新目录里只放这些和随包不同的文件，`kept.json` 记下是哪些、按哪个程序版本算的；程序换了版本，旧的更新挪进临时目录，下次检查重新算。
- **官网只放增量**（10-31 用户定：「服务器上只有增量的文件，不是全部 1184 个」）：清单仍列全部文件，但 `files/` 里只放和某个支持版本（`oldest`～`release` 之间的每个发布标签）随包台词不同的文件，加上 4 个词条表和图鉴名（游戏里这两样是另一种形式，比不了 hash，压缩后约 0.3 MB）。比如按 v0.5.2 算，当时只要 59 个文件、0.88 MB，而不是 1184 个、9.3 MB。
- 清单带 `oldest`：最老的支持版本，默认 0.5.3（第一个带客户端的版本），`--oldest` 可以往后挪；更老的程序不用这份清单。
- 清单带 `release`：该提交包含的最新发布标签（`git describe`）。程序版本比它新，说明程序随包的文本比清单还新，游戏不用这份清单、删掉已装的更新。所以**每次发新版程序后要跑一次工具**，清单的 `release` 才跟上新版本；发版前出的清单不会把旧文本盖到新程序上。
- 清单里的路径：
  - `dialogue/<语言>/…txt`：台词文件，整份（带日文对照和注释，原样，玩家照样能看）；
  - `locales/<语言>.json`：`{"entries": {键: 译文}, "ui": {键: 文字}}`，该语言**全部**词条和界面文字（界面文字按游戏看到的样子，日文垫底）。游戏只取自己有、`{…}` 记号也相同的界面键（`Layer::apply`），新功能的界面文字旧程序自然用不上；
  - `library-names.json`：图鉴名，整份。
- 清单 `web/public/text/text-r<N>.json`（约 110 KB）：`schema: srw64.text-update.v1`、`revision`（整数，递增）、`oldest`、`release`、`date`、`commit`、`notes`（各语言一句）、`files: {路径: {"hash", "bytes"}}`。`hash` 是 SHA-256 的前 12 个十六进制位（约 1200 个文件，48 位不会撞；清单本身由 `latest.json` 里的完整 SHA-256 校验）。
- 文件 `web/public/text/files/<hash>.z`：zlib 压缩，按内容命名，内容不变就不变，CDN 可长缓存。官网留最近两份清单和它们提到的文件，其余由工具删掉。
- 以后台词文件格式要是改得旧程序读不了，换新的 `schema`（旧程序不认，照用随包文本）。
- **以后加文件、加种类、加语种**：清单按提交重新生成，新文件照常下载生效。程序不认的路径（新种类文本）和没有的语言直接跳过、不下载、不算大小，不会让整份被拒。大小上限按程序用得上的文件算：解开 256 MB、清单 16 MB、单个文件 16 MB（10-31 放宽，为加语种留余地）。
- 工具发现两个不同文件 12 位 hash 撞车就拒绝出清单。
- 出清单前工具自己检查：该提交的全部台词文件用 Python 版加载器读一遍问题数为 0，各语言词条表照导入器的规则编译通过（`source_sha256`、脚本签名）。流水线（`renames.json`、`make_zh_hant.py`、`apply_terms`、`check_dialogue.py`、`run_audit.py`）照平常在提交前跑，见 `docs/guide/release.md`「只发文本」。

## 官网

- 清单和文件随 `deploy.sh` 上线。
- `/latest.json` 加一段：

  ```json
  "text": {"revision": 4, "date": "2026-11-12", "url": "https://srw64.dreamquest.club/text/text-r4.json",
           "bytes": 111527, "sha256": "…"}
  ```

  数据由 `build_text_update.py` 写进 `web/src/data/text-update.json`（不放 `release.json`：`sync-release.mjs` 会整份重写它），`latest.json.ts` 原样输出为 `text`。`latest.json` 的 CDN 缓存刷新沿用部署脚本现有的刷新。
- 不必每次写博文；更新说明就是 `notes` 里那一句，「关于」页显示。

## 游戏端

- **检查**：沿用现有更新检查（同一次 GET、同一 User-Agent、同一「启动时检查更新」开关、一天一次）。`text` 的 `revision` 比已装的新（也比上次看过、不适用本程序的那份新），就读清单。
- **自动套用**（`src/host/text_update.cpp`）：下载清单（`http_get`，上限 16 MB）→ 校验 `bytes`／`sha256` → 程序不在清单的 `oldest`～`release` 之间就删掉已装的更新、换回随包文本，到此为止 → 跳过程序不认的路径和没有的语言 → 逐个文件取：和随包台词相同的不要，临时目录 `text/.staging` 里已有且 hash 对的留着（上次中途断了），已装的那份里 hash 相同的复制，其余下载 `files/<hash>.z`、解压、核对大小和 hash → 写 `kept.json`、清掉临时目录里多余的文件 → 对着游戏的目录检查（台词用 C++ 加载器读、词条比脚本签名；本程序没有的语言不读），有问题就不装 → 改名为 `text/r<revision>/`，保留上一版。装好立即热重载（同 F5，但不弹台词报告），一条通知「文本已更新（r4）」。失败时临时目录保留，下次检查接着下载缺的。手动「检查更新」也会顺带拿文本。文件夹由 `SRW64_TEXT_UPDATES` 指定（用户目录下 `text/`），装好一份只有和随包不同的文件（随包和清单一致时只有词条表与图鉴名，约 1 MB）。
- **叠加顺序**：随包文本 → 文本更新 → 名字 MOD → 玩家自己的覆盖目录（F5 那层）。玩家改的永远在最上面。
  - 台词：`roots` 从两层变三层。
  - `entries`／`ui`／图鉴名：新增一层，在 `localization::initialize` 之后用 `with_translations()` 叠上；`ui` 需要 `Catalog` 增加一个叠 `labels` 的方法。键不在原始记录里的条目忽略并计入问题。
- **程序升级后**：启动时 `kept.json` 的版本和程序不符，或程序已不在清单的版本范围内，就把已装的更新挪进临时目录、先用新程序随包的文本；下次检查按新的随包文本重新算，大多数文件不用再下。
- **「关于」页**：「文本更新」一行显示「正在使用文本更新 r4（2026-11-12）」和更新说明、下载中或失败；装了包时有「使用更新／随包文本」两个按钮（随包文本＝关掉文本更新层，排查问题用，记在 `text/use-bundled`）。
- **问题报告 zip**（`text_update`、`text_update_bypassed`）和 `dialogue-report.txt` 写上文本 revision。
- **隐私**：不新增请求内容，只多下载清单和变了的文件；`update_ask_note` 已改为「读取官网上的版本号，并下载最新的文本修正」。

### 安卓（2026-10-30 定：第一阶段就做）

更新检查本身 10-30 已在安卓和 Switch 接上（`docs/native/update-check.md`「安卓与 Switch」），文本更新只需在其上加下载与安装。当时的做法：

- 清单加 `android.permission.INTERNET`（普通权限，安装时授予，不弹框）。这是安卓包第一次有联网权限，发布说明要写清楚：只读官网的 `latest.json` 和文本更新，开关在「关于」页。
- `update_http.cpp` 的安卓分支经 JNI 调 Java（`SRW64Activity` 旁新增 `UpdateHttp.java`，`HttpURLConnection`）：`http_get` 与流式 `http_download`，超时、大小上限、User-Agent（平台 `android`）和桌面一致。
- `supported()` 对安卓放开，整套更新检查跟着上：标题问一次、「关于」页检查按钮与开关、新版本提示（「下载页」用 `SDL_OpenURL` 开浏览器）。HD 包提示同样适用。
- 文本更新装在内部数据目录（和存档一样以内部为准），不进 `Documents/Marchwind64`。
- 验证：Seeker 实机（Wi‑Fi／无网／中途断网三种），Win 上的安卓模拟器补一台 x86_64。

## 不做的

- 不更新字体、图片、程序逻辑；新界面键、新功能的文字仍随程序发。
- 不做按语言分包；不做行级差分补丁（文件按场景拆开，整份替换已经够小，补丁反而要求原文件一模一样，又绑回版本）；不按版本比较（全量清单＋比 hash）。
- 不支持 0.5.3 以前的程序版本（没有客户端）。
