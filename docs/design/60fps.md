# 60 帧研究

2026-10-01。静态分析（主循环反汇编、全部 overlay 的生成代码、RT64 与 ultramodern 源码、宿主绘制层），没有改代码、没有实机。凡写「推断」「未核实」的都要在第 7 节的试验里确认。

## 1. 结论

1. **原版逻辑固定每秒 30 帧**：每 2 个 VI 跑一帧游戏逻辑并提交一份显示列表。间隔值全程序只在开机时写一次，没有哪个场景改它。
2. **把逻辑改成 60 不可行**：所有等待、动画步进、滚动都按帧计数，间隔改成 1 就是整个游戏 2 倍速。（副产物：这正是一个现成的全局 2 倍速开关，见 §2.1。）
3. **可行的是显示插帧**：逻辑仍 30，RT64 在两帧之间按显示器刷新率多画几帧。RT64 自带这个能力，宿主现在把它关着（`RefreshRate::Original`）。
4. **插帧只对走矩阵的 3D 绘制有效**。本作按场景分两类：
   - 开箱大概率能用：战斗演出的机体与特效（每节点一次 MODELVIEW LOAD 的四边形）、3D 地面、世界地图模型、标题与序章的缩放文字。HD 机体图与 HD 模型的宿主绘制已经在读 RT64 的插值矩阵，会一起动。
   - 完全不动：一切 TEXRECT——战术地图的地图块、单位、光标、滚动，战斗的天空层，背景、头像、HUD、对白。RT64 不对矩形做匹配。
5. **最想要 60 帧的战术地图恰好是不动的那一类**，要给 RT64 加「带编号矩形的插值」补丁（或把地图层矩形改成正交四边形），这是整件事里最大的一块工作。
6. 宿主自己画的界面（RmlUi 页面、对白栏）在呈现钩子里每次呈现画一次；现在每秒只呈现 30 次。插帧开着时呈现次数跟显示器走，这些界面的过渡动画不用改就能到 60／90／120。

建议顺序：先加一个试验开关实机看开箱效果（半天）→ 战斗演出／世界地图／标题按节点槽号给矩阵组编号、处理切镜（数天）→ 战术地图矩形插值（最大）。

## 2. 原版的帧节奏

| 地址 | 作用 |
| --- | --- |
| `80080838` | 调度线程。消息 `0x29A`（VI 回扫）：调空桩 `80085F30`，`D_80172D0C`＋1、`D_8015DC50`＋1，再 `80080A14`。`0x29B`／`0x29C` 是 SP／DP 完成，`0x29D` 是 PreNMI |
| `80080600` | 建调度线程，`osViSetEvent(队列, 0x29A, 回扫数)`；回扫数是调用方传入的，没有追到立即数，由实测 30 帧反推为 1（推断） |
| `8007F9A0` | 游戏线程主循环，每收到一条类型 1 的消息走一次 `8008163C`（推断是调度线程转来的回扫） |
| `8008163C` | 每次都读手柄并累加（`80087A48`、`80087AA4`）；**`D_80172D0C < D_8010F0C8` 就返回**；否则清零计数、算按键边沿、跑当前场景的帧函数 `D_8015DC7C` |
| `8007FC48` | 开机初始化，**`D_8010F0C8 = 2`** |

- 在全部生成代码（`build/recomp/cpu-bound/generated`，常驻段加全部 overlay）里搜对 `8010F0C8` 的访问：一处写（`8007FC64`）、一处读（`80081660`），没有经基址指针的访问。所以间隔恒为 2，逻辑恒为 30 帧，掉帧时才更低。
- 实测吻合：标题画面录 8 秒得 240 帧（[debug-interface.md](../guide/debug-interface.md)）；帧率读数（`frame_rate.hpp`）数的就是每秒提交的显示列表。
- 手柄每个 VI 都读并 OR 进累加字，所以输入采样是 60 Hz、消费是 30 Hz（[original-controls.md](../gameplay/original-controls.md)）。
- `80085F30` 是每个 VI 调一次的空桩（原本大概是性能打点），宿主把它当「帧边界」挂了一串钩子（`game_hooks.cpp`）。也就是说**宿主已经有一个 60 Hz 的节拍**，只是游戏逻辑隔一拍才动。

### 2.1 为什么不能把逻辑改成 60

`D_8010F0C8 = 1` 后每个 VI 都跑一帧逻辑。游戏里的等待（「等 20 帧」「30 帧延时」）、动画步进、滚动步长、镜头靠近的 1/8 系数全部按帧写死，没有时间步长的概念，结果是全局 2 倍速。逐处减半步长等于重写所有 overlay，不考虑。

副产物：这是一个不动 VI、不动音频时钟的**全局 2 倍速**（推断，未实机）。音频线程自己收回扫消息，音乐速度不变，音效触发会密一倍；两个播种时钟按 VI 走不受影响。之前记录「宿主没有任何调速设施」是指 ultramodern 的速度倍率；这个间隔字是游戏自己的。要做「按住快进」可以从这里试，和 60 帧无关。

## 3. 宿主现在怎么呈现

- ultramodern 的 VI 线程固定 60 Hz（`events.cpp` `vi_thread_func`，速度倍率常量 1），每个 VI 给图形线程排一个屏幕更新。
- 游戏每 2 个 VI 提交一份显示列表 → `send_dl` → RT64 一个 workload。
- RT64 `updateScreen` 只在 VI 寄存器或帧缓冲内容变了时才产生一次呈现（`rt64_state.cpp:1950`），所以每秒呈现 30 次。
- `graphics.cpp:399`：`refreshRate = RefreshRate::Original`，目标帧率 0，不做帧匹配、不插帧。
- 宿主的呈现钩子（`capture_frame`）每次呈现调一次：两侧清黑、对白栏、RmlUi（`context->Update()`／`Render()`）。因此宿主界面现在也是 30 帧。

## 4. RT64 的插帧怎么工作

源码在 `build/recomp/upstream/RT64`（提交 4337374 加本项目补丁）。

- **开关**：`RefreshRate::Display`（取交换链刷新率，Metal 经 `CocoaWindow::getRefreshRate`）或 `Manual`（`refreshRateTarget`）。
- **原始帧率**：`VIHistory::logicalRateFromFactors`——最近几次画面更换之间隔了几个 VI，全部相同才给出 60÷间隔，否则 0（不插）。本作稳定时是 30；读盘、切场景抖一下会暂时退回不插，稳定后自动恢复。可以用扩展指令 `gEXSetRefreshRate(30)` 钉死。
- **前提**：呈现的那块帧缓冲必须是本 workload 画过的颜色图（`interpolationEnabled`，默认的 SkipBuffering 模式下查 VI 历史）。本作是普通双缓冲，推断成立，未核实。
- **每个游戏帧渲染 N 次**（N＝目标÷原始，60 Hz 是 2，90 Hz 是 3，120 Hz 是 4），每次用不同权重把「上一帧 → 当前帧」的变换插值后**整帧重画**，不是廉价的重投影。GPU 负载按 N 倍算。
- **匹配**（`rt64_game_frame.cpp`）：
  - 只看透视与正交两类投影下的绘制；**矩形投影（TEXRECT／FILLRECT）不参与**（`GameFrame::set` 的 switch 直接跳过）。
  - 没有显式编号时（`G_EX_ID_AUTO`）：先按绘制调用哈希分桶，哈希只含合成器、OtherMode、几何模式、三角形数，**不含贴图**；桶内对所有「当前矩阵 × 上一帧矩阵」算位置、朝向、屏幕位置的差，从小到大贪心配对。
  - 有显式编号（`gEXMatrixGroup…`）时按编号配对，可逐分量指定插值或跳过，可开顶点插值、UV 插值。
  - 视图／投影矩阵、贴图滚动（tile 的 uls/ult）、LookAt 也插值。
- **没配上的东西**直接按当前帧画，等于仍是 30 帧，不会出错，只是不顺。**配错的**才会出毛病（两个物体互相滑向对方的位置）。
- 延迟：插出来的帧走在当前帧之前，当前帧本身晚一点才显示，60 Hz 下多约半个游戏帧（17 ms），对战棋无所谓。

## 6. 要做的事

### 6.1 第一档：矩阵类场景

1. 设置项「帧率：原版 30／跟随显示器」（默认先留 30），`presentation.json` 存；对应 `RefreshRate::Original`／`Display`，切换走现有的 `updateUserConfig`。调试会话固定 30：截图对照脚本（`check_aspect.py` 等「只差动画帧」的比对）和录像都假定一个 workload 一帧。
2. `srw64_render_node`（`game_hooks.cpp`）已经包住了每个精灵节点的绘制，并且拿得到（槽, 子）。对模式 0xE/0xF/0x10 和模型节点，在节点绘制前插 `gEXMatrixGroup`（编号＝槽×3＋子＋常数），之后复位。扩展 GBI 已经常开。
3. 跳过条件：节点本帧新建或换了场景／图集（槽被别的演员复用）、位置跳变超过阈值、镜头硬切、演出状态机换段。对应帧给该组 `G_EX_COMPONENT_SKIP`，镜头则给视图组跳过。
4. 帧首插 `gEXSetRefreshRate(30)`，免得读盘抖动时来回切换。
5. 留一张按场景关闭的表（参照 Mischief Makers 的做法），出问题的演出先关。
6. 性能：Deck 上 4×MSAA 加 HD 层，每帧要压进 16.7 ms（90 Hz 的 OLED 是 11.1 ms）才有意义；达不到时 RT64 不会降级，只会整体变慢。要实测，必要时限制目标为 60。

### 6.2 第二档：战术地图

地图上的运动全是矩形的平移：滚动是地图层所有精灵同一个偏移，光标和单位是各自的屏幕坐标。两条做法：

- **A. RT64 补丁：带编号的矩形插值**。显示列表里用带编号的 G_NOOP 标签（现有 HD 钩子已在用这种标签）给后面的矩形标组号；RT64 在 `DrawCall` 里记下，帧匹配时按「组号＋组内序号」对上前后两帧的矩形，渲染插值帧时按权重插矩形坐标（和裁剪）。矩形不走顶点速度缓冲（那套 `pos − vel × (1 − w)` 只在 RSP 顶点着色里），要在矩形转屏幕坐标处单独加。宿主这边 `srw64_render_node` 给地图层精灵发标签；HD 地图层、HD 单位图标的宿主绘制要拿到同一个插值后的偏移。改动集中在 RT64，游戏侧小，但 RT64 补丁要跟上游维护。
- **B. 游戏侧把地图层矩形改成正交投影下的四边形**，每个精灵一个矩阵，RT64 现成的矩阵插值就能用。不改 RT64，但要改写 `80095974`、`800945D4`、`80096CD8` 等几个绘制器发出的指令，宽屏已经在这些绘制上套了 `gEXSetRectAlign`／裁剪，还有 HD 纹理替换按矩形哈希识别，牵连面大。

倾向 A。不论哪条，地图块换帧动画（水面、范围闪烁）和光标自身的帧动画不插。

地图滚动与光标每帧走几像素没有量（`801FFADC` 的跟随是「滚动量＝32 − 光标 x」这类直接换算，步长取决于光标自己的移动），试验时一并测，用来判断 30 → 60 的观感收益。

### 6.3 宿主层要查的点

- 呈现钩子每个 workload 会被调 N 次：`srw64::ui::presented()`／`in_flight`、`names::cover_presented(workload)`、`dialogue::gpu_draw(workload)`、`wide_map` 的可见带都按 workload 号取数，重复调用应当幂等，逐个确认。
- `record.start` 每次呈现读回一帧，帧数会翻倍；`srw64_screenshot` 可能截到插值帧。
- 帧率读数现在数的是显示列表（恒 30），要再加一个呈现计数才能看出插帧是否生效。
- `get_display_framerate()` 两处写死 60（`host.cpp:106`、`graphics.cpp:524`），ultramodern 用它做别的节拍，暂不用动。
- 音频完全不受影响（逻辑与 VI 节奏没变）。

## 7. 试验计划（半天，需要构建与实机）

1. `graphics.cpp` 加 `SRW64_REFRESH_RATE=display|<数字>`，对应 `Display`／`Manual`；帧率读数加呈现计数。
2. 依次看并录像：标题（缩放文字、火焰）、序章、世界地图、一场带镜头移动和弹幕的战斗演出、战术地图滚动与单位移动、对白、场间 RmlUi 页面。
3. 记录：呈现帧率是否到 60；哪些东西动了；配错的例子；宿主层有没有闪烁、错位、重复记账；`logicalRateFromFactors` 是否稳定在 30；Mac 上每帧 GPU 时间。
4. 量战术地图滚动、光标、单位移动的每帧像素数。
5. 据此决定第一档的编号与跳过规则，以及第二档走 A 还是 B。

## 8. 未核实

- `osViSetEvent` 的回扫数（按实测 30 帧反推为 1）。
- 本作的缓冲方式满足 RT64 的 `interpolationEnabled` 条件。
- 残影（帧回授）与插帧共存的效果。
- 自动匹配在战斗演出里实际的错配率。
- Deck（Vulkan）下交换链刷新率的取值，以及 gamescope 限帧时的表现。
- `D_8010F0C8 = 1` 的 2 倍速是否有逻辑以外的副作用（显示列表缓冲是否够每 VI 一份）。
