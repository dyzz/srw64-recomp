# 宽屏画面：以 Steam Deck 16:10 为基准，4:3–16:9 随屏幕

2026-09-28 用户决定以 Steam Deck 的 1280×800（16:10）为分辨率基准：战场（战术地图）要真正扩大视野，界面与场间也跟着调整。2026-09-29 追加：还要适配 16:9，覆盖大多数怀旧掌机，特效要在各种分辨率下都对。所以画面宽度不是固定的 384，而是**随屏幕在 4:3 与 16:9 之间取值**，16:10 是设计与验收的基准。§5 起是静态分析得出的方案；地址、行号以 2026-09-28 的 main（3d3cff6）为准。上级计划见[三平台移植](three-platform-port.md)，原先的宽屏设想见[原生增强规划](native-enhancements-plan.md) §5（W1/W2）。

## 1. 现状

- RT64 设成 `AspectRatio::Original`（`src/host/graphics.cpp:368`），渲染 1× 原生分辨率。320×240 画面在 1280×800 里是居中的 1067×800，左右各约 107 px 黑边，纵向放大 3.33 倍（非整数）。Linux 冒烟截图（`build/linux-x64/smoke/s1-*.png`）就是这样。
- 107 px 黑边正好是 32 个原版像素。画面宽度 W＝240×屏幕宽高比（原版像素），原版 320 居中：

  | 屏幕 | 例子 | W | 每侧多出 |
  | --- | --- | --- | --- |
  | 4:3 | 640×480、960×720 | 320 | 0 |
  | 16:10 | Steam Deck 1280×800 | 384 | 32 |
  | 5:3 | 800×480 | 400 | 40 |
  | 16:9 | 1280×720、1920×1080 | 426.7 | 53.3 |
  | 比 16:9 宽 | 2560×1080 | 426.7（两侧再留黑） | 53.3 |
  | 比 4:3 窄 | 720×720 | 320（上下留黑） | 0 |
- 默认窗口 960×720（`graphics.cpp:571`），界面密度的参考尺寸也是 960×720（`src/native/ui/frontend.cpp` `sync()`）；Deck 默认界面大小 Largest，约 864×540 dp。
- 游戏不发任何 RT64 扩展指令（extended GBI）。

界面有两套坐标：

| 坐标 | 页面 | 在 1280×800 下 |
| --- | --- | --- |
| **G**：原版 320×240 映射进 4:3 画面（`u=min(W/320,H/240)` 居中，写 px） | 场间、改造、部件、换乘、存档、标题各页、能力、HD 战前页；对白栏与履历（`src/host/dialogue_scene.cpp:109`） | 铺满 4:3 画面，黑边空着；不受界面大小设置影响 |
| **D**：整窗 dp | 原生战前页、设置窗、姓名页、联动页、通知、标题设置按钮 | 用到黑边；设置窗在 Large 以上伸进黑边约 30 px |

## 2. 机制：RT64 按画面宽度渲染 ＋ 扩展指令，不改帧缓冲

比较过两条路：

- **A（采用）**：RT64 `aspectRatio=Manual`、`aspectTarget=W/240`、`extAspectRatio=Expand`。RT64 按 `resolutionScale.x×W/320` 渲染 W 宽的目标，窗口正好铺满（16:10 时 384、1.2 倍）。以下以 384 举例。游戏仍以为屏幕是 320×240；默认情况下它的矩形（`G_EX_ORIGIN_NONE`）不拉伸、居中落在 32..352，也就是**什么都不做时画面和现在一样**。需要变宽的东西由宿主在显示列表里插扩展指令选择性放开：
  - `gEXEnable`：每帧都要发，RT64 每个 workload 会清掉扩展状态（`rt64_state.cpp:1833`）。
  - `gEXSetScissor(LEFT, RIGHT, 0,0,0,240)`：把裁剪放到 0..384。
  - `gEXSetRectAlign(LEFT, LEFT, …)`：矩形坐标直接按 0..384 解释（原版 TEXRECT 是无符号 10.2，写不出负 x，所以要让游戏在 0..384 的坐标里排版，而不是 −32..352）。
  - `gEXSetRectAspect(ADJUST)`、`gEXSetViewportAlign(CENTER)`：保持 4:3 的场景用，防止铺满宽度的背景和 3D 视口被拉宽。
- **B（不采用）**：把游戏帧缓冲改成 384 宽（`0x8010F5C0` 屏幕宽、VI 模式表 `0x80178A10`、缓冲地址表 `0x800C6870`）。RT64 会如实显示成 16:10，但每块颜色/深度缓冲从 0x25800 涨到 0x2D000 字节要重排内存，而且所有画面一起变，风险大。

「默认保持 4:3」不必写进游戏的显示列表：宿主在 `send_dl`（`src/host/graphics.cpp`）里每次提交前直接设 RT64 的状态——启用扩展指令（操作码 0x64）、矩形 `ADJUST`、视口 `CENTER`——等价于在列表开头放这三条指令，而且不依赖游戏走哪条建列表的路径（RT64 在每个 workload 和 `rsp->reset()` 时会清掉，所以每次都设）。只有要放宽的场景才需要往列表里插指令。

插指令的位置：现有绘制器包装（`src/host/game_hooks.cpp`，如地图 `800945D4`）在调用原函数前往 `*cursor` 写命令、推进游标，调用后再写复位命令。现在的宿主只做原地改写（G_NOOP 标签），还没有追加过命令，这是新基础设施。每帧的公共前导可以挂在帧显示列表构建 `8008AE90` 调用的 `8008AD40` 上（需加进 `NATIVE_HOOKS`）。显示列表缓冲每帧 0x24000 字节，余量未量。

比例只随窗口变、不按场景切换：RT64 虽然每个 workload 重读配置，切换会有约一帧错位；保持 4:3 的场景用 `ADJUST`＋视口居中即可。设置里是「画面比例：自动／4:3（原版）」，4:3 时回到 `Original`。

## 3. 宿主绘制层要跟着改

两类原生绘制层（`src/host/`）：

- **呈现钩子层**（对白栏与履历、共享 RmlUi 界面、姓名页遮罩）按窗口像素自己算画面矩形。要把「4:3 画面」换成「W 宽画面 + 中间 4:3 列」：`u=min(窗宽/W,窗高/240)`，原版 320 坐标再加 (W−320)/2。
- **RT64 场景内层**：`NativeClip(pixel, fbWidth)` 里 `fbWidth` 是逻辑 320。
  - `native_marker.cpp:340`、`native_sprite.cpp` 四边形路径已经用 RT64 的 `screenScale/screenOffset`，会跟着正确居中或变宽。
  - `native_sprite.cpp` 文字矩形（`HdSpriteVS.hlsl`）、`native_map.cpp:271`（刻意设成单位变换）、`native_portrait.cpp:163`、`native_background.cpp:149` 直接按 320 映射，开 1.6 后会被横向拉宽 1.2 倍并被裁。要给它们一个「居中（+32）／左对齐宽画面」的映射参数，与所在场景的 `RectAlign` 一致。

## 4. 各场景做法

| 场景 | 做法 | 要点 |
| --- | --- | --- |
| 战术地图 | **变宽** | 见 §5 |
| 地图上的对白 | 地图变宽，头像与对白框居中 | 对白栏可以拉到 384 宽 |
| 场间与各接管页 | 页面留在中间 320，两侧露出加宽的背景 | 8 张背景（亮/暗 16 张 HD，1920×1440）外扩到 2304×1440，暗版用现有 3D LUT 重新导出；`native_background` 加两侧四边形；原版图片模式两侧填暗色或模糊延伸。提示行与底栏可拉到 384 |
| 世界地图 | 变宽 | 3D 视口自然加宽；地表分块的剔除范围要查；星空 5582 要左右补四边形与外扩图；舰船、地标跟随 RT64 |
| 标题 | 火焰变宽 | 火焰是 128 px 图块重复 2.5 次，uv 扩到 −0.35..2.65；游戏把负 x 夹到 0（`80096CD8`），宿主要自己画出边外；集中线（611）无 HD，两侧填色 |
| 开场、结局、制作人员 | 保持 4:3，两侧黑 | 本来就是黑底；开场星空可以顺手延伸 |
| 战斗演出 | 先保持 4:3（`ADJUST`＋视口居中） | 背景是贴 320×240 图的 3D 网格，放宽会露出网格边；特效、闪屏要逐个查。放在最后 |
| 原生战前页、设置窗等 D 类页面 | 已按整窗排版 | 统一边界：跟随画面而不是窗口 |

## 5. 战术地图放宽

地图绘制器 `800945D4`（已包装为 `srw64_original_map_draw`）每格一个 16×16 CI 纹理矩形，不按行列循环，而是逐格剔除。坐标要改成 0..W，所以游戏自己的「屏幕」要加宽到 W。下表的新值按 W＝384 写；实际要按运行时的 W 取值（W＝320 时等于原值），16:9 的 426.7 取整为 426 给游戏逻辑用，多出的不到 1 像素留黑。改动点（原值 → 16:10 的值）：

| 位置 | 作用 | 改动 |
| --- | --- | --- |
| `800945D4` @`80094A94` | 右边剔除 `x+16 < 0x149` | → `0x189` |
| `801FFCB0`（约 48 处调用） | 以点居中：scrollX = clamp(152−px, 320−W, 0) | 152→184、320→384；地图宽 <384 时居中（见下） |
| `801FFADC` | 每帧跟随光标：x>272 或 <32 时滚动 | 272→336 |
| `801FFE34` | 「点在屏内」[32,288]：`0x101` | → `0x141` |
| `801FFE78` | 中心框 [96,224]：`0x81` | → `0xA1`（可选） |
| `801E4760` @`801E4888`、`801E49A4` @`801E4B20`、`801E4D10` @`801E4E5C/70` | 移动/攻击范围整格绘制边界 `0x138` | → `0x178`；边缘 8 px 片段路径的裁剪还没读 |
| `801E44BC` | 网格 `0x140`（三处）、`0xF0` | → `0x180` |
| `801CABAC` | 地形面板跟随光标的左右夹取 189/156 | → 221/220，或保持 |
| 脚本滚屏 3D35/3D34/3D36 震屏，`801C8E20` 等内联的重新居中 | 夹取范围未知 | 要逐个读 |

宿主已有依赖这些边界的功能，要一起改：`enemy_cycle.cpp:89`、`move_jump.cpp:160` 用 `801FFE34`。

- **改常量的方法**：现在只有整函数包装（`tools/recomp/toolchain/generate_cpu.py` 的 `NATIVE_HOOKS`）。建议在 `generate_cpu.py` 加一个「立即数补丁」表：按函数和指令地址把常量换成 `srw64_wide(旧值, 新值)`，运行时按画面比例设置取值，并校验原值、找不到就让生成失败。这样 4:3 模式下行为与原版逐字节一致。小函数（`801FFCB0`、`801FFADC`、`801FFE34`）也可以直接在宿主重写。
- **窄地图**：只有 11 张地图正好 320×240（34、65、66、70、73、74、81、116、117、119、157），其余最窄 432，比 16:9 的 427 还宽。窄地图的夹取区间会倒置，`801FFCB0` 会把它钉在左边、右边空出 W−320；要让它居中（scroll＝(W−320)/2），两侧地图外区域画暗色边框。
- **HD 地图层**：`native_map.cpp` 本来就从整张地图底图按摄像机取 uv，边界框随剔除放宽自动变大；要把映射换成 384 宽，并把 uv 夹在地图内（窄地图不能拉边）。
- **地图上的 HUD**（单位窗口、指令菜单、阶段横幅）静态没找到坐标。游戏若仍按 320 排，在 `LEFT` 对齐下会贴左偏 32 px；要么逐个找到坐标加 32，要么只对地图、单位、范围、光标开 `LEFT`，HUD 保持默认居中。后者改动少，先按后者做。
- 单位图标 `801E21F8/801E26C0` 本函数不剔除，调用者是否剔除未知；伤害数字 `80209900` 没有屏幕边界常量。

## 6. 阶段与验收

每阶段结束都在 16:10（1280×800）、16:9（1280×720）、5:3（800×480）与 4:3 各截图对照；4:3 设置下必须与现在逐像素一致。目标是铺满屏幕、不留黑边（带鱼屏除外；比 4:3 窄的屏幕只能上下留边）。

1. **基础**（2026-09-28 代码完成，未实机）：
   - 设置「通用 → 画面比例」自动（默认，随屏幕 4:3–16:9）／4:3，存为 `presentation.json` 的 `aspect`（`auto`／`4:3`）；`SRW64_ASPECT=4:3` 可单次覆盖。状态在 `src/host/game_frame.hpp`（`frame::wide`、`frame::width(窗宽,窗高)`、`frame::scale`）。
   - RT64：`send_dl` 每次按交换链尺寸算 W，变了才 `updateUserConfig(false)`：W>320 时 `aspectRatio=Manual W/240`、`extAspectRatio=Expand`，否则 `Original`；每次提交前设扩展默认值（见 §2）。
   - HD 层：`gpu::frame_resolution` 把画面宽度与原版左边缘传给着色器，`NativeFrame`（`NativeGpu.hlsli`）取代地图、头像、背景、精灵矩形里的 `NativeClip`；模型与四边形仍跟 RT64 的 `screenScale/Offset`。
   - 呈现层：对白栏与履历（`rasterize_frame` 多一个画面宽度参数）和 8 个 G 类页面改用 `frame::scale`，页面戳记带上画面宽度。
   - 默认窗口 1280×800。
   - 两侧涂黑：`graphics.cpp` 的 `mask_sides` 在呈现时把 4:3 以外清成黑色；游戏的清屏色（战斗里是灰）、全屏闪光和残影都会画到两侧。这只是过渡：用户要的是铺满屏幕、不留黑边（带鱼屏除外），放宽的场景要跳过它，每个场景最终都要铺满。
   - 实机过程中改掉的两处：
     - 视口对齐 `CENTER` 让 RT64 从画面中点起算 x，而游戏给的是绝对坐标，标题菜单文字、战斗精灵等读 RT64 视口的原生层右移了 160 像素；改为对齐时带 −640（10.2，即 −160 像素）偏移抵消。
     - 标题卡、序章文字的残影（`80083744` 每帧把上一帧拷回来）被 `ADJUST` 压回 4:3，每帧缩一点、越叠越花；RT64 补丁（`native_model_hook_patches.py`）让用了 tile copy 的矩形照旧铺满全宽。
   - 2026-09-28 Mac（Metal）实机验收，`tools/recomp/debug/check_aspect.py`：16:10 与 4:3 各跑一次（`--fixed`）。战术地图整张截图只差 1 个像素、战前页一致、战斗演出与世界地图模型只差动画帧（0.1–0.3%）、标题菜单、序章缩放文字与章节标题卡一致，两侧纯黑。场间页面在 1280×800 下两种比例的缩放倍数相同（3.33）。
   - 2026-09-29 多分辨率（自动）：16:9（1280×720，W＝426.7）、5:3（800×480，W＝400）、1:1（720×720，W＝320、上下留边）、带鱼屏（2520×1080，W＝426.7、两侧留边）各跑章节标题卡与序章缩放文字，残影正常；16:9 下标题、地图、战前页、战斗演出正常。
   - 已知：战斗演出中途切换比例，画面会花约两秒（帧缓冲换宽度后，战斗用到的上一帧拷贝对不上），之后恢复；其他时候切换正常。Deck（Vulkan）上尚未实机。
2. **战术地图变宽**（2026-09-29 代码完成，Mac 实机初验通过）：
   - 视野宽 Wv＝画面宽度取整、不超过地图宽、不小于 320；每帧在帧边界（`80085F30` 之后）由 `src/host/wide_map.cpp` 算出。地图比画面窄时（11 张 320 宽的地图）Wv＝320，照原版居中、两侧黑。
   - 常量：`tools/recomp/toolchain/generate_cpu.py` 的 `MAP_WIDTH_CONSTANTS` 按「函数名＋指令地址」把 10 处常量改成 `srw64_map_x(原值, 份数)`（原值＋份数/2×(Wv−320)）：地图格剔除、以点居中与右边夹取、光标跟随 272、「点在屏内」、中心框、网格三处。范围绘制的 `0x138` 只决定整格还是分片，分片不裁剪，不用改。
   - 放进宽视野的绘制：`8008AE90` 的两处节点调用（`8008B3FC` 精灵、`8008B3E0` 回调）改走宿主 `srw64_render_node`（`game_hooks.cpp`）。精灵按子记录 +2＝1（随地图滚动：地图、单位、光标、地图特效，模式 4/5/6/8/12/13）；回调按地址（网格、移动/攻击范围、目标格、伤害数字 `80209900`、3D56 目标区 `800A3AD8`），只在地图显示时。总览（`801027DB`＝1）不放宽。放宽的绘制前后插 `gEXPushScissor`＋`gEXSetScissor(LEFT, RIGHT)`＋`gEXSetRectAlign(LEFT, LEFT, 偏移)`，之后复位并 `gEXPopScissor`；窗口、横幅、头像仍居中。
   - HD 地图层按视野左边缘绘制（`MapDraw::view_left`）；两侧清黑改为按每帧的可见带（`wide_map::Band`，随 workload 传给呈现钩子）。
   - 实机（`tools/recomp/debug/check_wide_map.py`）：16:10（Wv＝384）与 16:9（Wv＝426）下地图铺满、单位与光标对齐、移动范围对齐、光标推到四边时地图边框贴屏幕边；34 号窄地图居中；4:3 设置与原来一致；连续 40 次随意改窗口大小（含带鱼屏与竖长窗口）不崩、正常退出。
   - 顺带修掉的退出崩溃：Mac 上 Plume 的窗口属性更新排在主队列里，退出时（SDL_Quit 清队列）读已释放的窗口而崩溃；`prepare_rt64.py` 给 `plume_apple.{h,mm}` 加共享的存活记录，窗口析构后排队的更新直接跳过。之前序章检查 4 次退出全崩，修后 0 次。
   - 未做：跟着单位的窗口（地形面板 `801CABAC`、`801C9D08`、`801E3AE4`）仍按 320 居中，单位在宽出来的部分时会离得远些；3D36 震屏无夹取（原版就会露出地图外 15 像素）；还没走完第一话全流程、R 跳最远格、L2/R2 切敌、地图战斗、总览缩放与地图上的对白。
3. **逐帧的画面形状与 3D 放宽**（2026-09-29，Mac 实机）：每帧由绘制决定填满多少（`wide_map::Shape`）：默认整幅；还是 4:3 的画面（没有加宽版本的背景、战斗演出）标为原版，两侧清黑；放宽的战术地图给出视野范围。3D 视口不再一律居中，只在战斗演出时保持 4:3（`send_dl` 按形状设 `gEXSetViewportAlign`）。摸底（`SRW64_WIDE_EXPERIMENT`，已去掉）结论：世界地图的模型、标题与序章的集中线放开视口就自然铺满；战斗演出放开后露出背景网格边与残影，暂不放。战术地图的精灵只认地图、单位与光标、地图特效几类（模式 4 的场间背景也带滚动标志，排除）。

8. **战斗演出**（2026-09-29，Mac 实机 16:9 铺满）：原先以为背景是贴 320×240 图的 3D 网格，其实天空是 2D：`8008422C` 读 ROM `0x5BC30` 的背景记录，天空放精灵槽 0/1、模式 2，由 `80095974` 以 32×32 块、按 320×240 取模环绕绘制（可横向无缝循环）；3D 地面本来就有约 ±1500 宽。有天空时游戏关掉清屏（`8010F5B4`＝0），所以放宽后两侧没人画，才露出灰色和拖影（战斗不用 `80083744` 帧回授）。做法：战斗时（`801C9710` 每帧 `mark_battle`）`80095974` 的包装在宽裁剪里先按 ±320 像素偏移各画一份天空，再画本体；3D 视口不再居中（地面、机体、特效自然放宽）；战斗帧的矩形用 RT64 的自动规则（`G_EX_ASPECT_AUTO`），让整宽的上下遮幅条（节点 0x85）和闪光拉满，HUD、对白框不到整宽照样居中。机体入场会比原版早一点出现在画面边上（16:9 下约 54 单位）。
13. **战斗窗口贴边、去遮幅条**（2026-09-30，用户在 Deck 上看到战斗上下有黑边，要求满画面、HP 窗与头像随分辨率摆放）：上下黑边是原版自己画的遮幅条，战斗 overlay 里一段静态显示列表 `80222D50`（设黑色，填 (0,0)–(320,16) 与 (0,224)–(320,240)），4:3 下也有。天空（`80095974`）、地面 3D、宇宙星空都画满 240 行，去掉遮幅条后不露空。做法（`battle_hud.cpp`，自动比例时生效，4:3 设置保持原版）：
    - 帧边界按设置把两条填充改成空指令或还原（先核对这 8 个字，overlay 不在时不动）。
    - 节点回调画完后改写它这段显示列表：每个矩形前插 `gEXSetRectAlign` 偏移（放在矩形的装载指令之前，原生绘制的标记和它前面的标签不被拆开），外面包一层整幅裁剪。上方 HP 窗（`800945D4`/`8009B74C` 槽 31、`801C2C98` 槽 29/30、`8008EB5C` 双方数字同一条、「反」槽 36）上移 12，左半贴左边、右半贴右边，跨中线的底色和数字条在 160 处拆成两段；头像（`800964E4` 槽 27/28）贴自己那侧、下移 16，胸像下沿正好到画面底；对白框（槽 32/33 的边框与 `8009B970` 底色）下移 14，左边跟左边缘、右边跟右边缘，中线左边那块边框图块在空隙里重复补齐。
    - 宿主自己画的部分另给偏移：HD 头像（`native_portrait.cpp`）、原生界面文字与徽章（`native_sprite.cpp`，按所在窗口）、原生台词（`native_dialogue.cpp`，框的位置与宽度，排版宽度随之加宽；原版字形仍按原位置匹配隐藏）。
    - 实机（Mac，1280×800 与 1280×720）：天空、地面（マジンガーZ 对 ザクⅡ，20 号地图）、宇宙（87 号地图）三种背景，头像左右两种方位都铺满；4:3 设置下遮幅条与窗口原样。检查：`check_aspect.py --fixed auto [--battle 迷你关文件]`。
    - 战斗背景的全部种类：ROM `0x5BC30` 的 38 字节记录，第 `块 × 101 + 地形` 条；块由地图的环境号经 `800C5940`（32 个环境号 → 24 块）得出，地形号是所在格的地形（飞行时 100）。记录＝标志与色调（8 字节）＋最多三个 3D 模型＋一张 2D 远景（320×240 CI4 与 16 色调色板）。有效记录 430 条：2D 远景 37 张（配色合计 99 种：星空、城市、草地山林、海湖、沙漠、雪山、夕阳、熔岩、云天、暴风云、漩涡、暗色），180 条只有 3D 与纯色底（洞窟、基地内等），首字节 1 的是黄昏（`40c11503`）、夜晚（`40000020`）等色调变体。`check_battle_backgrounds.py` 每类强制一场（写双方的地形/环境字节，调试接口 `memory.write`），92 类在 1280×800 全部铺满（2026-09-30）。
14. **原版图片模式的标题火焰**（2026-10-01，用户报「开场的火焰没有适配宽屏」）：HD 模式的火焰由宿主按 uv 循环延伸（`native_sprite.cpp`），原版图片模式下是游戏用 `80096CD8` 画的槽 9、场景 686，只盖中间。原图每帧 320 宽、按 256 像素循环（图集 512 宽的一半；按 320 平移有接缝，镜像像万花筒）。`80096CD8` 的包装在原版仍画着它时（没有 HD 标记）用调用前的寄存器副本再画两份，偏移 ±256，套整幅裁剪；Mac 1280×800 无缝铺满。同日存档会话报「标题画面缩到 960×720 必崩」（Gfx 线程在 RT64 解释器读 RDRAM 之外）：`send_dl` 原先只在画面宽于 4:3 时启用扩展操作码 0x64，缩放那一帧是按 16:10 写的、处理时宽度已是 320，16 字节的扩展指令被当成两条 F3DEX2，偏移 +256 的字 `0x04000000` 正是 `G_BRANCH_Z`，跳进空内存。改为每个显示列表都启用（F3DEX2 没有 0x64）。
15. **帧回授的竖条模糊**（2026-10-01，用户报「开场 BANPRESTO 中间一条竖带很糊，别的场景有时也有」）：开场（BANPRESTO 与版权页）、章节标题卡、序章都开着 `80083744` 的残影，每帧把上一帧按 64×16 一块、5 列 15 行画回来（`LOADTILE` 多载一列一行，`SETTILE` 行宽 17 字＝68 texel）。RT64 对用了帧缓冲 tile copy 的矩形本就拉满（不压回 4:3），但 copy 按自己的比例采样（取整后的宽度 ÷ 68 texel，16:10 下 326/68＝4.794），矩形却按两边各自取整铺（64 texel 落在 307 或 308 像素上）；比例是小数时每块最多差约 1 像素，每帧回授一次就把整列抹开。16:10 下是中间一列（原版 x 128–192），16:9 下是第 2、4 列；4:3 是整数比例，不受影响。改 RT64（`prepare_rt64.py`）：
    - tile copy 的范围按两边各自取整（`rt64_framebuffer_manager.cpp`），与盖在同一块上的矩形覆盖同样的像素，不再「左边取整＋宽度取整」差一列。只做这一条不够：copy 是 68 texel 宽，比例照样对不上矩形，糊的列只是挪了位置（实测从中间一列挪到左边一列）。
    - 1:1 的贴图矩形若采样 tile copy、按整幅拉满（非 `ADJUST`、无扩展原点），就按它自己覆盖的像素数 ÷ texel 数采样（`rt64_workload_queue.cpp`，GPU tile 上传前按各帧缓冲对的比例改 `tcScale`/`ulScale`；比例差 5% 以上的不动，留给换了 texel 大小的重解释）。拷回原处时逐像素对齐，与 4:3 相同。
    - 实机（Mac）：1280×800 与 1280×720 开场各列一样清晰（修前 16:10 中间一列、16:9 第 2 列的软边比是其他列的 5–20 倍），960×720 不变；章节标题卡（`act.json`）旋转残影与定格正常。其他用 1:1 矩形贴回帧缓冲的画面走同一条路径，未逐一实机。
