# 全文本地化：文本导出与中英翻译

日期：2026-09-23。这份文档说明以下几件事：

- 全部文本怎样导出；
- 由谁负责翻译；
- 怎样用阿里云百炼上的 DeepSeek 出中英两种语言的初稿并做 AI 审校；
- 译文怎样交给游戏；
- 之后还剩哪些步骤。

数字都来自当天的实际调用和生成结果。

## 结论

- **导出**：已覆盖全部 51,174 条 ROM 文本记录、30 页开场缩放文字（人工转写）和 244 条原生 UI 文案，每条都归入一个类别并附上下文。导出工具会检查两件事：每条记录恰好出现一次；剧情区（17347 起）与剧本实际引用的 33,628 个文本编号完全一致。
- **分工**：
  - 名称、界面、系统提示（记录 0–5798 中需要翻译的部分）走词条表，已由另一会话完成中英两套，见[数据文本汉化：词条表与译名规范](../native/localization-terms.md)；
  - 剧情对白、选择肢、战斗台词、开场序章走本文的机翻流程，人名、机体名、武器名一律取自词条表，台词里独有的专名另有一份中英词表（`content/translation/story-terms.json`）。
- **完成情况（2026-09-23）**：中英两种语言的全量初稿与一轮 AI 审校都已跑完。
  - 初稿用 `deepseek-v4.1-flash`（业务空间里版本号最新的 DeepSeek），检查不过的条目重试三轮，最后一轮用 `deepseek-v4-pro-0813`。
  - 审校用 `deepseek-v4-pro-0813`。
  - 结果：中文 45,206 条中 45,197 条通过全部机械检查，英文 45,139 条通过；审校改了中文 2,114 条、英文 1,931 条。
- **交给游戏的方式**：用户决定台词做成玩家可改的文本文件，不并入语言目录。
  - `tools/translation/write_dialogue.py` 已写出 `content/dialogue/{zh-Hans,en}/`，每种语言 422 个文件，含 45,013 条机翻、70 条待译模板和 30 页开场。
  - 另有 93 条手写对白在 `story/scene-0001.txt`，生成器不改动它。
  - 读取端由另一会话实现（`da649d3`），C++ 与 Python 两种展开结果逐条一致，零错误。
- **费用**：全部调用按 flash 标价计约 50 元；其中审校和最后一轮重试用了 pro，pro 的价格要以控制台为准。
- **下一步**：主要是人工审校（唯一原文约 91 万字）和显示接入。
- **对白排版（2026-09-23 定）**：统一打包 HarmonyOS 字体，英文取 0.85 倍字号，一条对白整条连排、原版翻页点只做同步，名字留在框内但收紧名字行。按模拟，翻页次数中文减少 24%、英文减少 37%，见[对白排版](dialogue-typesetting.md)。
  - 剧情对白已能在游戏里显示；
  - 战斗台词已接入，2026-09-23 实机验证中英切换正常；
  - 选择肢、胜败条件、开场文字和章节标题卡尚未接入。
  - 剧情审阅页可以把原文与中英译文对照阅读（见 P3）。

## 1. 导出

```sh
.venv/bin/python -B tools/content/extract_original.py      # 先有原始数据目录（make recomp-data）
.venv/bin/python -B tools/content/export_text.py           # → assets/text-export/
```

输出里含日文原文，只放在 git 忽略的 `assets/text-export/`，每次整体替换。约 2 秒完成。

| 文件 | 内容 |
| --- | --- |
| `manifest.json` | ROM、生产代码与输入文件摘要，各类别计数，编号区间表，控制符与标记说明，全部输出文件的 SHA-256 |
| `records.jsonl` | 每条记录一行：`key`、`category`、`group`、依据（`code`／`content`／`transcribed`）、无损原文 `source`（含 `<BR>`／`<STOP>`／`<G:XXXX>`）、`display`（动态姓名折成【主角名字】等）、`source_sha256`、可见字数、标记、`native_page`、`terms_section`、已有中英译文，以及按类别的上下文 |
| `summary.md` | 各类别的记录数、唯一原文数、字数、原生页与词条表覆盖 |
| `categories/*.csv` | 每类一张表（UTF-8 BOM，可直接用 Excel 打开）：键、上下文摘要、原文（⏎ 表示换行，▸ 表示翻页）、标记、已有译文 |
| `story/scene-NNNN.json` | 142 个场景，按剧本顺序列出每句的事件、阶段、触发条件、路线段、说话人及候选、对白模式 |
| `battle/speaker-runs.json` | 战斗台词按表内顺序、同一说话人连续为一段（1,524 段） |

上下文字段按类别不同：

- 剧情：全部出现位置。共用脚本会在多个场景出现，第一处作为主上下文。
- 战斗台词：说话人（文本头前三位）、所在段与段内位置、合体技起句（文本头后缀 `0024`）。
- 名称：机体／武器／人物编号，以及对应记录，如武器菜单名 ↔ 纯名称、简称 ↔ 全名、精神名 ↔ 说明。

| 标记 | 含义 |
| --- | --- |
| `numeric-gap` | 原版在空格处画数字，译文必须保留空格 |
| `fragment` | 运行时拼接的句子片段 |
| `dynamic-name` | 含动态姓名 |
| `paged` | 含 `<STOP>` 翻页 |

## 2. 分工与写入边界

- **词条表**：名称与系统文本由 `content/locales/terms/<locale>.json` 按分区维护，每个不同原文只译一次；`tools/content/apply_terms.py` 展开成语言目录条目（`"origin": "terms"`）。机翻不写这些键。
- **机翻草稿**：先存在 `assets/translation-runs/<tag>/`，每批一份，保存请求上下文、用量、逐条检查结果，可续跑。`run_mt.py collect` 把通过检查的条目整理成语言目录格式（`"origin": "mt"`、`"review_status": "draft"`，附模型、提示词版本、批次标记），并用 `compile_locale` 验证。
- **台词的最终去处（2026-09-23 更新）**：用户决定，剧情和战斗台词做成独立文本文件（暂定 `content/dialogue/<locale>/`），玩家可以自己修改，程序附带的文件可被用户目录里的同名文件覆盖。台词**不并入** `content/locales/*.json`，也不进嵌入的 import spec。
  - 文件格式、读取、校验与覆盖由词条表会话负责，文件内容由本流程产出；格式定稿后，`collect` 会直接按新格式输出。
  - 放弃合并进语言目录的原因之一是体积。实测若把中英各 45,013 条台词并入，每个语言文件会从约 1.1 MB 涨到 13.5 MB，嵌入用的 import spec 会从 1.7 MB 涨到约 23 MB，生成的 C++ 头文件估计约 76 MB（现为 5.6 MB）。
- **角色卡**：SRW64 原创角色的性别、身份和口吻写在 `content/translation/zh-Hans/roster.json`。这里不定译名，译名仍以词条表为准。

## 3. 机翻流程

工具在 `tools/translation/`：

| 文件 | 作用 |
| --- | --- |
| `run_mt.py` | 分批、请求、检查、修正（`run`），AI 审校（`review`），重查（`recheck`），报告（`report`），整理成语言目录格式（`collect`，后面的批次覆盖前面的） |
| `run_full.sh` | 一个语言的全流程：初稿两遍（第二遍只补失败的批次）、审校两遍、报告 |
| `dashscope.py` | 百炼 OpenAI 兼容接口 |
| `references.py` | 词表与角色卡（中英） |
| `term_candidates.py`、`draft_terms.py`、`audit_terms.py` | 台词专名的候选、起草与一致性审计 |

保证译文结构正确的逻辑在 `src/srw64_native/translation.py`，测试在 `tests/test_translation.py`。

```sh
export SRW64_DASHSCOPE_ENV=<百炼 .env>
tools/translation/run_full.sh zh-Hans zh-v1 draft      # 或 review / all；en 同理
PYTHONPATH=src .venv/bin/python -B tools/translation/run_mt.py collect --tag zh-v1 --tag zh-v1-review --output <zh 文件>
```

**AI 审校（`review`）**：

- 用 `deepseek-v4-pro-0813`，每批最多 70 句。模型看到原文和初稿，只返回要改的条目及理由（中文）。
- 改动同样要过全部机械检查，与初稿相同或检查不过的改动不采用。
- 审校时载入最新的词条表与台词专名，初稿之后才定下的名字也能在这一轮统一。

凭据从 `--env-file`、`SRW64_DASHSCOPE_ENV` 或仓库根目录 `.env`（git 忽略）读取 `DASHSCOPE_API_KEY` 和 `DASHSCOPE_BASE_URL`，只发往 `*.aliyuncs.com` 的 HTTPS 地址。试跑用的是《机战Z》汉化项目现有的华北2业务空间配置。

请求参数：`temperature 0.1`，JSON 输出，关闭思考；只在 429 或 5xx 时重试。《机战Z》特别篇试过思考模式，推理会耗尽输出上限，因此不用。

### 保证能载入

每条原文在 `<STOP>` 处切成页，选择肢在 `<BR>` 处切成选项。页内处理：

- 去掉 `<BR>`，原生对白框会自动换行、分页；
- 动态姓名的每一串字码变成【主角名字】【搭档昵称】等占位符，其他特殊字形变成 ⟦G1⟧。

模型必须返回同样页数的数组，占位符的次数和顺序也要不变。还原时把原始字码串原样放回，因此页结构和 `signature` 与原文一致。任何不符都报错，不做静默修补。译文里的 `<`、`>` 会换成全角，模型写不出控制符。

### 分批与上下文

**剧情**：按场景分批，每批不超过 40 句或 2,400 字。共用脚本的句子只在第一个出现的场景翻译，其他场景里作为只读上下文（`ctx`）。同一场景的批次按顺序跑，后一批带前一批最后 8 句的原文和译文；不同场景并行。全量共 904 批。每批附带：

- 场景标题与本话主角；
- 每句的阶段、路线段和触发条件；
- 说话人角色卡：中文名取自词条表，原创角色取自 roster，已有作品的角色取自《机战Z》汉化图鉴的简介和性别，只作参考；
- 相关词表：“必用”来自本项目词条表的人名、机体、武器、作品名分区，有三类例外只作“参考”：1–2 字的名字（コウ、大作、忍）、平假名名字（ひかる）、ボス、マスター 这类普通词。平假名武器名（した、くちばし）不参与匹配；精神、能力、零件只作“参考”。另有一部分“参考”来自《机战Z》汉化词表的专名类，只收本项目词条表还没定的日文，并去掉只有英文写法的项。

**战斗台词**：按表内顺序每 60–80 句一批，尽量在说话人换人处切开，共 164 批。约 14000 号以前是各角色的通用情境块，大致顺序为攻击 → 被击坠 → 大伤害 → 小伤害 → 回避 → 防御光束 → 弹尽／射程外。其后是武器专用台词和多人合体技对话。选择表（哪种情境、哪件武器选哪句）尚未逆向，因此提示词只给说话人和区段说明。

**开场序章**：30 页一批，按段落对应。

### 检查与修正

逐条检查以下几项；检查不过的条目，把问题用中文写明后重发一轮，只重译这些条目：

- 页数、占位符、控制符；
- 空译文；
- 残留假名；
- 未转换的「」『』；
- 整条的引号是否成对；
- 译文与原文的长度比。

“必用”译名没出现只记为警告，不自动重发，避免“ボス”这类同时是普通词的名字被强行替换。模型自己标注的疑问（指代不明、双关、新译名）写在 `flag`。

## 5. 全量结果（2026-09-23）

| | 中文（`zh-v1`） | 英文（`en-v1`） |
| --- | ---: | ---: |
| 条数（剧情 33,628 + 战斗 11,548 + 序章 30） | 45,206 | 45,206 |
| 初稿后通过机械检查 | 45,110 | 44,962 |
| 三轮重试后通过 | **45,197** | **45,139** |
| 初稿与重试的输入 / 输出 tokens | 6.42M / 1.28M | 7.60M / 1.48M |
| 按 flash 标价计的费用（忙时／闲时） | 22.1／11.0 元 | 24.0／12.0 元 |
| 审校：审过 / 改动 | 45,127 / 2,114 | 45,139 / 1,931 |
| 审校 tokens（pro） | 5.00M / 0.72M | 5.18M / 0.95M |

- **初稿**：两种语言同时跑，各 6 路并行，每种语言约 1 小时。两种语言都在最开始的 20 多批出现过一次“回复里有两个 JSON 对象”，解析器已改为合并多个对象。
- **内容审核拦截**：中文有一批被百炼的输入审核拒绝（`data_inspection_failed`），英文同一批通过。`retry` 遇到这种情况先去掉上下文，再二分到单句，最后单独译出了这一批。
- **英文占位符**：英文初稿的占位符最初沿用中文标签，模型会把【搭档名字】“翻译”成 [Partner's Name]，占 118 条失败。改用 `{PartnerName}` 这类 ASCII 占位符后重试，这类失败基本消失。
- **检查器调整**：
  - 长度比改为按整条计算，并对日文按字种加权（片假名算半个，长音和小写假名不算），否则 ライトニングソォォォォード→闪电剑 这类喊招式都会被误报；
  - 英文增加日式敬称检查（`-sama`、`-san`）。
- **剩余未通过**：中文 9 条、英文 67 条，多是页数合并和漏掉 `{HeroMech}`。这些条目在台词文件里写成两种语言都空着的待译模板，附上草稿注释。
- **审校**：
  - 最初让审校模型沿用 `tr` 字段返回，它常照抄初稿。改成单独的 `revised` 字段并要求必须与初稿不同后，改动才真正落地。
  - 改动主要有：误译（呼び出せんのか）、日式用词（发进→出发）、代词和称呼对象、さん→先生、漏掉的引号。
  - 审校会给中文补句号，这与“页末标点跟随原文”的规则冲突（见第 8 节）。
  - 各有 2–3 批两次都因回复截断而失败，这几批保留初稿。
- **页末标点（2026-09-24，`zh-v1-joins`）**：游戏改为整条连排后，实机发现中文在原版翻页处常常缺标点，前后两句粘在一起。原因是 v4 规则“页末标点跟随原文”：日文页末常常不带句号。
  - 规模：中文 13,358 个翻页处中约 5,200 处没有标点，涉及 4,347 条。英文不需要处理：翻页处以字母结尾、下一页大写开头的 304 处几乎都是专名跨页。
  - 做法：`run_mt.py joins` 让 `deepseek-v4-pro-0813` 通读整条连起来的中文（附日文原文）补标点。程序逐字比对，只保留恰好插在这些翻页处的标点（。，！？等），其余改动全部丢弃，已有标点不动；39 条漏答的用 `--missing` 补问了一次。
  - 结果：401 条有改动，加了 477 个句号、6 个逗号、6 个问号；其余约 4,700 处判定为句子跨页接着说（如“师父在九泉之下|也会哭泣”），不加。输入 0.47M、输出 0.16M tokens。
  - 末页收尾标点（`zh-v1-final`、`zh-v1-final2`，`joins --final`）：剧情对白里有 3,057 条（9%）在收尾引号前没有句末标点，其余 91% 本来就有，所以统一补上。只允许在收尾引号或括号前插入 。！？……，模型把句号放在引号外时移进引号。
    - 结果：补了 2,967 条；还剩 59 条，模型判断不需要补。
    - 第一轮漏了约 400 条，原因是模型把句号写在引号外，程序没认出来；改为也接受这种写法后，第二轮补上了。
  - 半角叹号、问号：中文里有 74 处沿用了日文原文的半角 ! ?，写出台词时统一换成全角 ！？；省略号后面紧跟的句号（“……。”，171 处，多是初稿照搬日文）也在写出时删掉（`chinese_marks`）。
  - 试跑时淘汰了两种做法：一种让模型直接给每个页末的完整标点，结果删掉了原本正确的“！？”“……”；另一种在翻页处加编号标记让模型逐个判断，结果在句子没说完的地方也加句号。
- **写出前的规范化**：
  - 原文是一对「…」或（…）跨越所有页时，写出时统一成首页一个开引号、末页一个闭引号。这一步修正了模型漏引号或每页各加一对的问题：英文不符的条数从 888 降到 47，其余是一条里有多对引号的情况，不做改动。
  - 原始批次结果不改动。

## 英文版

中英两种语言共用同一套导出、分批、占位符保护、检查和合并流程，只有提示词的语言规则和词表来源不同。英文直接从日文翻译，不经过中文转译，以免叠加两次误差。

- **词表**：
  - 名字来自词条表的英文版（`content/locales/terms/en.json`，与中文同一批定稿）；
  - 台词专名来自 `content/translation/story-terms.json` 的 `en` 字段；
  - 《机战Z》的中文参考词表不用于英文。
- **角色卡**：英文名取自词条表。原创角色的性别与身份说明、《机战Z》图鉴里的性别、作品和简介（中文）两种语言都用，模型读得懂。
- **世界观说明**：提示词里的专名一律写日文原名（ムゲゾルバドス帝国等），不写中文，避免中文译名渗进英文。

  - 全角标点；
  - 直引号；
  - 罗马字敬称，如 `-sama`、`-san`。试跑里出现过一次 “Banjo-sama”，因此加了这一项。
  
  英文的长度比阈值放宽到 0.6–8。
- **两种语言的覆盖**：两种语言都尽量补齐；有条目只在一种语言通过检查时，另一种语言回退日文。台词不进语言目录，所以不受 `tests/test_english_locale.py`“中英键集合必须相同”的约束。

## 7. 译文规范（提示词里已写明）

- 忠实、自然、口语化，符合人物身份与语气；不增删信息，不加注释。
- 页数与原文一致，页内不换行；引号跟随原文首页与末页。
- 【主角名字】等占位符原样保留，次数与顺序不变；名字后的さん、くん多数省略。
- 标点：
  - 「」改为“”，『』改为‘’；
  - （）内心独白保留全角括号；
  - 省略号用……，破折号用——；
  - ！？用全角；数字用半角；外国人名用间隔号·。
- 称谓与军衔：少尉／中尉／大尉 = 少尉／中尉／上尉，少佐／中佐／大佐 = 少校／中校／上校，艦長 = 舰长，お嬢様 = 大小姐，閣下、殿 = 阁下，師匠 = 师父。
- 保留口癖、结巴、拖长音、敬语层级；喊招式名时保持气势。
- 词表：“必用”项必须照用；词表外的专名，高达等作品用中国大陆通行译名，没有通行译名的音译，并在 `flag` 中写出新译名。
- 两种语言共同：需要时补上主语或代词，依据是说话人、对话对象、前后文和角色卡的性别；指代无法确定时用名字或中性说法，并标“指代不明”。游戏把一条台词的各页连成一段显示（见[对白排版](dialogue-typesetting.md)），所以页末是句子或分句边界时要带标点，句子跨页继续时不加（提示词 v5 起；v4 的规则是“页末标点跟随原文”）。

英文：

- 自然口语，可用缩约形式；人名按词条表的西式顺序。
- 去掉 -san／-kun／-chan；作称呼用的头衔译成英文：お嬢様 my lady、師匠 Master、閣下 Your Excellency、艦長 Captain。
- 军衔：少尉 Ensign、中尉 Lieutenant、大尉 Captain、少佐 Major、中佐 Lieutenant Colonel、大佐 Colonel。
- 只用 ASCII 标点加弯引号 “ ” ‘ ’：…… 写作 ...，！？ 写作 ?!，内心独白用 ( )。
- 招式名按词条表写成 Title Case；呻吟和惊叫写成自然英文，如 Ngh!、Gah!。
