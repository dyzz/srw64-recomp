# 120 Hz 调度与 4 倍速

**状态：2026-10-24 起默认开启**，玩家在「游戏速度」里选 2／3／4 倍速（[game-speed.md](../native/game-speed.md)）；`SRW64_VI_RATE=60` 退回原版的 60 Hz（最高 2 倍）。针对 Issue #10（要更快的快进）。

## 1. 结论

1. **60 Hz 下 2 倍速是结构上限**。原版调度器每个 VI 最多放行一帧画面（§2.3），游戏线程又要等画面交出去才跑下一步逻辑，所以逻辑最多每秒 60 步。想更快只能提高 VI 频率。
2. **VI 改成 120 Hz、逻辑间隔改成 4/2/1，就是 1x/2x/4x**。120 Hz 下的 1x 与原版逐场景一致（同一 VI 切场景、30 帧、敌方阶段同样 38.9 秒）。
3. **音频必须隔拍**。原版音频线程每收到一次回扫就合成一次，120 Hz 下会合成两倍的样本。
4. **实际能到几倍看设备**。Mac 和 Windows（1080 Ti）4x 约 117–119 帧/秒；Seeker 每帧画不完一拍，只有约 55 帧/秒。慢设备上 120 Hz 反而让 2x 从约 33 帧提到约 54 帧；3x/4x 再隔帧不画（逻辑照跑），Seeker 上到约 77 步/秒，敌方阶段比 2x 快约 1.47 倍（§3.5、§5.3）。
5. 宿主每拍跑的钩子绝大多数不受影响；按拍数计时的三处已改（§4.4）。

## 2. 原版的调度（静态，生成代码）

### 2.1 回扫怎么分发

| 地址 | 作用 |
| --- | --- |
| `8007F884` | 调 `80080600`（osCreateScheduler），第 5 参数＝回扫数 **1**：每个 VI 一次回扫事件 |
| `8015D730` | 调度器结构；`+0x260` 是 client 链表（节点 `{next, 队列}`），`+0x27C` 帧计数 |
| `80080A14` | libultra 原版 `__scHandleRetrace`：帧计数＋1、调度任务，然后**给链表上每个 client 发一条回扫消息** |
| `80080748` | osScAddClient。只有两个调用者：`8007F820`（游戏线程）和 `8007E6D4`（音频，节点 `800D2360`、队列 `800D4540`） |
| `8007E148` | 音频线程：在 `800D4540` 上等消息，类型 1（回扫）就调 `8007E28C`，没有分频 |
| `8007E28C` | 音频帧：按 `osAiGetLength` 反馈算长度、`alAudioFrame`、`osAiSetNextBuffer`，三缓冲轮转 |

游戏只用 `osSetEventMesg` 登记了 SP（4）、DP（9）、PRENMI（14）、SI（5），**没有 AI**，所以 ultramodern 的 AI 消息对本作不起作用；要处理的只有调度器的 client 链。

### 2.2 游戏线程

`8007F9A0` 每收到一条类型 1 消息：

1. 同步模式 `D_8010F5DC`（实测为 1）且上一帧没画成（`D_80187878`）时跳过逻辑；否则调 `8008163C`。
2. `8008163C`：`D_80172D0C < D_8010F0C8` 就返回；否则清零计数、清"本步已画"`D_8010F720`、跑场景函数。
3. 有画面且在途帧 `D_8015F942` 小于 2、本步还没画：调 `80081614`→`8008AE90` 建显示列表并提交（在途帧＋1），置 `D_8010F720`；在途已满则记一次"没画成"。
4. 类型 2（图形完成）：在途帧－1（`8008ACD4`），完成帧计数 `D_8010E09C`＋1。

### 2.3 每个 VI 最多一帧

`80080C94`（任务就绪判断）：图形任务只有在 `osViGetCurrentFramebuffer() == osViGetNextFramebuffer()`（没有待生效的换屏）时才放行。一帧画完换屏后，下一帧要等 VI 把换屏生效才能开始画。所以**每个 VI 最多画一帧**，再加上 2.2 的"画不出就等"，60 Hz 下逻辑上限就是 60 步/秒。

## 3. 做法

### 3.1 时间域

| 时间域 | 120 Hz 下 |
| --- | --- |
| VI 线程（回扫、屏幕更新、VI 生效） | 120 Hz。改的是 ultramodern 的速度倍率，只有 VI 线程读它（`prepare_runtime_lifecycle.py` 改写 `timer.cpp`）；`osGetTime`、计时器仍按真实时间 |
| 游戏逻辑 | 间隔 4/2/1 → 30/60/120 步/秒（`game_speed.hpp`） |
| 音频合成 | 仍 60 次/秒：包住 `80080A14`，奇数拍把音频节点暂时摘出 client 链（`sched_rate.hpp`） |
| 宿主 VI 计数 `srw64_current_vi()` | 仍是 60 Hz 单位：`on_vi` 隔拍计数（`host.cpp`） |
| RT64 原始帧率推断 | 基准跟 VI 频率（`rt64_vi.cpp` 补丁），推出 30/60/120 |

### 3.2 改了哪些

- `src/host/sched_rate.hpp`：倍率、音频隔拍、换画面节拍（§3.3）、调试计数。
- `generate_cpu.py`：`80080A14` 改名为 `srw64_original_retrace`，由 `game_hooks.cpp` 包住。
- `prepare_runtime_lifecycle.py`：`timer.cpp` 的倍率读环境变量；`events.cpp` 也改写，VI 线程每拍先问宿主 `srw64_vi_latch()` 再让画面生效（CMake 一并替换）。
- `prepare_rt64.py`：`rt64_vi.cpp` 的基准帧率；`rt64_present_queue.cpp` 的呈现降频（§3.4）。
- `launch.cpp`：`--play` 启动器放行这些变量（对照、排查用）。
- 按拍数计时的钩子乘倍率（§4.4）。
- `src/host/big_cores.hpp`：安卓上加速时关键线程绑大核（§3.6）。
- `src/host/draw_skip.hpp`：慢设备上 3x/4x 隔帧不画（§3.5）；`graphics.cpp` `send_dl` 调它，`events.cpp` 的 `osViSwapBuffer` 问 `srw64_vi_swap_now()`。

### 3.3 2x 的换画面节拍

新画面在 GPU 画完后的第一个 VI 生效。120 Hz 一拍只有 8.3 ms，2x 每 2 拍出一帧时，GPU 完成时刻落在拍边界附近，就会有时隔 1 拍、有时隔 3 拍才换（Mac 上每 4 秒 6–9 次）。所以 2x 时新画面等偶数拍才生效。

但 GPU 一帧要两拍以上的设备（Seeker），每帧都等偶数拍会拖慢下一帧开始画（掉到 46 帧，有一次 32 帧）。所以：

- 画面已经晚了 3 拍以上就立即生效；
- 最近 32 次换画面里有 4 次以上晚到，就判为慢设备，之后 10 秒不限（`sched.latch_slow_spells` 计次）。

1x 本来就每 4 拍稳定换一次，限了反而让 Mac 插帧呈现从 60 掉到 54，所以只限 2x；4x 每拍都换。

### 3.4 呈现降频

4x 每秒 120 个新画面，RT64 在原始模式下来一帧就呈现一帧；Mac 的 Metal 交换链没把提交挡在 60，宿主界面也跟着画 119 次。补丁：不插帧、原始帧率高于显示器时，每个画面攒「显示器÷原始」个呈现额度，攒满 1 才呈现：60 Hz 屏隔一帧，90 Hz（Deck）四帧呈现三帧，144 Hz 每帧都呈现。在 60 Hz（`SRW64_VI_RATE=60`）下不生效。

试过又放弃的两种：睡到下一次刷新再呈现，在 Metal 上晚半拍，只剩 51 次；按时间判断（距上次呈现不到 0.75 个刷新周期就跳过），Mac 上没问题，但 Deck 90 Hz 屏上阈值 8.3 ms 正好等于 120 帧的间隔，几乎隔一帧跳一次，只剩 58 次。

### 3.5 慢设备上 3x/4x 隔帧不画

Seeker 每个显示列表在 RT64 里要处理约 9 ms，比一拍（8.3 ms）稍长；游戏换屏后要等 VI 让新帧缓冲生效（`80080C94`）才提交下一帧，所以一帧占两到三拍，3x/4x 都卡在约 55 步/秒，和 2x 差不多。线程都没跑满（§5.3）。所以慢设备上 3x/4x 只画一部分帧（`draw_skip.hpp`）：

- **游戏照常每帧跑逻辑、建显示列表**，只是图形线程不把其中一些交给 RT64，直接完成（`graphics.cpp` `send_dl`）。游戏看到的和画过一样，逻辑和结算不变；这一帧钩子排给画面的东西（对白帧、宽屏形状）一并丢掉。
- **没画的帧换屏不等拍**：运行库的 `osViSwapBuffer` 问宿主 `srw64_vi_swap_now()`，是就当场让新帧缓冲生效（`prepare_runtime_lifecycle.py` 改写 `events.cpp`），下一帧马上能提交。VI 线程每拍的生效也改在消息锁里做，两处不会同时改 VI 状态（Switch 上先发现过不加锁会丢 VI 消息，现在所有平台都加锁）。画过的帧也立即生效只再快约 2%（4x 14.64→14.14 秒，在波动范围内），没采用。
- 屏幕上留着最后画的那帧：RT64 默认的 SkipBuffering 呈现最近一次 workload 画的、在 VI 历史里出现过的帧缓冲。
- **画 3 帧中的 1 帧**，3x、4x 都是。游戏用两块帧缓冲轮流画，画的比例是奇数，两块才会轮流被画到，哪块都不会旧过 3 帧。画 1/2 或 1/4 时总有一块一直没画：1/2 时 RT64 每秒只呈现约 5 次（原因没查）；1/4 时进战斗的条纹转场在新旧两张画面间来回闪。
- **读画面的帧照画**：进战斗的转场每帧把上一帧画面当贴图读、再一条条涂黑。图形线程跳帧前遍历显示列表（`reads_picture`：`G_SETTIMG` 落在见过的、宽 256 以上的 16 位 `G_SETCIMG` 里），读画面的这个列表和之后 60 个列表全画（调试状态 `draw_skip.holds` 计次）。录像对照：不加时转场隔帧闪，加了以后和不跳帧一样逐渐变黑。
- **只在慢设备上**：3x/4x 加速时按一秒一窗数逻辑步，连续两秒不到应有的四分之三（4x 120、3x 90）就判为慢设备，本次运行一直有效。Mac、Windows、Deck 的 4x 都在 93% 以上，不会触发（Mac 实测 `slow` 保持 false）。交给 RT64 的帧率提示相应除掉（`game_speed::picture_rate()`：3x 30、4x 40），插帧照常。
- `SRW64_DRAW_EVERY=N` 不管设备都画 N 帧中的 1 帧，`=1` 永远不跳；`SRW64_SWAP_NOW=0` 没画的帧也等拍换屏（对照）。调试状态 `draw_skip`（`slow`、`every`、`skipped`、`holds`）。

### 3.6 安卓：加速时关键线程放大核

慢的另一半原因在手机的大小核（§5.3 采样）：这些线程每帧只忙几毫秒，安卓按负载把它们放在小核。`big_cores.hpp`：加速时（`game_speed::running`）图形线程在每个显示列表开头按线程名把关键线程绑到算力最高的那组核（`sched_setaffinity`，读 `/sys/devices/system/cpu/cpu*/cpu_capacity`），不加速了就放回所有核；绑着时每 600 个列表重扫一次，新建的线程也绑上。

- 绑的线程：`Game Thread*`（游戏、它的调度和音频线程）、`Gfx Thread`、`SP Task Thread`（音频合成）、`VI Thread`、`RT64 Workload`、`RT64 Present`。界面、SDL、RT64 的纹理/着色器工作线程、驱动的线程不动：另加 `mali-event-hand`、`SDLThread` 只再快 0.1–0.4 秒，在波动范围内。
- 只在加速时：原速游玩不多用大核。拔线实测整机功耗看不出差别（§5.3），一直绑（`=1`）也一样；为保守起见默认仍只在加速时绑。大小核一样的设备（Deck、桌面）什么也不做。
- `SRW64_BIG_CORES=1` 一直绑，`=0` 不绑（对照）。调试状态 `big_cores`（`mode`、`on`、`bound`、`released`）。`run-as taskset` 被 SELinux 拒绝，只能进程自己绑。

## 4. 宿主钩子审计（`80085F30` 每拍、`get_input` 每次读手柄）

### 4.1 只看状态、重复无害

`wide_map`、`battle_hud`、`menu_widen` 的面板补丁、`enemy_pilot_page`、`map_combo`、作弊锁值、语言切换、场间各页 `frame`、迷你关与脚本注入的 `service`；各原生页的按键屏蔽、对白阅读器、开场 R+START、键盘、设置窗口松键门（按下沿或状态）。

### 4.2 按宿主 VI 计时

`script_inject`、`stage_info::sample`、调试按键时长、`game_speed` 的菜单窗口：用 `srw64_current_vi()`，仍是 60 Hz 单位。

### 4.3 风险低、没改

`menu_widen` 的"最近画过的窗口"按拍数判断，但记录与字幕排版在同一次构建显示列表里完成。

### 4.4 已改：乘倍率

- `quick_load`：Z → Z+START → 松开（2/8/10 拍）。`check_title_return.py` 在 120 Hz 下 14 项全过，没有重按。
- `battle_page`：30 拍没步进算过期（故意按拍数，设置窗口暂停时不算过期）。
- `mini_stage`：进入时的 START 脉冲（32 次读手柄里按 4 次）。

另：游戏自己的战斗播种钟 `D_8015DC50` 每拍＋1，120 Hz 下走得快一倍；同样的操作得到的种子和 60 Hz 不同。

## 5. 实测

### 5.1 Mac（Metal，60 Hz 屏，HD）

- 1x：120 Hz 与 60 Hz 场景切换在同一 VI（采样 0.25 秒），30 帧，音频正常。
- 不隔拍音频：`latency_recoveries` 304 次、样本两倍；隔拍后 0 次。
- 敌方阶段（enemy-cycle 迷你关，含一场战斗）：1x 38.9 秒、2x 19.5 秒、120 Hz 1x 38.9 秒、**4x 9.8 秒**，阶段结束截图逐像素相同。
- 4x：约 119 帧/秒，降频后呈现 60 次/秒、94% 的呈现正好隔一帧。
- 插帧（帧率 60）：120 Hz 1x 呈现 60，60 Hz 下是 50（[60fps.md §9](60fps.md) 的节拍问题在 120 Hz 下没出现）。

### 5.2 Windows（1080 Ti，D3D12，144 Hz 屏）

1x 与 60 Hz 相同；4x 117 帧、115 次呈现（144 屏上降频不触发）；插帧跟显示器时 60 Hz 1x 呈现 113、120 Hz 1x 136、4x 插到 144 也是 136；2x 换画面节拍限与不限都稳定（两轮各 20 秒）。

### 5.3 Seeker（Mali-G615，120 Hz 屏）

| 情况 | 帧/秒 |
| --- | --- |
| 60 Hz 2x（HD / 原版画面＋关 MSAA） | 32 / 34 |
| 120 Hz 2x（HD / 原版＋关 MSAA） | 54 / 48.5 |
| 120 Hz 4x | 约 49–51 |

卡住 Seeker 的不是画质：每帧比一个 60 Hz VI 稍长，60 Hz 下要等两个 VI；120 Hz 下三拍（25 ms）就能显示。

2026-10-26 复测（0.5.0 之后的 main、HD 1.2、插帧跟屏幕）：enemy-cycle 迷你关的敌方阶段（同样约 1169 个游戏帧、含一次应对页），从确认回合结束到回到我方空闲：

| 档位 | 秒 | 游戏帧/秒 |
| --- | --- | --- |
| 1x | 39.4 | 29.7 |
| 2x | 22.1 | 53.0 |
| 3x | 21.3 | 54.8 |
| 4x | 20.9 | 56.0 |

三档、四档在 Seeker 上切得过去、档位生效，但游戏帧到 55 左右就上不去，实际只比 2 倍速快 4–5%。

隔帧不画（§3.5）之后，同样的测法（新包、HD 1.2、插帧跟屏幕，结束截图的地图区域与 2x 逐像素相同）：

| 档位 | 秒 | 游戏帧/秒 | 呈现/秒 |
| --- | --- | --- | --- |
| 2x | 22.34 / 22.35 / 22.58 | 52–52.5 | 73–74 |
| 3x（画 1/3） | 15.30 / 15.43 | 76 | 85 |
| 4x（画 1/3） | 15.05 / 14.96 | 78 | 66 |
| 4x 不跳（`SRW64_DRAW_EVERY=1`） | 21.07 | 55.5 | 53.5 |

3x、4x 比 2x 快约 1.47 倍，两档几乎一样快。试过的其他组合：

| 4x 的组合 | 秒 | 呈现/秒 |
| --- | --- | --- |
| 画 1/2 | 17.76 | 5.9（3x 画 1/2 也只有 6.4） |
| 画 1/4 | 14.45 / 14.64 | 88–89（转场闪） |
| 画 1/4，没画的帧也等拍换屏 | 15.8 | 90 |
| 不跳帧、所有帧立即换屏 | 16.28 | 55 |
| 画 1/4、所有帧立即换屏 | 14.14 | 88 |

3x 画 1/3、没画的帧也等拍换屏：16.55 秒。到每秒 80 步左右又上不去，线程仍然都没跑满（4x 时 RT64 Present 27%、Gfx 26%、游戏线程 22%）。Mac 上同一个包（原版画面）1x 38.93、2x 19.46、4x 9.81 秒，和改之前的 38.89–38.95／19.50–19.57／9.77–9.83 一样，没有判成慢设备。

大小核：Seeker 是 MT6878（天玑 7300），CPU 0–3 是 A55（2.0 GHz，`cpu_capacity` 228），4–7 是 A78（2.5 GHz，1024），游戏所在的 top-app 组 8 核都能用。4x 敌方阶段每隔几毫秒读各线程的 `/proc/<pid>/task/*/stat`，只数处于运行态的样本：Gfx Thread（`send_dl`、RT64 解释显示列表）94% 在小核，游戏线程 90%，SP Task 99%，RT64 Present 75%。这些线程每帧只忙一小段，系统按负载把它们放在小核。先做的实验是把进程所有线程都绑到大核：

| 档位 | 不绑／全部线程绑大核（秒） | 游戏帧/秒 |
| --- | --- | --- |
| 2x | 22.27／21.09 | 52.5／55.5 |
| 3x（画 1/3） | 15.30–15.43／14.19 | 76／82 |
| 4x（画 1/3） | 14.98／13.53、13.14 | 78／86 |
| 4x 不跳 | 21.07／17.83 | 55.5／65.3 |

结束地图都相同。绑大核后每个显示列表的 RT64 处理时间：标题 1x 下 8.9 → 6.5 ms，4x 敌方阶段约 13 → 11 ms，远没有到算力比的 4.5 倍，剩下的时间不在这个线程自己的计算上（RT64 等 workload 槽位、等 GPU）。所以小核只是一部分原因。

正式做法只绑关键线程、只在加速时绑（§3.6），同一个包对照：

| 档位 | `SRW64_BIG_CORES=0`（秒） | 默认（秒） |
| --- | --- | --- |
| 2x | — | 21.76 |
| 3x | — | 14.46 |
| 4x | 14.91 / 14.86 / 14.94 / 15.07 | 14.15 / 13.89 / 13.98 / 14.01 / 13.92 |

4x 快约 6%（全部线程绑是约 10%）；结束地图都相同。

耗电：插着线、电量 100% 时电池电流读数是 0，`dumpsys powerstats` 也没有数据，只能拔线经无线 adb 测（Mac 上的 adb 服务要在沙箱外启动，否则连手机报 No route to host）。拔线后在敌方阶段那一段每 0.2 秒读 `battery/current_now`（µA，放电为负）和 `voltage_now`，按手机时钟截出确认回合结束到回到我方空闲的区间，交替跑（屏幕常亮、HD 1.2、插帧跟屏幕、电量 100%、电池 29→31 °C）：

| 情况 | 秒 | 平均功率 | 能耗 |
| --- | --- | --- | --- |
| 4x 不绑 | 15.00 / 14.89 | 2.64 / 2.76 W | 39.7 / 41.0 J |
| 4x 默认 | 13.51 / 13.73 | 2.49 / 2.85 W | 33.6 / 39.2 J |
| 1x 不绑 | 39.11 | 2.80 W | 109.4 J |
| 1x 一直绑（`=1`） | 39.17 | 2.81 W | 110.0 J |

整机 2.5–2.9 W 里看不出绑大核多出的功耗：两组 4x 的差别（±0.15 W）比同组两次之间还小，每次敌方阶段因为更快结束，能耗持平或略少；1x 一直绑也一样。另外比较了游戏所有线程 `/proc/<pid>/task/*/time_in_state` 的增量（每秒平均有几个核在忙，平均频率）：

| 情况 | 小核：忙核数，平均频率 | 大核：忙核数，平均频率 | 敌方阶段（秒） |
| --- | --- | --- | --- |
| 4x 不绑（两次） | 1.37–1.39，1.18–1.20 GHz | 0.69–0.70，0.89 GHz | 14.92–15.10 |
| 4x 默认（两次） | 0.67–0.72，0.91 GHz | 1.30–1.31，0.75–0.77 GHz | 13.92–14.02 |
| 1x 不绑 | 1.03，1.23 GHz | 0.73，0.62 GHz | 39.24 |
| 1x 一直绑（`=1`） | 0.42，0.82 GHz | 1.25，0.57 GHz | 39.09 |

CPU 总时间基本不变（每秒约 2 个核），约 0.6–0.8 个核的工作从小核挪到大核；大核上平均频率只有 0.75 GHz 左右，小核的频率反而降了，所以整机功耗看不出变化。

**还差多少到真 4x（2026-10-26）。** 画得更少不行：4x 画 1/3、1/5、1/7（关键线程绑大核）各两次：14.17／14.13、13.83／13.74、15.56／15.42 秒。1/5 只快 2–3%，1/7 反而慢：插帧要补的画面更多（呈现 95–99 次/秒），而游戏本身每秒约 85 步的上限并不在画帧上。

simpleperf（`--trace-offcpu -g`，4x 敌方阶段 9 秒，`perf_harden` 已是 0）：

| 线程 | 睡眠 | 主要开销 |
| --- | --- | --- |
| Gfx Thread（`send_dl`） | 80% | 60% 在等下一个任务；`send_dl` 36%（每画一帧约 13 ms），其中 RT64 `State::fullSync` 31.5%：等 GPU 栅栏 12%、`renderAndSynchronize` 23%、等贴图上传 5%；真在算的（贴图哈希、拷贝）不到 10% |
| 游戏线程（`8007F9A0`） | 86% | 在 `osRecvMesg` 等消息；建显示列表 11.5% |
| RT64 Workload | 83% | 等 GPU 栅栏 25%、等新 workload 56% |
| RT64 Present | 74% | 等 GPU 栅栏 40% |
| SP Task（音频 HLE） | 85% | 合成 14% |

所以画的那一帧的大头不是解释显示列表，而是 RT64 默认开着的 `framebuffer.renderToRAM`（`rt64_emulator_configuration.cpp`，宿主没改）：每个显示列表都在图形线程上按原生分辨率再画一遍、等 GPU 画完、写回 RDRAM（`copyNativeToRAM`），正好卡在游戏等的路上。按列表关掉它（`State::setRenderToRAM(0)`，每个 workload 后清掉）一进迷你关就崩：RT64 改在 Workload 线程上做帧缓冲当贴图的复制（`FramebufferManager::createTileCopySetup`），每次新建 Vulkan 帧缓冲，内存耗尽（`Scudo ERROR: internal map failure (Out of memory)`）。要走这条路得先修 RT64 的这处，并确认游戏有没有用 CPU 读帧缓冲；实验开关已删。

插帧（跟 120 Hz 屏）：RT64 按 VI 历史猜游戏帧率，只看最近 3 个画面间隔、必须全相等，否则给 0、不插帧（`rt64_vi.h`）。120 Hz 下 Seeker 的 GPU 完成时刻落在 8 ms 拍边界两侧，1x 的间隔常是 3、5 拍，于是 70% 的帧没有帧率（60 Hz 下也有 53%）。现在宿主在每个显示列表前把逻辑步频（`game_speed::step_rate()`：30，加速时 30×档位）用 `State::setRefreshRate` 交给 RT64（`graphics.cpp` `send_dl`；RT64 每个 workload 后清掉）：

| Seeker，插帧跟屏幕 | 无帧率的帧 | 呈现/秒 | 游戏帧/秒 |
| --- | --- | --- | --- |
| 60 Hz 1x | 53% | 55.9 | 29.4 |
| 120 Hz 1x，不给帧率 | 70% | 47.3 | 29.8 |
| **120 Hz 1x，给帧率** | 0 | **81.1** | 29.9 |
| 120 Hz 2x，不给／给帧率 | 100%／0 | 57.3／70.2 | 53.8／51.4 |

Mac 上 1x 插帧仍是 60 次呈现、4x 不受影响。慢设备上 2x 插帧会多花一点 GPU（游戏帧 53.8→51.4，在 Seeker 本身的波动范围内）。

### 5.5 音频队列

Deck、Seeker 上曾看到 120 Hz 时音频队列长 20–40 ms。那是 `audio-live.json` 的单个瞬时值：它记的是某一次入队刚完成时的设备队列，随设备取数的相位锯齿式变化，不能拿来比较。调试状态加了 `audio_stats`（入队时已排队的帧、游戏询问剩余量时的队列与得到的回答、两次入队的间隔分布），取 15 秒平均：

| 平台、情况 | 入队时已排队 | 询问时队列 | 告诉游戏 | 入队间隔落在 15.5–18 ms |
| --- | --- | --- | --- | --- |
| Mac 60 Hz／120 Hz，1x | 14.1／13.9 ms | 30.7／30.5 ms | 13.5／13.4 ms | 50%／86% |
| Seeker 60 Hz／120 Hz，1x（各两次） | 21.3–21.5／21.5–21.6 ms | 37.8–38.0／38.0–38.1 ms | 14.8–14.9／14.9–15.0 ms | 55%／92% |
| Seeker 60 Hz 2x／120 Hz 2x／120 Hz 4x | 21.6／21.6／21.6 ms | 38.2／38.1／38.0 ms | 15.0／15.0／14.9 ms | 59%／89%／91% |
| Deck 60 Hz／120 Hz，1x（各两次） | 15.8–16.0／15.7–16.2 ms | 32.4–32.6／32.4–32.8 ms | 14.1–14.2／14.1–14.3 ms | 100%／100% |
| Deck 60 Hz 2x／120 Hz 2x／120 Hz 4x | 16.0／16.1／15.9 ms | 32.6／32.8／32.5 ms | 14.2／14.2／14.1 ms | 100%／100%／99% |

两种频率下队列一样深，每秒都是 60 次合成；120 Hz 下合成的间隔反而更均匀（音频线程只在偶数拍听回扫，抖动小）。

## 6. 开关与调试状态

| 环境变量 | 作用 |
| --- | --- |
| `SRW64_VI_RATE=60` | 退回原版 60 Hz（最高 2 倍速） |
| `SRW64_FORCE_FAST=1` | 设置开着 2 倍速时每一帧都加速（测量用） |
| `SRW64_VI_AUDIO=all` | 音频每拍都收回扫（对照） |
| `SRW64_VI_LATCH=0` | 关掉 2x 换画面节拍 |
| `SRW64_RT64_BASE=60` | RT64 基准帧率退回 60（对照） |
| `SRW64_PRESENT_PACE=0` | 关掉呈现降频 |
| `SRW64_RT64_RATE_HINT=0` | 不把逻辑步频交给 RT64，让它按 VI 历史猜（对照） |
| `SRW64_DRAW_EVERY=N` | 3x/4x 时不管设备都画 N 帧中的 1 帧；`=1` 永远不跳（§3.5） |
| `SRW64_SWAP_NOW=0` | 没画的帧也等拍换屏（对照） |
| `SRW64_BIG_CORES=1` / `=0` | 安卓：关键线程一直绑大核／从不绑；默认只在加速时（§3.6） |

调试状态：`sched`（`factor`、`retraces`、`audio_skipped`、`interval`、`rendered`、`sync_mode`、`logic_ticks`、`picture_ticks`、`latch_slow_spells`）、`rt64_original_rate`、`lists_without_rate`（RT64 没有帧率时送出的显示列表数）、`audio_stats`（§5.5）、`present_gaps`（呈现间隔分布）、`present_steps`（相邻呈现隔几个 workload）、`draw_skip`（§3.5）、`big_cores`（安卓，§3.6）。安卓用 `attach.py --env`，桌面 `--play` 启动器已放行这些变量。
