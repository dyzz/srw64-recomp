# 新机体、新武器用真正的新编号（路线 B）

2026-11-16。状态：**B1–B5 都已实现并实机验证（§10、§11）**。接在[战斗动画与自定义机体可行性](../data/battle-animation.md)（路线 A／B／C）和[新机体与新武器](mod-names-art-data.md) §2.3.1 之后。审计工具 `tools/recomp/audit_table_readers.py`，测试 `tests/test_audit_table_readers.py`。

## 1. 为什么要换路线

终极断空我走的是路线 A：借用原版没人用的号码（`src/host/mod_units.hpp` 的空号清单）。一台机体就把空号用掉了大半：

| 空号 | 总数 | 终极断空我占用 | 剩余 |
| --- | --- | --- | --- |
| 机体号（νガンダム 重复记录） | 314、325 | 314 | 1 |
| 武器号（无人带的副本） | 881、882、1209 | 全部 | **0** |
| 地图图标资源 | 978、991 | 978 | 1 |
| 场景总表槽 | 10 | 1003、1051、1052 | 7 |
| 前任表行 | 3 | 1 | 2 |
| 武器继承映射行 | 15 | 3 | 12 |

此外还有两个结构性的毛病：

- **图是借来的**：站姿 (2324, 1724, 2016) 是现有 ROM 资源（デスサイズ 的图集配别的调色板），只有 HD 包按这个三元组换图时才是终极断空我。所以原版图像下整个包不加载，包要求 `srw64.hd >=1.3`。
- **乘员表加不了行**：`D_800CA418` 后面紧接着别的表。现在靠剧情 MOD 换机后由宿主直接写机体实例。

下一台新机体最多只能放进 325，而且一件新武器都加不了。所以要改走路线 B：表本身扩出新行，新机体、新武器、新资源都用原版之外的新号码。

## 2. 读取点审计（2026-11-16，静态）

### 2.1 方法

生成的 C 代码（`build/recomp/cpu-bound/generated`）里每条指令都带着 MIPS 反汇编注释。表地址都是用 `lui` 加 `addiu`／`ori` 拼出来的：ROM 地址交给 DMA 辅助函数，RAM 地址则用 `lui` 加读写指令的偏移。

`audit_table_readers.py` 在每个函数里按指令顺序追踪 `lui` 放进寄存器的值，经过 `addiu`／`ori`（精确值）和 `addu`／`subu`（基址加下标），记下它落进哪张表：要么是拼出的常量，要么是读写地址。另外列出和表大小、上限相同的比较立即数（363、354、1329、1053、6436 等）。

这个方法有三个局限：

- 不跟分支，所以结果是线索，每条都要读原代码确认；
- 如果基址是从别的函数传进来的，就扫不到；
- 只能找已知的表。还没认出来的、按机体号索引的表，靠 §6.2 的运行时绊线兜底。

测试 `test_build_readers` 把下面这些读取点的数目锁住：重新生成代码后如果多出读取点，测试会失败，提醒回来补方案。

### 2.3 战术地图 overlay 里的地图图标表

ROM `0x100D78` 随战术地图 overlay（`load_000AB160`）一起载入 RAM `0x80218218`。原文档说有 5 处 `lhu` 读它，审计实际找到 **21 个函数、23 处读取**，另外 `801C60C0` 拼了一次基址。读法统一是 `lui rX, 0x8022` → `addu rX, rX, 下标×2` → `lhu …, -0x7DE8(rX)`。ROM 那份没有任何直接读取点。

### 2.6 存档里的位宽（代码确认）

- **机体号存 10 位**。场间存档 `80092240` 和中断存档 `80092CA4` 都写 `机体号 << 6 | (实例 +0x2C & 0x3F)`。读档（`srw64_original_intermission_restore` `800927A4`）先把 `0xFFFF` 当空槽，再用 `srl 22` 取出机体号，交给 `800A8CE8` 重建实例。所以新机体号最大 1022。剧本里 999 表示「只登记驾驶员」，也要避开。
- **武器号存完整 16 位**（代码确认）：
  - 场间存档（`srw64_original_intermission_serialize` 里 `800925A8` 起的循环）为 700 个武器槽各写 6 字节（`80092498`）：`+0` 武器号（`0xFFFF` 为空）、`+2` 实例 `+0x18`、`+4` 段数 `<<4 | +0x22 低 4 位`。
  - 机体记录（16 字节）的 `+0xE` 存它第一件武器的槽号，件数是机体号字低 6 位。
  - 读档时 `80092BA8` 起的循环逐槽调 `800A8E5C(槽, 武器号)`，按存下来的武器号重建实例；机体部分则由 `800A8CE8` 按机体号重建数值，再把武器指针指回槽号。
  - 所以新武器号不受位宽限制，只要避开 `0xFFFF`；读档也不依赖武器列表，列表以后改了，旧存档里的武器照旧。代价是存档同样依赖武器号，§3.6 的改号要连武器槽一起改。

### 2.7 其余数据常量的归类（找没认出来的表）

§2.1 的扫描只认已知的表。为了找漏掉的，把生成代码里所有拼出来、落在常驻区之后（ROM `0x5BC30`–`0x2000000`）的常量全部列出来，共 114 个，逐个归类：

- **overlay 的起止地址**：`8007FD80`–`80080138` 那一组载入函数用的。
- **显示列表的分段地址和 GBI 命令字**：`0xC6xxx`（常驻静态列表，例如 cut-in 遮框 `800C6D00`）、`0x2184F0`、`0x6019C`、`0x6031C`、`0x14816C`、`0x2C81E8`，以及 `0x200400`、`0x163011`、`0xFF00xx` 等掩码和颜色。
- **按人物索引**：人物能力 `0x7A1A0`、技能阈值 `0x7B1B0`、精神习得 `0x7CFB0`、头像 `0x7C05C`／`0x7C07C`／`0x84220`、人物战斗曲 `0x7D6A0`。新机体不影响这些表；新人物是另一件事。
- **其他**：`0x6EC10`（`8008A568`，只有文字引擎 `8008B724` 一个调用者，2 字节一项、约 6000 项）、章节标题 `0x84B20`、调试表 `0x847D0`／`0x8AB58`、台词与语音表 `0x1161C0`／`0x121150`／`0x20F250`、命中特效与防御反应库、文字表 `0x1A34980`。
- **按机体号索引、§2.2 原本漏掉的：只有机体战斗曲 `0x7DF30` 一张**，已补进表和审计脚本。

overlay 自带数据里如果还有按机体号索引的表，这个办法找不到，因为那类表读的是 RAM 地址，像 §2.3 的地图图标那样。

## 3. 方案

### 3.1 ROM 表：改基址到虚拟窗口

做法分三步：

1. 在宿主的 `8007F704` 里加一个虚拟窗口，每张表占一块。块里的内容是「原表的字节（叠加数值 MOD 的补丁）」加上「新行」。窗口要放在 **`0x08000000`** 起：已经占用的虚拟 ROM 段有名字字形 `0x02400000`、改造文字 `0x03000000`–`0x03400000`，以及剧情 MOD 文字 `0x03400000`–`0x07400000`（`story_mod.hpp`，遇到不认识的记录会抛错）。顺便把这几段登记进同一个头文件，免得以后再撞。
2. 生成器用现成的常量改写机制（`generate_cpu.py` 的 `MAP_WIDTH_CONSTANTS`，按（函数名, 指令地址）定位），把 §2.2 那 17 处拼基址的 `addiu` 常量改成 `原常量 + (窗口地址 − 原表地址)`。`lui` 不用动。
3. 下标乘步长的算法不变，所以号码 ≥ 原表行数时，地址自然落到窗口里的新行。

具体到各表：

- **武器列表**：整块搬进窗口（363 个指针加全部行），新机体的指针指向窗口里的新行。`0x82E40` 那 720 字节的空隙就不用再省着用了。
- **动画记录**：偏移是相对 `0x184990` 的 u32，新记录放进窗口，偏移写成 `窗口地址 − 0x184990`。不用再占用偏移表的副本 `0x19AA40`。
- **机体战斗记录**：354 行扩到和机体表一样长。原版 354–362 号机体也就有了自己的行，不会再读到后面武器表的内容。

### 3.2 地图图标：搬到空闲 RAM

把 23 处 `lhu …, -0x7DE8(rX)` 的偏移常量改成 `-0x7DE8 + (新表 − 0x80218218)`，新表放在空闲 RDRAM 里。可用范围是 `0x80415300`–`0x807E0000`，宿主已经占用 `0x807E0000` 以上。overlay 载入时（`8007F704` 里的 `overlay_loaded` 那一段），宿主把原表 363 项加新项写进新表。新表的位置要在宿主登记一张「RDRAM 占用表」，免得以后和别的功能冲突。

### 3.3 资源：新资源号

- 把 `80089EAC` 的 `0x1924` 改成宿主给的上限。
- `80089BBC` 读描述符不经过 `8007F704`，所以要由宿主接管（加进 `NATIVE_HOOKS`）：号码 < 6436 调原函数；新号码由宿主填描述符，数据地址指向虚拟窗口，解压读数据时照常经过 `8007F704`。
- 宿主侧直接读资源表的代码要接同一份登记：`rom_art.cpp`、`src/native/app/rom_import.cpp`，以及启动前准备图片的 Python（`battle_graphics.py`、`export_graphics.py`）。
- 新资源在 HD 下照常按内容摘要换图。原版图像下显示 MOD 自带的原像素图。这样「原版图像下整包不加载」的限制就没有了。

### 3.4 名字

把 §2.5 里 33 处加 527／1370／2699 的常量改成表达式：号码在原表范围内照旧，新号码映射到宿主的私有文字号区间。宿主的文字描述符钩子（`srw64_original_text_descriptor`，`8008C510`）提供这些记录，内容取自 `mod_names`。

### 3.5 成对表：不扩表，由宿主补查

- **乘员、前任、武器继承**：读这几张表的函数里，有好几个已经由宿主接管（`unit_register`、`deploy_record`、`weapon_inherit`）。在宿主里加「MOD 额外行」，原表查不到时再查它。实现见 §10.4：前任查找 `800AA814` 由宿主应答（`800A9A70`、`800AAD28` 都经它取行），武器段数在 `800AA8F4` 之后由宿主补写，所以 `800AB33C` 不必接管；乘员在 `800AAD28` 登记之后写。
- **变形、合体**：涉及的读取点多（约 30 个函数），第一期不做，新机体照现在这样去掉 変形／分離／合体 能力。

### 3.6 号码怎么分配

存档里存的是号码，所以同一台 MOD 机体在不同的运行之间必须拿到同一个号码，不能按包的载入顺序现排。做法如下：

- 包里只写本包内部的名字，例如 `"units": {"final": {...}}`。剧情 MOD 引用时写 `"unit": "@final"`（跨包引用写 `包id@名字`），由宿主解析成号码。
- ~~宿主在用户数据目录维护一份登记表~~（实现时改了，见下一条）。
- **实现的做法**（`mod_units.hpp` `assign`）：号码由「包 id@名字」的 FNV-1a 哈希算出，机体落在 400–998，武器落在 1400–2399（受私有文字号的区间限制，§10）；两个名字算到同一个号时，按哈希顺序后来的往后挪一位。所以不需要登记文件：同样的包在任何机器、任何安装顺序下号码都一样，只有新装的包和已有的包撞号时才会挪动。
- 存档旁的 `mod-units/<哈希>.json`（v2）记下每个号码对应的「包 id@名字」，机体在 `keys`、武器在 `weapon_keys`。读档时按名字自动改号（§10.4）：名字现在算出别的号，就把记录里的机体号、武器号改成新号再交给原版解析；号码对应的包没启用，就拦下、回标题并提示（`mod_saves.hpp`）。
- 号码 ≥ 363 的机体在原版里根本不存在，所以停用 MOD 后读到这种存档一定能识别出来，比现在借 314（停用后会变成一台 νガンダム）更容易判断。

### 3.7 终极断空我迁移

1. 新机体、新武器改用名字（`final`、`final-cannon` 等），站姿、场景改用 MOD 自带的新资源。
2. `story/final.json` 里的 314 改成 `@final`。
3. 旧存档：用 v1 伴随文件和驾驶员确认归属，或用该机武器槽里的三个旧专用武器确认来源。把旧 314、专用武器 1209／882／881、以及武器槽的适用机体编号一起迁移。机组、改造段数和装备由原版恢复，读档时保留磁盘记录原样。普通 ν 高达继续用 314。

## 4. MOD 格式 v2 草案（`data/new_units.json`）

```json
{
  "schema": "srw64.new-units.v2",
  "resources": { "stance": "art/battle/stance.bin", "cannon-atlas": "art/battle/cannon.png" },
  "scenes":    { "cannon": ["@stance-scene", "@cannon-atlas", "@cannon-palette"] },
  "weapons":   { "final-cannon": { "copy": 875, "inherits_from": 875, "animation": { "camera": 1, "…": "…" } } },
  "units":     { "final": { "copy": 224, "pose": ["@stance", "@stance-atlas", "@stance-palette"],
                            "icon": "art/icons/final.png", "weapons": [870, 871, "@final-cannon"],
                            "inherits_from": 224, "crew": [171, 168, 170, 169, 166] } }
}
```

规则：

- 写数字就是原版的号码，写 `@名字` 就是本包的新东西；
- `resources` 可以是原版格式的二进制，也可以是 PNG，PNG 由工具切成图集（见 §7）；
- `crew` 进宿主的额外乘员行（§3.5）。

### 6.2 运行时绊线

漏改的读取点会用原基址加大号码去读，地址落在原表结尾之后、而且对齐到这张表的步长上。开发构建在 `8007F704` 里检查每次读取：如果地址在某张已登记表的结尾之后、与基址的距离是步长的整数倍、读取长度也和平常一样，就打出 `SRW64_TABLE_TRIPWIRE 表名 号码 调用者`。正常读后面那张表也可能碰巧对齐，所以这只是线索，不报错。overlay RAM 里的表做不了这种绊线，只能靠静态审计。

### 10.2 没有包给的号码

存档里有新机体、但包被停用时，原版在被拦回标题前还会照常读一阵这台机体。第一次实机这时宿主崩溃（SIGBUS）：名字记录没有来源，原版去读文字表 0 末尾之后的乱数据；武器表偏移是 0，把指针表当武器行一路读下去。现在：没人给的新号码读 0 号行（机体 0、武器 0 的记录），武器表指向 ROM 里那段 0xFF 空隙（空列表），名字记录借 0 号机体／武器的名字（`window_byte`、`upgrades::name_source`）。

- **人物号带标志**：人物记录 `+0` 只有低 9 位是人物号，敌方段每条都带 0x200（实测 433 存成 0x3B1）。`mod_saves.hpp` 取号时 `& 0x1FF`，改号时保留高位。之前我方段改号也没处理标志，只是我方没遇到带标志的。
- **改动**（`mod_saves.hpp`）：`banks()` 给中断存档三段；伴随文件的机体、武器、人物键覆盖三段，`restored` 也查敌方和第三方的池。
- **实机（Windows，凯的测试包）**：剧情 MOD 增援组放出敌方新人物 433（劲敌）开新机体 727（RZ测试）、只带新武器 1960；地图上中断存档，伴随文件记下 727、1960、433。把伴随文件改成 727＝`@zb`、433＝`@kai` 模拟号码变动，重开后「继续」：日志 `remapped {"units":{"727":619},"pilots":{"433":434}}`，读回的敌方是 619＋434，地图图标变成 ZZ。

## 11. B3：包自带的战斗图（2026-11-16，已实现并实机验证）

### 11.1 资源怎么进游戏

- 载入函数 `80089E9C(资源号)` 先查自己的槽表，再调 `80089BBC(资源号, &解压后大小, &偏移)`：后者用一次 PI DMA 读描述符里的偏移，再读 `0xA20BD0+偏移` 处的 4 字节解压后大小；然后 `800897AC` 从 `0xA20BD4+偏移` 起经 `8007F704` 读 LZSS 流解压。`80089EAC` 的 `sltiu 0x1924` 是唯一的上限。
- 宿主接管 `80089BBC`（`NATIVE_HOOKS` 的 `srw64_original_resource_descriptor`）：6436 号起的包资源由宿主给大小和偏移，偏移指向资源窗口（`0x0A000000`–`0x0C000000`）；上限改成 `0x4000`（`generate_cpu.py`）。读流照常经 `8007F704`，宿主从窗口里给。
- 流只用字面量：每 8 字节前放一个 `0xFF` 标志字节（`mod_sprites::stream`），解压器照常认，体积多 1/8。

### 11.2 PNG 怎么变成三份资源（`src/host/mod_sprites.hpp`）

- **调色板**：种类 3、字节数 256、4 字节 0，再是 128 个 RGBA5551。0 号透明；不透明颜色按 RGBA5551 算最多 127 种，多了整份不用（作者先用 `tools/mods/sprite_pixels.py` 减色）。半透明以下（alpha < 128）算透明。
- **图集**：种类 7（和 361 台机体站姿一样）、宽、高、0，再是 CI8 像素。每帧按原图的 32×32 格子原样放进图集（和 ROM 的站姿一样：游戏画一块时会多采右边一列、下面一行，所以图集里的邻居必须是原图里的邻居），多帧上下排、帧与帧之间空一行，最右空一列；全透明的块不出零件。单帧时宽高就是 32k+1。2026-11-20 之前是去重后每行 8 块重排，原版图像下图块边界会出现别的块的一像素线（Windows 实测发现，见 [机体 MOD 网页工具](unit-mod-web-tool.md) W1）。
- **场景**：步数、顶点模式；每步（帧, 拍数）；`FF`、循环步；每帧一个 u16 偏移；每帧的 16 字节零件（标志 0、s、t、32、32、x、y、顶点偏移）和结束零件（`0x8000`，末 4 字节是本帧顶点的结尾）；16 对齐后是顶点，每个 16 字节（x、向上的 y、z、0、10.5 定点的 s、t、0）。`mirror`（默认）用模式 0：每块 8 个顶点，后 4 个绕 x=0 镜像给另一侧；cut-in 这类不该翻的用模式 1：每块 4 个。格式和 ROM 里的站姿逐项对过（2324 号），`tests/test_mod_sprites.py` 用 ROM 工具自己的解码器把宿主生成的结果读回来。
- `origin` 是图里对应场景原点的像素：站姿是脚下中间（ROM 站姿的范围大约是 x −60…70、y −90…6）。

### 11.3 包里怎么写

```json
"sprites": {
  "stand":        { "image": "art/battle/stand.png", "origin": [59, 90], "hd": "art/battle/stand-hd.png" },
  "cannon-cutin": { "image": "art/battle/cannon-cutin.png", "origin": [56, 48], "mirror": false,
                    "ticks": [22], "hd": "art/battle/cannon-cutin-hd.png" }
},
"scenes": { "cannon-cutin": "@cannon-cutin" },
"units":  { "final": { "pose": "@stand", ... } }
```

- 多帧写 `"frames": [...]`，配 `ticks`（每帧拍数）和 `loop`。
- `around: [前, 后]`（默认 [0, 0]，各 0–32）：在自己的场景资源前后再放几份同样的场景。演员 +0x2C 存的是场景的**资源号**，有的行为例程会把演员切到相邻的资源号（`801C5700` 加 k：光束 118 切到 +1、+2，原版就是光束身 3559、尾 3560）；包里的图放在这种演员上时，前后没有场景，切过去就把图集当场景读，守方视角一画就崩（RT64 LoadTile 读出 RDRAM）。每个行为切几格见 `weapon-animations.json` 的 `steps`，网页「换图」自动填。另有 58 个行为拿场景号做别的计算（`battle_steps.hpp` 的 complex），一条记录里只要有一个，演员就只能用原版的图（cut-in 除外），宿主拒绝加载。
- **换色**（`scenes.<名>`: `{"recolor": 行号, "colors": {"格号": "#rrggbb"}}`，`mod_units::recolor`）：原版战斗场景总表那一行的场景、图集照旧，调色板是包自己的一个资源：从 ROM 读原调色板（`rom_import::resource`），改写列出的格（RGB 换成 RGBA5551，保留原来的透明位），长度不变，所以行为例程切到相邻场景（光束身、尾用同一张调色板）、拿场景号计算的例程都不受影响，complex 记录也可以换色。`Taken::palette_sources` 记「包调色板 → 原调色板」，`host.cpp` 交给 `sprites::set_palette_sources`：HD 画面按原调色板找原场景的 HD 图，再按游戏实际画的颜色走已有的重着色变体（和游戏自己改调色板时同一条路）。没有 HD 图的特效在 HD 画面里照样是原版像素配新颜色。`tests/native_mod_data.cpp` 核对光束 56 的换色。
- 资源号按包的顺序从 6436 起排，每张图占 3 个（带 `around` 的再多前后几份场景：前面的副本、自己的场景、后面的副本、图集、调色板）；资源号不进存档，所以不用像机体号那样固定。
- `hd` 是每帧一张的 HD 图，宿主按（场景, 图集, 调色板, 帧）登记成 HD 画面（`sprites::add_generated_image`），只在 HD 图像模式下画；原版图像模式画包自己的像素图。
- 原生页面（改造、能力、换乘、战前页、图鉴、战斗鉴赏）显示的机体图来自这里：`mod_units::art` 给出像素图和 HD 图，形状和 `battle_assets.py` 的条目一样。

### 11.4 终极断空我

站姿、断空砲发射姿势、断空砲 cut-in 改成包自带的图（像素图由 `sprite_pixels.py` 从 HD 图缩小、减色得到：91、99、90 色），不再借デスサイズ、ウイングゼロ 和一张没人用的 cut-in。包不再要求 `srw64.hd`：原版图像下也加载。光牙剑的两段 cut-in 仍借原版断空我的 cut-in（只换了调色板号），原版图像下就是原版的四人 cut-in，HD 下由 HD 包换上加了阿兰的那张。
