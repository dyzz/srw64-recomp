# 宽屏战斗演出的「展开」：由来、提交、现在的问题与困难

2026-11-18。起因：录屏素材里 **天馬翔覇（武器 152，アースゲイン 34）和 鳳凰光覇（武器 1182，スーパーアースゲイン 306）的战斗动画，机体跑到了画面最左边**。本文交代这个问题从哪来、到现在为止的相关提交、这次查到的东西、同类问题的范围和眼下的困难，供接手的会话继续。

技术细节的正文在 [battle-animation-rendering.md](battle-animation-rendering.md) §17，代码 `src/host/battle_spread.hpp`，本文不重复。

**11-18 实测更新**：天馬翔覇使用录屏语音包时，关掉展开仍会滑出画面。已修复语音等待期间战斗更新多走的问题，见 [audio-mods.md §12.2](audio-mods.md#122-长语音先播差值保留原版动作时长2026-11-18)。下文第 3、6 节保留排查前的假设和计划，第 4 节是独立的场景分类调查。

## 1. 问题的由来

1. **宽屏铺满（09-29/30，v0.3.1 起）**。`c631da78` 让画面随屏幕从 4:3 放宽到 16:9；`e81197a7` 让战斗铺满：天空按 ±320 多画两份、3D 视口不再居中、去掉遮幅条、HUD 贴边（[deck-16x10.md](deck-16x10.md) 第 8/13 条）。地面、机体、特效都是 3D 场景里的东西，视口放宽后自然往两侧多显示一些，这一步没有挪动任何东西。
2. **放宽后露出来的毛病（11-10 玩家录像，安卓 16:10）**。原版的演出是按 4:3 屏幕摆的：
   - 飞行物的入场、出场点写死在「镜头目标 ±160」，也就是原版屏幕边。宽屏下这个位置在画面中间，于是光弹凭空出现、半路消失（F91 的 メガマシンキャノン）。读这个镜头目标的行为例程有 214 个，逐个改常量不现实。
   - 必杀技的整屏背景是按 4:3 大小做的普通精灵，宽屏下两侧露黑（スペースコンビネーションアタック 的红色漩涡）。
3. **展开（11-10 起）**。办法是在每帧算精灵矩阵的 `8008261C` 外面包一层：调用期间临时挪动精灵的位置和缩放，算完写回。游戏状态、帧数、随机数都不变。中间那段不动，两侧线性拉开，让原版屏幕边落到画面边；光束拉长；整屏背景放大。
4. **一直在补的根子**。展开是屏幕空间的变形，只对「按屏幕边摆」的东西有意义；可战斗里大部分东西（地面、机体、贴在机体上的特效）是摆在世界里的。哪些该挪、哪些不该挪，游戏数据里没有现成的标记，只能靠规则去猜。到现在每一版出的问题，都出在这个「猜」上。

## 3. 这次的问题：天馬翔覇／鳳凰光覇

### 3.1 静态查到的

两招的脚本几乎相同（镜头模式 0，命中脚本 106，攻方动作 73），21 个演员。关键的一个：

- 登记 734／738，场景 **2897／2902**，行为 **57**，用的是**机体自己的图集**（2894／2905，即 `unit_poses[34]`、`[306]`）——这就是天马、凤凰形态的机体。它是脚本演员，不在槽 168/169 里，所以 `b422f2d6` 的「机体不碰」**保护不到它**。

其余演员：3950、4473、3794 三张整屏背景（行为 289/277）；火焰类 4496–4499（行为 56/70，跟着机体）；4519 毛笔招式字 4502–4508（行为 58，自己摆）。

行为 57（`80217D58`）：等相位 0x57 时换场景并显示，0x51 时隐藏；相位 4/5 看机体槽 +0xC 的坐标推进（−200 或 0 起，≥ 250 结束）；结束时清 +0x36（不再算在用）。它**跟着机体摆**（不写摆法 +0x38），也不写自身速度。

### 3.2 为什么会被推走（推断，未实机）

按展开现在的规则，跟着机体摆的演员在离机体半个原版半宽以内时，会保持与机体的原始间距，不该被推走。所以静态上**解释不了**。候选：

1. **机体位移在 +0x28 而不在 +4**：`801C5BAC` 给跟随演员定位时，加的是「机体槽 +4..+0xC **加上 +0x28..+0x30**」；`battle_spread.hpp` 算跟随修正时 `host` 只读 +4。如果冲刺时机体的位移主要在 +0x28，演员和 `host` 的距离会超过阈值，跟随修正渐变为零，演员按自身位置被外推到画面边。（可能性最大）
2. **跟随修正对错了机体槽**：修正用块 +0x23 选 168 还是 169；如果这两招的演员所在的块和 `801C5BAC` 实际加的槽不一致，就会对着错的机体算。
3. **其实不是展开的问题**：原版 4:3 下机体可能本来就在原版屏幕左缘，宽屏只是让它看起来不在边上了。要先用 `SRW64_BATTLE_SPREAD=0` 对照；关掉仍在最左，就用 ares 看原版。

同一个行为 57 还用在 **天王捷破斬（159，ヴァイローズ 35，场景 2859）**，多半也有问题。

## 5. 当前的困难

1. **游戏数据里没有「这是屏幕上的东西还是世界里的东西」的标记**。展开只能靠规则猜。`b422f2d6` 把范围从「所有槽」缩到「脚本演员」，但演员里仍是**默认处理**：凡是站在 |u| > 0.3 的都会被平移。这和第一版出问题的根子是同一个，只是范围小了。这次的问题说明，演员里也有「世界里的东西」，而且就是机体本身。
2. **不能简单按「画机体自己的图集」整类排除**。机体图集里既有机体本身（姿势、变身形态），也有会飞出去、本来就该到画面边的部件（ロケットパンチ、有线拳、锁链、伸出的手臂）。要区分「机体本身」和「从机体飞出的部件」，现有数据里没有直接的字段。
3. **跟随修正和原版定位不完全一致**（第 3.2 节第 1 条），而且没实机数据，不知道是不是这个原因。
4. **验证成本高**。1329 个武器脚本、294 个行为例程，一场演出要跑几分钟，判断基本靠看录像。§17 记过：想用「4:3 以外出现特效的帧数」自动统计，会被转场扫描线和本来就越界的长图干扰，开/关的数字很接近，不能当证据。到现在实测过的飞行武器只有 31 件，必杀技、变身类几乎没覆盖。
5. **只在 Windows 上验证过**，Mac 和安卓都没有。
6. **原版对照缺位**。有些「偏」是原版 4:3 本来就有的（例：4039／4045 留边，查明是测试机体的缩放 85%），每一个疑点都要先排除这一种。

## 6. 下一步（建议）

1. **实机取数**（Mac，`srw64_launch` 独立会话，HD，1280×800）：战斗鉴赏，攻方 机体 34＋ブラッド（驾驶员 27，`route: 0`）配武器 152，再试 306／1182、35／159。开/关 `SRW64_BATTLE_SPREAD` 各录一遍。冲刺那几帧用 `srw64_memory` 读：槽 168/169（`0x800FFA70 + 槽×0xC4`）的 +4..+0x30、行为 57 演员所在的槽、块 +0x23。按第 3.2 节判断是哪种原因。
2. **定修法**。下面是要用户拍板的方向：
   - **小修**：如果是原因 1，跟随修正的 `host` 改成和 `801C5BAC` 一致（+4 加 +0x28）；A 类里的机体姿势图从光束／背景表里拿掉（脚本里有 `NOT_BEAMS`／`NOT_BACKDROPS`）。改动小，但同类问题以后还会一件一件冒出来。
   - **反过来，改成白名单**：只有明确是飞行物或背景的场景（光束表、背景表，再加一张「飞行物」表）才挪，其余演员一律不动。漏列的后果只是「这一发没飞到画面边」（和关掉展开一样），不会把机体挪走；代价是要离线或靠实机补全飞行物表。从 §17 的教训看，这个方向更稳。
   - **加运行时审计**：在 `battle_spread::apply` 里（用环境变量打开）记录「画机体自身图集、而且被平移超过若干单位或缩放不是 1」的演员（武器号、场景、u、平移量）。用鉴赏把 328 件逐件跑一遍，拿到 B 类的完整清单，也可以拿来补白名单。
3. 修完按 §17 的方法复验（机体站定边界、地面、光束到边），补 Windows 台式机一遍，结论写回 §17。
4. 注意：`battle-animation-rendering.md` 工作区里有别的会话没提交的改动，写回时只提交自己的行（记忆 [srw64-shared-worktree]）。

## 7. 伸缩武器的命中位置复核（2026-11-18）

对照原版 ROM 模拟器与 Windows 当前版，攻方分别选机体 13、15、176、182，守方统一用机体 34、驾驶员 27。原版用临时 ROM 副本替换演示对战表的一组参战数据，沿用原版动画脚本。Windows 鉴赏用原图、无语音包。原版演示与鉴赏的伤害和对白可以不同。录像按转场或首次命中闪光对齐，保留原速。

- **65 龙爪，场景 2909**。首次命中闪光前一帧，原版和当前版 4:3 的金色爪尖都已叠在守方身上。当前版 16:10 的爪尖停在守方右侧，16:9 的间隙进一步扩大。命中闪光仍出现在守方身上。现象已复现；宽屏位置和横向缩放各占多少，尚待验证。
  - **11-21 查明并修复**（Mac，HD，鉴赏 机体 13＋驾驶员 11 打 34＋27，草原）。龙爪的演员（槽 171，行为 65）不是一直用 2909：攻方镜头里 2909 伸出、2910 伸满；镜头切到守方后依次换成 2911、2912（命中那一帧）、2913。这几张是行为例程按编号直接换上的，不在战斗场景登记表里，`battle_spread_scenes.py` 只给登记过的场景分类，所以它们不在光束表里，只被当成点平移。守方镜头里，爪的根部在镜头外约 200 单位（u≈1.24，正好在原版屏幕边外），平移把根部再往外推了约 40 单位，整只爪跟着右移，爪尖就停在守方右侧。把 2910–2913 加进光束表（先放在 `EXTRA_BEAMS`，后来并入 §9 的 `SWITCHED`）以后，根部仍外推，爪尖按光束规则落在原来的位置（守方附近在 |u| ≤ 0.3 内，不动）。修后命中那一帧，4:3 设置、16:10、16:9 的爪尖都叠在守方身上，爪身伸到画面右边（`build/recomp/debug/claw/contact-aspects.jpg`，修前修后对照 `before-after-16x10.jpg`）。

## 8. 恶魔高达各招录屏（2026-11-20，Mac，1280×800，HD，宇宙背景）

战斗鉴赏，攻方 デビルガンダム 四种形态（机体 24／25／26／303，驾驶员 15 或 14）和 デビルアクシズ（38，驾驶员 313），守方 シャイニングガンダム＋ドモン（3／4），伤害 3000。一共 17 段不同的动画：武器 94–104、1168–1171、1233、1234（1235 与 1171 同一段）。展开开着。录像在 `build/recomp/debug/devil/`（`<武器>-u<机体>.mp4`，`sheet-*.png` 是每秒 3 帧的缩略图，红框是原版 4:3 区域）。

**仍是 4:3 的：マザーテンタクル（95）和 ガンダムヘッド（1171／1235）的触手身体。** 攻击打到守方那一侧时，横贯画面的触手身体两端正好停在原版屏幕边（1280 宽里的第 107–1173 列），两侧露出背景；头部和攻方那一侧的触手（场景 2755／2987，光束表）正常伸到画面边。

内存探针（武器 95，每 0.25 秒读一次演员表和槽）：那段身体是**槽 170、场景 2756（ガンダムヘッド 是 2988）、模式 0xB**，摆法 1，坐标是屏幕坐标（x 恒为 160，y 从 254 滑到 160 再回去）。场景类型表 `800C9C6C` 里它是 0x93，所以 `801C50D8` 把它建成屏幕坐标 TEXRECT（`80096CD8`，不经矩阵），`battle_spread` 只处理模式 0xE–0x10，管不到。

- 其余 14 段（バルカン砲、メガビームキャノン、デビルファング、拡散粒子弾 各形态）没有看到停在 4:3 边的东西：机炮弹雨、光束、拡散粒子弾 的放射背景都到画面边。这一项只是看缩略图，没有逐帧核对。

### 8.2 触手身体修复（2026-11-20）

两张场景的每一帧都是同一块 32×32 图块（上下两行，t=128／160）横向排成一条，每帧都盖满原版 320 列，游戏绘制时把每个零件裁到 0..320。`80096CD8` 的包装在原绘制之后，用调用前的寄存器副本再画几份：整幅裁剪，每份横向平移 ±64、±128……（两块图块的整数倍）。平移的份数按画面比原版多出的宽度决定，16:10 和 16:9 各一对（±64）。做法和标题火焰一样，图块周期对齐，所以接缝处看不出来。代码：`battle_spread.hpp` 的 `screen_strip_extra` / `kStripPeriod`，`game_hooks.cpp` 的 `resident_func_80096CD8`。4:3 设置下、`SRW64_BATTLE_SPREAD=0` 时都不画副本。

## 9. 行为例程换上的场景逐件核查（2026-11-21）

**问题**：`battle_spread_scenes.py` 只给战斗场景登记表里的场景分类。可行为例程会用 `801C5700` 把演员换成「本场景 + n」，这些场景不在登记表里，从来没被分类过，只会被当成点平移。龙爪（§7）就是这种情况。从登记表最小到最大的场景号里，没登记、但按同一几何规则会被判成光束或背景的场景有 162 个，另有 622、4422 没有任何战斗脚本用到。

**做法**：
1. 静态归类：每个候选场景归到号码在它之前、最近的已登记场景（父场景）。64 个父场景，被 546 个脚本用到。
2. 实机审计（Mac，1280×800，HD，宇宙背景）：每个父场景挑一件武器在鉴赏里打一遍，每 0.1 秒读槽表，记下候选场景是否可见、所在位置，可见时截图。57 组直接用 `weapons.csv` 里的机体；另 5 组手配：反重力ストーム 637／628 用 グレンダイザー 160／159，断空光牙剣 874，击坠和反应各用一次。**114 个候选场景实际画了出来**，48 个在代表武器里没出现，其中 4400、4815、4582 是命中、击坠、反应脚本的。
3. 把这 114 个放进脚本的 `SWITCHED`，按同一规则分类：109 个光束、1 个背景 3988，龙爪的 4 个也在里面。重新生成后 `.inc` 比原来多 110 个号。
4. 修后用同一计划再审计一遍，172 对修前／修后截图逐对看。时机对不上或截到战前页的重拍过（161、436）。修前修后有争议的 18 对，又在 4:3 设置下拍了同一时刻作对照：4:3 下展开不生效，画的就是原版位置。

**结论**：
- 明显变好的：光束、弹雨、有线武器的线原先停在 4:3 边，现在伸到画面边（3571、3588、3625、3628、3651、3944、3965、3970、4022、4376、4482、4607、4644、4662 等）。反射浮游炮光束的折点对上了浮游炮（3582、3584）。有线爪和光束接上了（4070）。
- 起初判成「变差」的 18 对，对照 4:3 原位后**15 对是修后对**：飞来的光束或龙卷头部越过机体（4203、4163、3651、4406）、矛尾长度（4833、4836、4839）、有线爪位置（4065），原版本来就是这样。修前因为根部被外推，反而短了一截。3556 差别可以忽略。
- 小代价：有线兵器线端的部件（3912 的浮游炮、4067 的爪），原版正好在 4:3 边上露出一点；修后跟着线端落到画面边，几乎看不到了。
- 没发现机体或圆形特效被拉变形。

**没覆盖的**：48 个没出现的候选不在表里，以后有武器画到它们再补。只看了每个父场景的一件武器；只测了 16:10、Mac、HD。截图和对照在 `build/recomp/debug/scene-audit*`、`scene-audit-pairs/`（`sheet-*`、`tri-*` 是修前／修后／4:3 三联）。

### 9.1 补齐没覆盖的部分（2026-11-21）

**其余武器**：466 件能在鉴赏里直接打的武器全部跑了一遍（普通命中），另外对父场景下还有没出现候选的武器补跑了三种变体：击坠、回避（反应码 0x16）、被反击（武器由守方在反击时使用）。切り払い（0x12）变体对射击武器会让演出卡住不结束，跑了一部分就停了，没有新发现。审计脚本因此加了看门狗：一场超过 70 秒就按键结束。

- 又有 15 个候选画了出来，已并入 `SWITCHED`：3719、3720、4719、4720、4811、4835、4841 只在**回避**时出现，3909、3911、3978、4074、4076、4407、4590、4591 只在别的武器的普通命中里出现。
- 仍然没出现的 35 个，不在表里：622、3565–3567、3596、3598、3646、3648、3677、3748、3880、4016、4017、4055、4121、4122、4125、4204、4205、4211、4400、4422、4543–4548、4582、4636、4645、4663、4804、4815、4837。其中 622、4422 没有任何战斗脚本用到；4204/4205/4211 属于只有合体形态能用的反重力ストーム；4400、4815、4582 属于命中、击坠、反应脚本，鉴赏的几种变体都没触发。
- 每个父场景与行为例程的组合（共 75 种）都至少有一件武器跑过，并与 4:3 原位对照。

**ヴェスバー型有线浮游炮（武器 411）**：3631、3640、3641 是从原版屏幕边拉进来的折线（又宽又高，几何规则判不成光束），只被平移，宽屏下线头停在画面边内侧。手工加进 `EXTRA_BEAMS` 后，线和原版一样从画面边拉进来。另一处是 3637 斜线的外端：原版里它本来就停在屏幕边内约 3% 的地方，宽屏下按比例保留，不算问题。

**光束按当前帧拉伸**：原来按整段动画最长的那一帧算拉伸量，较短的帧够不到画面边（16:9 下明显，例如 3651、4376），飞进来的头部也会偏位（3969、4607 等）。现在拉伸方向仍由全部帧决定（两边都伸出的闪电如果每帧换方向，另一侧就不拉了，第一次只按当前帧时 4590 出现过这个问题），长度取当前显示的那一帧：子记录 +0x19 是当前步号（龙爪 2909 的 12 步实测 0→11）。用开发开关对比过「当前步号」和「下一步」，当前步号与原版位置一致，下一步会让 4163、161、4607 偏离，所以没有偏移。

**判断位置的方法**：4:3 设置下展开不生效，画的就是原版位置；4:3 和宽屏截图纵向比例相同，所以宽屏里该在的位置 = 原版位置按展开映射（中间 ±0.3 不动，外侧按画面宽线性拉开）。第一轮里被判「变差」的头部越过机体等情况，按这个标准大多是修后对。

**Windows**（家里台式机，`D:\srw64-spread2`，用 Mac 工作区的最新代码编译）：
- 16:10 与 Mac 逐张对照，摆放完全一致；Windows 窗口是 1280×800 实像素，Mac 是 Retina 2560×1600，所以 Windows 上多边形光束的边缘锯齿更明显，不是摆放问题。
- 16:9 与 16:10 对照：16:10 到边的在 16:9 也到边，没有黑边、接缝或压扁。
- 原版图像模式也跑了一轮。
- 编译时发现 main 上 `src/host/hd_pack.cpp`（`31c4fe31`，Switch HD 包）引用 `<unistd.h>`，Windows 编译不过；已在工作区改成 Windows 下用 `<io.h>`、二进制打开、64 位定位（未提交）。

**安卓**：没有设备连着，没测。
