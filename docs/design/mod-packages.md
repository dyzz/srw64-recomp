# MOD 包：格式、依赖、分类与挑战奖励

2026-10-03。本文汇总与用户讨论定下的 MOD 方向，是设计，尚未实现（除注明「已有」的部分）。它接替[内置 MOD 路线图](mod-roadmap.md)开头「当前不接入外部 MOD、不做包加载器与依赖」的范围限定：现在要支持玩家安装第三方 MOD 包，但仍只放数据、不放代码。已有基础见[自定义战役](custom-campaign.md)（追加剧本、MOD 管理、独立存档）与[改造上限](../gameplay/upgrade-limits.md) §7（改造规则文件）。

## 1. 已定的原则

- **原版不进 MOD 列表**。原版剧情和数据就是游戏本身；MOD 只是改动，没有任何包覆盖时一切走 ROM。
- **我们的内置内容按包的格式交付**，排在用户包下面：HD 包 `srw64.hd`、我们的译文。它们在 MOD 管理里标「内置」，不能删除；HD 包跟图像模式开关，译文跟语言设置。
- **包里只有数据，不带代码**。规则类改动只能打开宿主自带的规则并填参数（§6）。代码 MOD（上游 `.nrm`）以后真有需要再单独做一档。
- **不做自动下载，但做只读的在线索引**（2026-10-22 改，原来是「不做在线仓库与自动下载」）。官网发布一份索引，游戏只拿它比版本、提示新版，下载由玩家自己点；文件正本在作者的 GitHub Release，国内只有我们手动放网盘的镜像。缺依赖时说明缺什么，由玩家自己装。分发与投稿见 §13。

## 2. 包格式 v1

一个包是一个文件夹，或把它压成的 zip（扩展名 `.srw64mod`）。制作时用文件夹，发布时用 zip，拖进 MOD 管理即安装到用户目录 `mods/`。

```text
mod.json
campaign/   追加剧本（现在 campaigns/<id>/ 的内容）
challenge/  单关挑战（§8）
story/      改主线关卡（§7）
data/       数值（§5）
rules.json  打开宿主规则（§6）
art/        美术（§4）
dialogue/   台词与语言
audio/      音乐与语音
```

只需要用到的目录。`mod.json`：

```json
{
  "schema": "srw64.mod.v1",
  "id": "example.gaiden",
  "version": "1.2.0",
  "name": { "ja": "外伝", "zh-Hans": "外传", "en": "Gaiden" },
  "description": { "zh-Hans": "…" },
  "authors": ["example"],
  "game": ">=0.4",
  "requires": { "example.newpilots": ">=1.0" },
  "optional": { "srw64.hd": ">=1.0" },
  "conflicts": { "someone.oldgaiden": "*" }
}
```

- `id` 发布后不再改，用「作者.名字」避免撞名；版本 `主.次.修`。
- `game` 是对宿主版本的要求。
- `license`（2026-10-22 加）是作者给包内内容的许可证，限允许再分发的几种：`CC-BY-4.0`、`CC-BY-SA-4.0`、`CC-BY-NC-4.0`、`CC-BY-NC-SA-4.0`、`CC0-1.0`、`MIT`、`GPL-3.0-or-later`。宿主里可选（写了就得是其中之一），投稿到索引时必填（`tools/mods/validate.py`）。
- v1 定下后只加字段、不改已有字段的含义，未知字段报错（与改造规则文件同样严格）。

## 3. 依赖与载入顺序

- 三种关系：**必需**（缺了不能启用，写明缺哪个、要几版）、**可选**（有就排在它后面，没有也能用）、**冲突**（不能同时启用）。
- 每个 `id` 只装一份，所以只检查版本是否满足，不做版本求解。
- **顺序自动算**：被依赖的包在下面，内置包最底；玩家只能调整互不相关的包之间的先后。依赖成环报错。
- 停用一个包时，提示依赖它的包会一起停用。
- MOD 管理加「已安装」总表：每个包的类别、依赖、冲突、覆盖了多少项、顺序。四个分类页（追加剧本／美术／台词与语言／音乐与语音）列出含该类内容的包。
- **启动前校验**：Python 工具与宿主共用一套规则，坏包不启用，报错写明文件、字段与原因。

## 4. 外观类：按键叠加

顺序是 原版 → 内置包 → 用户包（按 §3 的顺序）→ 玩家自己在用户目录的修改；同一个键后面的赢，没提供的键往下层找。

| 内容 | 键 |
| --- | --- |
| 头像 | 图像资源号-调色板号 |
| 机体立绘 | 场景-图集-调色板 |
| 战术地图 | 地图编号（整张） |
| 场间背景、剧情图片 | 资源号 |
| 图标、世界地图、边框等 RT64 贴图 | 贴图哈希；运行库按顺序载入多个替换目录，后面的覆盖前面的 |
| 台词 | 记录号（`@17410`），即现有用户目录覆盖的做法扩成多层 |
| 音乐 | 曲目号 |
| 剧情语音、战斗语音 | 台词记录号；战斗台词号（音频的设计见[音乐替换与战斗语音](audio-mods.md)） |

新增的资源（不是改原版的）带包名，如 `example.newpilots:portraits/ryu.png`，不会互相覆盖；别的包用这个名字引用它，这就是依赖的主要用途。

现在各类加载代码只认一个 `hd/`，要改成先按顺序把所有包合并成一张「键 → 文件」表，再交给绘制代码。配套导出工具：按分类导出原版图和 HD 图，文件名就是键。

## 5. 数值类

可改的表都已解析（[原版数据目录](../data/original-data-catalog.md)）：机体 363、武器 1329、人物 361（能力记录 257 条、技能阈值、精神习得）、改造增量与价格、机体改造上限、武器改造类型。

```json
// data/units.json：按机体号逐字段覆盖，没写的保持原版
{ "36":  { "hp": 4500, "armor": 1300, "upgrade_cap": 12 } }
// data/weapons.json
{ "160": { "power": 2600, "upgrade_type": 2 } }
// data/pilots.json：按人物号
{ "28":  { "skills": { "NT": [1,4,8,12,18,24,30,38,45] }, "spirits": ["熱血", "必中", "ひらめき"] } }
// data/rules.json：批量规则，逐条覆盖优先
[{ "select": { "faction": "enemy" }, "set": { "hp": "×1.3", "armor": "+200" } }]
```

- **生效方式**：宿主在游戏开始前改它手里那份 ROM 数据的对应字节。原版逻辑、我们的状态页与改造页、图鉴、战斗查看器读到的是同一份数，不会出现「界面一个数、结算另一个数」。改造规则文件（`srw64.upgrade-rules.v1`，已有）原样并入 `data/`。
- **生效时机按字段标注**，MOD 管理里显示：
  - 每次现读：机体基础值（能力重算 `800A5254` 每次从 ROM 记录回读），旧存档立即生效；
  - 新建时复制一次：武器改造类型（`800A6A98` 只在建武器实例时复制），名册里已有的不变；
  - 读档时重建：机师基础能力（`800A8E0C → 800A7F8C` 从 ROM 记录整套重算，2026-10-26 静态确认）。
- **共用记录**：多个人物共用一条能力记录，改一个会连带别人。编辑工具要提示共用者；单独改一人需要把他的映射改到另一条记录，空记录有多少待查。
- **编辑工具**：在原版数据浏览页／图鉴上加「改这一项」，导出成 `data/*.json`，普通玩家不用手写编号。

验收：改一个机体、一个武器、一个机师字段，核对原版状态页、我们的页面、实际战斗结算、存读档后都一致。

**已实现：地形适应**（2026-10-26，`src/host/mod_data.hpp`）。目前只认 `data/units.json`（按机体号）与 `data/pilots.json`（按人物号）里的 `terrain`，四个通道 `air`／`land`／`sea`／`space`，值 `A`／`B`／`C`／`D`／`-`，没写的通道保持原版：

```json
// data/units.json
{ "184": { "terrain": { "sea": "A" } } }
// data/pilots.json
{ "133": { "terrain": { "space": "A" } } }
```

- 写进 ROM 记录：机体 `0x71B80 + 号×0x24` 的 `+0x0E..+0x11`，人物经映射 `D_800CA9C4`（ROM `0x553B4`，s16，-1 无记录）找到能力记录 `0x7A1A0 + 记录×0x10` 的 `+0x07..+0x0A`。这些字节并进改造规则文件那张拷贝补丁表（`upgrades::patches()`），游戏每次从 ROM 读记录（`8007F704`）后打上；改造规则自己的字节在下面，两者不重叠。
- **生效时机**：机体在下一次能力重算（`800A5254` 每次把记录 `+0x0E..+0x11` 抄到运行时 `+0x16..+0x19`）；人物在整套重建 `800A7F8C`（运行时 `+0x2E..+0x31`），读档时 `800A8E0C` 会对每个人跑一遍，升级也跑。读场间存档时机体实例也从 ROM 重建（`docs/gameplay/cheats.md`「读档重建实例时从 ROM 取回」），所以旧存档读档即生效；关内中途启停 MOD、读中断存档，要到下次重算（改造、换乘、部件、关内若干处）或升级，中断存档未实测。
- 包改变（安装、启停、删除）或前端告知游戏版本后，下一次 ROM 读取前重新收集（游戏线程）。坏文件整份不用，`SRW64_MOD_DATA_PROBLEM` 写明包、文件和原因；`data/` 里别的 `.json` 报「暂不支持」。带 `--output` 时写 `mod-data.json`。
- 图鉴读同一组字节（`library.cpp` 按 MOD 版本号重建缓存）；战斗查看器走原版建记录的函数，本来就一致。
- 人物的能力记录可能共用，改一个人会连带同记录的人（`mod_data::sharing` 能列出来，编辑工具以后据此提示）。
- 示例包：`config/recomp/mods/space-a`（`srw64.space-a`），把我方主力里宇宙不到 A 的 20 名驾驶员与 21 台机体的宇宙改 A（魔神系、孔巴特拉V、盖塔3 组、豪将军、大铁人、丹拜因系、钢加农、钢坦克等），空陆海不动。我方按关卡部署记录的阵营挑，弁庆、武藏、银铃按剧情归我方；20 人的能力记录都独用。艾莉卡（宇 C）身份未核对，没放进去。实战按机体与驾驶员等级之和分档（`800A6194`，≥8 才是 A），所以像ゴーショーグン（184，宇 A）配真吾（133，宇 B）这种机体已是 A 的，原版在宇宙也只按 B 算，要改驾驶员才行。
- 测试：`make recomp-mod-data-test`（`tests/native_mod_data.cpp`，用真 ROM 核对两条记录、文件规则、包的上下覆盖与补丁合并）。

## 6. 规则类

经验倍率、资金倍率、敌人等级加成这类要改逻辑的，由宿主实现成规则（沿用现有[可选规则](../gameplay/rule-fixes.md)），包里的 `rules.json` 只负责打开并给参数。包不能带新逻辑。

## 7. 剧情类：改主线

按**事件**改，不按整关。2026-11-02 用户定：**MOD 事件不占原版的事件位，触发判断和状态都在宿主**；原版脚本引擎只负责执行 MOD 事件的指令。

### 7.1 分工

| 部分 | 谁管 | 说明 |
| --- | --- | --- |
| 原版事件 | 原版 | 照常从 ROM 进 `8019B400`（0x1A00 字节）、经 0x100 字节指针表由 `8009DE7C` 登记，一字不动。63 个事件、0x1A00 字节、每组 16 槽这些限制只管原版 |
| MOD 事件何时触发 | 宿主 | 宿主按 MOD 包写的条件判断，不进原版登记表 |
| MOD 事件已触发、MOD 自己的标记 | 宿主 | 宿主状态，随存档走（§7.4）；不借原版变量 |
| 执行 MOD 事件的指令 | 原版脚本引擎 | 对白、部署、镜头、编成等仍是原版指令，由原版虚拟机执行 |

脚本字节必须放在原版能寻址的地址上（执行指针 `owner+0x1C` 指向游戏地址），定为 `807E0000`–`807EFFFF`（64 KiB，紧挨 `807F0000` 注入暂存区之下、不共用）。这块是宿主分配的 8 MiB 数组里游戏从不碰的一段，不进存档；宿主在启动某个 MOD 事件前把它的字节写进去。

**内存区无人使用**（2026-11-02 静态）：游戏只用到 4 MiB，加上模式 2 装的战斗动画编辑器 `80400000–804152F0`（[战斗动画数据](../data/battle-animation.md)）。在全部重编译代码里搜 `lui 0x8042`–`0x807F` 只有一处：`8007FD80` 往 `80600000` 拷 ROM `0x22F800`，长度 `0x22F800−0x22F800＝0`，什么也不写。宿主自己只用 `807F0000`（注入）与 `807FFF00`（战斗 HUD）。Vita 的 16 MiB 分配也盖得住。

### 7.2 原版的触发与执行（2026-11-02 静态）

- **登记表**（`8009DE7C`）：分类组 g 在 `engine(8015F950)+0x14+g×0xC4`；组内 +0 计数（s16）、+4+槽×4 事件指针、+0x64／+0x44／+0x84／+0xA4 + 槽×2 依次存事件头第 1–4 参数；类型 12–14 的指针在 `engine+0x8/+0xC/+0x10`；`+0x98E` 是登记总数。执行过的槽把 +0x64 那格写成 `0x2000`（类型 2 `8009E6A4`、类型 9 `8009EC3C`）。
- **扫描**：`8009E180` 按轮询阶段 `+0x9AA` 多次调 `8009E3B0(engine, 起始类型, 结束类型)`；后者对范围内每个类型经 `8009E308`（跳转表 `800D0610`）取触发函数、由 `8009E480` 逐槽调用，一旦 `+0x97C ≥ 0x2000`（有事件启动）就停止。各触发函数命中时的做法相同：写 `+0x97C`（类型 2 写 `0x2002`），调 `8009EE98(engine+0x948, 事件指针)` 设好执行指针，下一帧起由 `8009EFDC` 执行。
- **读档与回到地图都会重新登记，槽状态不存**：中断记录由 `80093278(1)` 序列化，`80091ED0(1)` 只存引擎的 `+0x994..+0x99B`（选择寄存器、胜败显示等 4 个半字），以及变量 `8015E818`、`8016A1F0` 12 个半字、人物状态表 `8015DE90` 500 字节；分类组、延迟计数 `+0x97E` 都不存。`800801A4` 的三条恢复路径（`800803BC` 读 SRAM、`80080454`／`8008057C` 从缓冲回到地图）都是 `800936A0` 恢复之后调 `8009DD58(场景, 1 或 2)`，从 ROM 重读事件、`8009DE7C` 全部重新登记（模式非 0，不重置变量）。所以原版靠变量防止事件重放（说服头里的门槛变量、类型 7 的 `3E03 133,3,0 … 3E13 133,0`），不靠 `0x2000`。
- **`3D46` 离场不触发类型 2**：类型 2 的触发函数 `8009E604` 调 `800A293C(角色)` 取 HP 百分比，截成整数为 0 才触发。角色不在地图上时查人物状态表 `8015DE90[角色]`：0 → 0（触发），1 → 1.0，其他 → 103.0。`3D46`（`8009FDC4` → `8020D300` → `8020CFF8`）经 `800A5178` 写 **2**，所以不触发；`3D4F` 那一路（`8020E358`）与战斗击破（`801FB18C` 等）写 0。

### 7.3 宿主怎么触发

- **接入点：包装 `8009E3B0`**。原函数返回后，若 `+0x97C` 仍 `< 0x2000`（这一轮原版没有事件启动），宿主对同一类型范围判断 MOD 事件；命中一个就照原版触发函数的做法写 `+0x97C`、把字节写进 `807E0000`、调 `8009EE98(engine+0x948, 807E0000)`。这样 MOD 事件和原版在同一个轮询阶段、同一个时机启动，原版优先，每轮最多启动一个，之后执行完全走原版。
- **条件**：MOD 包按原版的类型写（回合开始、击破／退场、HP%、交战前后、敌方全灭、残存数、区域到达、说服），宿主读原版触发函数读的同一批状态，能直接调原版小函数的就直接调（如击破用 `800A293C`），保证判断一致。宿主侧还能加原版没有的条件：已触发的其他 MOD 事件、MOD 标记、任意变量、路线、名册里有没有某人。
- **原版触发函数读的状态全在游戏内存里，宿主都读得到**（2026-11-02 静态，逐个看了九个触发函数）：

  | 类型 | 触发函数 | 读什么 |
  | --- | --- | --- |
  | 0 回合开始 | `8009E598` | 回合 `engine+0x9AC`、阶段 `+0x9AE` |
  | 2 击破／退场 | `8009E604` | `800A293C(角色)`（地图单位 HP，不在地图时查 `8015DE90`）、变量 `800A496C` |
  | 3 HP% | `8009E6E4` | `800A2BF4(角色)` 找地图单位 → 单位 `+0xC` 记录 `+4` HP；`8015DF1A`；`800A293C` |
  | 4／5 交战后／前 | `8009EA88`／`8009E9B4` | 交战双方记录指针 `engine+0x9A0`／`+0x9A4`，各自 `+2` 是角色号 |
  | 6 敌方全灭 | `8009E834` | 敌方数 `+0x9B1`、回合、阶段 |
  | 7 残存数 | `8009E8B4` | 敌方 `+0x9B1`／第三方 `+0x9B2`、阶段、变量 |
  | 8 区域到达 | `8009ECBC` | `800A3504`、`800A4288`（区域匹配）、`+0x998` |
  | 9 说服 | `8009EC3C` | `+0x992`（菜单选中的槽）、轮询阶段 `+0x9AA` |

  前八类宿主在包装 `8009E3B0` 时读同样的字段、调同样的小函数即可。只有说服不同：条件判断在建地图指令菜单时（`800A4634`）做，所以要另包装它。
- **默认只触发一次**：宿主记下本关已触发的 MOD 事件，不再判断；要能重复的事件写 `repeat: true`。MOD 作者不用写变量防重放。
- **说服**（2026-11-02 静态核实）：
  - 原版流程：地图指令菜单建「説得」时（`801C9EC8`）和执行「説得」时（`801DEDA8`）都先把当前单位主驾驶员的角色号写进 `engine+0x9A8`，再调 `800A4634(engine)`。它逐个看类型 9 的槽（分类组在 `engine+0x6F8`）：槽未执行（`+0x64 < 0x2000`）、说服者（第 1 参数）＝`+0x9A8`、门槛变量（第 3 参数，`800A2A84` 读）＝门槛值（第 4 参数）或第 3 参数为 `FFF8`、`800A2BF4` 找得到对象的地图单位、两单位地图坐标（单位 `+4`／`+5`）曼哈顿距离为 1；第一个满足的把槽号写进 `+0x992`，返回**对象单位主驾驶员的角色号**（单位 `+0xC → +0x38 → +2`）；都不满足写 `-1`、返回 `-1`。「说服者还能行动」由菜单那边判断，不在这里。
  - 菜单只看返回值是不是 `-1`；执行时用返回的角色号在 3 阵营×30 的地图单位表（`8015E100`，0x14 一条）里找到对象、算说服动画的朝向。选中「説得」由 `801DEBF4` 把轮询阶段 `+0x9AA` 设成 6（地图状态 `80172EB0＝0x53`）。
  - 阶段 6 的轮询里 `8009E3B0 → 8009E308 → 8009E480` 逐槽调类型 9 的 `8009EC3C`：`+0x992＝-1` 或阶段不是 6 就返回；否则把 `+0x992` 当槽号，槽已执行则返回，未执行就把它标 `0x2000`、写 `+0x97C＝0x2000`、`8009EE98` 启动，再把 `+0x992` 写回 `-1`。`8009EC3C` 没有别的调用者，`8009E480` 只在组内有槽时才调它。
  - `+0x992` 另外只有两处用：`8009DE7C` 每次登记置 `-1`；区域到达的 `800A4288` 在它不为 `-1` 时整个跳过（说服待执行时不判区域）。它不进中断记录。
  - **宿主做法**：包装 `800A4634`，先调原版，原版返回 `-1` 时再查本关的 MOD 说服定义（未触发或 `repeat`、说服者＝`+0x9A8`、宿主条件成立、按原版同样调 `800A2BF4` 判相邻），命中就把 `+0x992` 写成宿主标记值（`0x7000`＋定义序号，只要不是 `-1` 且宿主认得），返回对象单位主驾驶员的角色号，和原版一样。原版优先、菜单与动画不用改。
  - **标记值不能落到原版手里当槽号**：在阶段 6，`8009EC3C` 会拿它去索引槽数组并写 `0x2000`，越界。所以宿主包装 `8009E3B0` 时**先于原函数**检查：阶段 6 且 `+0x992` 是宿主标记 → 写 `+0x97C＝0x2000`、把字节写进 `807E0000`、`8009EE98` 启动、`+0x992` 写回 `-1`、记为已触发；原函数入口见 `+0x97C ≥ 0x2000` 立即返回。阶段 0／1／2 里 `8009EC3C` 先查阶段就返回，碰不到标记。玩家看到「説得」却没选、换了别的单位，下一次建菜单会重算 `+0x992`，和原版留着槽号的行为一致。
- **开场／过关／结束（类型 12–14）**：原版各只有一个，MOD 写的是**接在原版之后执行**的事件：原版那个跑完（`+0x97C` 回到空闲）后宿主用同样的启动方式接着跑，几个包按载入顺序依次跑。结束事件里原版的 `3D4B` 只写下一场景号，接着跑不受影响；在阶段 C3 启动是否安全待实机。
- **替换／删除原版事件**：要动原版事件才用；宿主在 `8009DE7C` 之后把原版那个槽标成 `0x2000`（等于删除），替换时再由宿主在原时机触发 MOD 版。`8019B400` 里的原字节不动。两个包动了同一个事件时按顺序后者生效，并提示冲突。
- **要影响原版事件时仍写原版变量**：原版事件只读原版变量，比如要让原版结束事件跳过一段对白，就得改它判断的那个变量。这是给原版读的，宿主替代不了。
- **出击部署**：按记录号改（换机体、改等级）。
- 没改的事件用 `copy_from: base:stage_events:*` 引用原版，包里不带从 ROM 取出的剧本。

### 7.4 宿主状态与存档

宿主状态分两种，寿命不同：

- **已触发的 MOD 事件**：只管本关。新关开始（`8009DE7C` 模式 0）清空，随中断记录走。
- **MOD 标记**（`set_flags` 写、`if.flags`／`not_flags` 读，键为「包 id/标记名」）：跨关，相当于 MOD 自己的剧情变量。只有新游戏清空（`800A4790` 把全部剧情变量写 3，`801C69E4` 选主角时调），随中断记录和场间存档两种记录走。

两种记录的做法相同：原版序列化时宿主按记录内容的哈希拍快照，恢复时按哈希找回；写进 SRAM 的那次另存旁注 `<存档库或运行目录>/story-state/<哈希>.json`，换进程读档时从旁注读。

- **中断记录**：`80093278(0／1)` 序列化进 `800FBEF0`（0x3AE0 字节），`800936A0(0)`（从缓冲回到地图，`80080454`／`8008057C`，含 GAME OVER 重试）与 `800936A0(1)`（标题コンティニュー读 SRAM，`800803BC`）恢复。写缓冲只有 `8009EE50`（`8009EDB8` 切画面前）一处调用，写 SRAM 只有 `801D223C`（地图菜单「中断」）。宿主的回合自动存档自己调 `80093278`，同样拍快照。
- **场间存档**（存档 1／2）：`800924D8` 序列化进 `801C2600`（0x1F00 字节），`800927A4` 恢复；哈希从 `+2` 起（前两字节不算）。这种记录只带标记，读回时已触发集合清空（下一关本来就是新关）。`800927A4` 另一个调用者 `80093FA0` 是手柄记忆卡那条路，同样经过包装。
- 没有旁注的记录（比如在 ares 里存的、或删了 `story-state/`）按「没有标记、没触发过」处理，日志 `restored … found: none`。

### 7.5 例子

「让某敌人可以加入」= 在某关加一个 MOD 事件，条件满足时 `3D5A 机师,0,机体,500` 登记；同时在 `data/` 里补这个人的精神、技能，补机体的改造上限与武器改造类型。待实机：名册上限（机体实例 140 台）、敌方机体换我方阵营后的地图图标（含 HD 图标）、のりかえ 列表。

第一个实例拟用「师匠存活加入」（独立军线大屿山（下），场景 129）：

- **说服**：说服者 4（ドモン）、对象 18（東方不敗），条件「变量 131 为 0」（战斗中对话过才写 0，原版交战后事件 `001d387c`）。
- **说服事件的指令**：新对白；`3D46 18,1` 让他离场（不触发原版击破事件，见 §7.2）；再自己做原版击破事件 `001d38c8` 的后半：按 `3E03 128,2,1` 调 `3D45 12` 或 `3D45 11`、写 `128＝3`、写 `101＝0`（打开王的击破事件，过关靠它）；最后写 `131＝3`，原版结束事件只在 131 为 1 或 2 时播死别，3 两段都跳过。
- **接在结束事件后的 MOD 事件**：条件「说服事件已触发」（宿主判断），补对白与 `3D5A 18,0,27,500`。
- `data/pilots.json` 给人物 18 补 SP（原版为 0）。

用户定：尽量放宿主，相当于抽象一层剧情脚本，方便别人写。作者写法见[剧情 MOD 指南](../guide/story-mods/README.md)。

## 8. 单关挑战与奖励

挑战就是一个迷你关卡加一支预设部队，打完显示回合数等结果。奖励可以带回主线。

### 8.1 两种进入方式

- **独立挑战加奖励箱（先做）**：从标题或 MOD 管理进入，用预设部队，与主线无关。过关后奖励进奖励箱；玩主线到场间时，场间菜单提示「有挑战奖励可领取」，领取后写进当前游戏。追加剧本的通关奖励也走同一个奖励箱。
- **从场间进入（后做）**：像机战 V/X/T 的 DLC 关，用当前部队打，打完回场间，资金、经验、部件自然留下。进挑战前宿主记下主线进度（话数 `8010F5EF`、场景 `F5F0`–`F5F2`、总回合 `F5EC`、关卡开始会重置的变量 100–114 与 128–139），打完恢复。过关流程（`3D4A`）会改哪些东西要先实机核清，一项都不能漏。

### 8.2 可给的奖励（用户 2026-10-03 定：只给这三类）

| 奖励 | 写到哪里 | 注意 |
| --- | --- | --- |
| 资金 | `D_8010F5F4`（u32） | 场间画面已能直接改资金 |
| 强化部件 | 库存 `D_8015E990`，每件部件一个 u16，高字节持有数、低字节装备中 | 持有数是一个字节，加之前查上限 |
| 改造段数、机师等级／经验 | 机体实例 `D_8016A210`（140 × 0x54）`+0x4C..+0x50` 五项段数，武器实例 `+0x16`；机师记录 `80172F40`（0x4C 一条）`+0x05` 等级、`+0x12` 经验 | 改段数后调能力重算 `800A5254`，不超过机体上限 `+0x51`。改等级不会自动长能力，要走原版的成长处理（成长循环 `800A6238`），具体调用方式待核实；先做经验或段数 |

不给机体／机师入队，不给剧情变量与隐藏要素（会打乱主线路线判断）。

### 8.3 规则

- 奖励写在挑战包的 `mod.json` 里，开打前就显示。
- **只改内存，不改存档文件**：宿主在场间写内存，玩家照常存档才保住；存档格式与校验仍由原版负责。
- **每个挑战在每份主线存档上只领一次**，领取记录放存档旁的附加信息。`saves/` 库已有附加信息文件，卡带栏还没有，要补。设置里另有「允许重复领取」，默认关。
- 领过奖励的存档在附加信息里记下来源，和玩法类 MOD 记录放在一起（§9）。

## 9. 存档

- 主线存档的附加信息记下当时启用的数值类、规则类、改主线的包及其版本，以及领过的挑战奖励。读档时对不上就列出差异提醒，但仍允许读取（中途装平衡补丁很常见）。
- 外观类不记。
- 追加剧本、独立挑战用各自的存档库（已有的分离做法）。

## 12. 参考的做法

| 生态 | 包与依赖 | 借鉴 |
| --- | --- | --- |
| N64Recomp（Zelda64Recomp 等） | `.nrm` zip 内 `mod.json`，`id:版本` 列表分必需与可选 | 同一运行库，字段命名接近 |
| Factorio | `info.json`，一行一条：`base >= 1.1`、`? 可选`、`! 冲突` | 依赖三种关系的划分 |
| RimWorld | `About.xml`：`modDependencies` 与 `loadAfter`／`loadBefore` 分开 | 「依赖」与「只影响顺序」分开 |
| 星露谷 SMAPI | `manifest.json`：`UniqueID`、`MinimumVersion`、`IsRequired` | 缺依赖时明确说缺哪个、要几版 |
| Bethesda（上古卷轴、辐射） | 插件顺序由玩家手排，靠 LOOT 之类的第三方工具补救 | 反面例子：顺序要由依赖自动算 |
| RimWorld、Bethesda 读档 | 存档记录 MOD 列表，读档时比对提醒 | §9 的存档记录 |
| Zelda64Recomp 的分发 | 游戏里没有联网代码；Thunderstore 社区页手动下载，拖进游戏安装，同名覆盖要确认；内置 `.nrm` 可被用户目录同 id 覆盖 | §13.7 的安装细节；国内访问 Thunderstore 只有约 60 KB/s，不能当主渠道 |
| Hollow Knight modlinks | GitHub 仓库里一份 XML 就是整个仓库：名字、版本、下载链接、SHA256、依赖，作者提 PR | §13.3 的投稿仓库 |
| Factorio 门户 | 公开 JSON API，游戏内列表、更新检查、启停；不自动装依赖 | §13.7 的第二阶段 |
| Minecraft BMCLAPI／MCIM | 客户端只认一个可替换的基地址，先官方后镜像回退，缓存带时间戳；志愿者节点网络只在百 TB 量级才需要 | 索引带 `generated` 时间戳；镜像只做网盘，不做直链 |

## 13. 分发与投稿

2026-10-22 定。接替 §1 原来的「不做在线仓库与自动下载」：官网发布一份只读索引，游戏只拿它比版本、提示新版，下载由玩家自己点。**不为国内做直链**：国内靠我们手动放网盘的镜像，和安装包一样；流程只为海外社区方便。

依据是当天从官网源站（阿里云深圳）的实测：Thunderstore 的网站、API、文件 CDN 都能通，但一个 583 KB 的包只有约 60 KB/s；github.com 卡住超时、raw.githubusercontent.com 直接断；jsDelivr 能通但慢。国内没有合适的第三方 MOD 托管站（3DM、游侠面向热门大作且要它们的账号与下载器，Gitee 附件要登录）。真正免费又快的国内渠道只有网盘，自建直链每月几元到几十元但要多维护一套 OSS、下载域名与凭据，用户决定不做，以后投稿量大了再议。

### 13.1 放哪里

- **文件只有一份正本：GitHub Release**。作者自己仓库的 Release 资产，索引记下直链与 SHA-256（Hollow Knight modlinks 的做法）。不重新托管：作者删了就下架，`sha256` 保证链接指向的内容没变。
- **索引像 latest.json 一样处理**：仓库里每个包一个文件 `web/src/data/mods/<id>.json`，官网构建时生成 `/mods/index.json`（`web/src/pages/mods/index.json.ts`），`deploy.sh` 随站点发布并刷新 CDN。官网域名是全球加速，海外读索引不慢；索引只有几十 KB，国内读也没问题。
- **国内镜像是网盘**：我们挑着镜像，不承诺全部。镜像过的包在它的 `<id>.json` 里加 `netdisk`（`quark`、`baidu` 链接，和 `release.json` 同样的字段），由用户手动上传后填链接。HD 包继续走 GitHub 加网盘。
- **费用**：零。GitHub Release 带宽不计费、单个资产上限 2 GB；官网 CDN 只多一个 JSON。
- **不做的**：OSS、下载域名、RAM 用户、Thunderstore 社区（海外玩家从 GitHub 和官网 MOD 页就能拿到；真有需求再申请，成本只是多传一份）。

### 13.2 索引格式 v1

```json
{
  "schema": "srw64.mods-index.v1",
  "generated": "2026-10-22T09:00:00Z",
  "packages": [
    {
      "id": "example.gaiden",
      "version": "1.2.0",
      "name": { "ja": "外伝", "zh-Hans": "外传", "en": "Gaiden" },
      "description": { "zh-Hans": "…" },
      "authors": ["example"],
      "license": "CC-BY-NC-4.0",
      "game": ">=0.4",
      "requires": { "example.newpilots": ">=1.0" },
      "optional": {},
      "conflicts": {},
      "contents": ["campaign", "art"],
      "file": "example.gaiden-1.2.0.srw64mod",
      "bytes": 1234567,
      "sha256": "…",
      "url": "https://github.com/<作者>/<仓库>/releases/download/v1.2.0/example.gaiden-1.2.0.srw64mod",
      "netdisk": { "quark": "https://pan.quark.cn/s/…", "baidu": "https://pan.baidu.com/s/…?pwd=…" },
      "page": "https://srw64.dreamquest.club/zh/mods/example.gaiden/",
      "source": "https://github.com/<作者>/<仓库>",
      "published": "2026-10-22",
      "yanked": null
    }
  ]
}
```

- `name`、`description`、`authors`、`license`、`game`、`requires`、`optional`、`conflicts` 从包内 `mod.json` 抄出来（CI 校验时抄，写回 `<id>.json`），索引不另写一份；`contents` 是包里实际有的目录。
- `url` 是正本直链；`netdisk` 可缺省。
- 每个 `id` 只列最新版；历史版本在 git 历史与作者的 Release 里。
- `generated` 让客户端知道索引多旧；和 `mod.json` 一样，v1 定下后只加字段、不改已有字段的含义。
- `mod.json` 新增必填字段 `license`（§13.4）。

### 13.3 投稿：提 PR

作者在本仓库提 PR，新增或修改 `web/src/data/mods/<id>.json`，手写的部分只有：

```json
{ "url": "https://github.com/<作者>/<仓库>/releases/download/v1.2.0/example.gaiden-1.2.0.srw64mod",
  "sha256": "…", "source": "https://github.com/<作者>/<仓库>" }
```

1. 作者把 `.srw64mod` 发在自己仓库的 Release 里。
2. PR 加或改 `<id>.json`；第一次投稿同时在 `web/src/data/mods/owners.json` 登记作者前缀（`id` 里点号前的部分）对应自己的 GitHub 用户名。
3. CI 下载文件、跑 §13.4 的校验，把 `mod.json` 里的字段抄进 `<id>.json`，结果以评论贴回 PR，和宿主报错同一文案。
4. 维护者按 §13.5 人工审，合并。下次 `deploy.sh` 发布时索引更新，想镜像的再手动传网盘、补 `netdisk`。

没有 GitHub 的作者：把文件和来源发给维护者，维护者代为发 Release（放在主仓库或一个专门的 `srw64-mods-mirror` 仓库）并提交条目，`owners.json` 记 `maintainer-verified:<作者名>`。预计很少，不单独做工具。

**为什么不做网页上传**：要承担审核与版权责任、防滥用；而且源站连不上 GitHub。投稿量大了再考虑。

### 13.4 自动校验

CI 和宿主启动前校验（§3）共用 `tools/mods/validate.py`，错误文案三语共用。任何一条不过就不合并：

- 下载 `url` 成功，SHA-256 与条目一致；`url` 是 GitHub Release 资产直链（其他托管以后再放开）。
- zip 可解；根目录有 `mod.json`；`schema` 是 `srw64.mod.v1`；未知字段报错（§2）。
- 文件名 `<id>-<版本>.srw64mod`，`id` 与 `<id>.json` 一致，版本严格大于已发布的版本。
- `id` 的作者前缀在 `owners.json` 里属于 PR 作者的 GitHub 用户名，或维护者代登记的记录。
- `game` 可解析；`requires`、`optional` 里的 `id` 在索引里存在（或在同一 PR 里）；`conflicts` 不含自己。
- 只允许 §2 列出的目录；文件扩展名白名单（`json`、`txt`、`png`、`webp`、`ogg` 等按内容类型定）；不允许可执行文件、脚本、动态库。
- 大小上限 100 MB；更大的先联系维护者。
- **不含原版数据**：原版资产只能用 `copy_from: base:` 引用（§7）。仓库里放一份我们导出工具产出的原版图像与数据的 SHA-256 清单（`tools/mods/original-hashes.txt`，由导出脚本生成），包内任何文件命中即拒绝。这是机器能查的部分，人工审再看改得不像的。
- `mod.json` 的 `license` 必填，限允许再分发的许可证：`CC-BY-4.0`、`CC-BY-SA-4.0`、`CC-BY-NC-4.0`、`CC-BY-NC-SA-4.0`、`MIT`、`GPL-3.0-or-later`、`CC0-1.0`。PR 模板里作者勾选「我对包内全部内容有以此许可证再分发的权利」。

### 13.5 人工审核

- 看：描述与包内内容一致；美术、音乐没有明显来自第三方作品；没有违法内容。
- 名称与描述三语不强求，至少一种语言。
- 一周内回复。拒绝时写明原因。

### 13.6 更新、下架与所有权

- **已发布的 `id` 加版本永不改**。修就发新版本。
- **链接失效**：CI 每周重验一遍索引里的 `url` 与 `sha256`（Hollow Knight 也这么做），失效的条目自动标 `yanked: "link"`，有网盘镜像的保留镜像。
- **下架**：条目加 `"yanked": "<原因>"`。索引保留条目并带原因，已装的玩家在 MOD 管理里看到提示；侵权的连网盘镜像一起删。
- **所有权转移**：原所有者提 PR 改 `owners.json`；联系不上的由维护者裁定。
- **改 `id`** 当新包处理：旧条目下架，`superseded_by` 指向新 `id`，游戏提示「作者已改用 X」。

### 13.7 游戏内

- **第一阶段**：MOD 管理读 `https://srw64.dreamquest.club/mods/index.json`（复用更新检查的 HTTP 层：无标识、首次联网前先问、15 秒超时、响应 1 MB 上限；索引超过 1 MB 前先分页），和已装包的 `mod.json` 比版本，列出「有新版 X」与「可安装」；按钮用系统浏览器打开条目的 `page`（官网 MOD 页，按语言给 GitHub 与网盘链接）；缺依赖只列出缺哪个、要几版。
- **第二阶段（海外）**：游戏内直接从 `url` 下载，核对 `sha256` 后走现有安装流程进 `mods/`。国内玩家 GitHub 下不动，界面提示去网盘，不做回退。安卓暂不做（HTTP 层是存根）。
- 安装细节借 Zelda64Recomp 的三条：同名覆盖要确认；接受打包了多个 `.srw64mod` 的普通 zip；内置包可被用户目录同 `id` 的包覆盖。

### 13.8 顺序

1. `tools/mods/validate.py` 与 `original-hashes.txt` 的生成；`web/src/data/mods/`、`owners.json`、`index.json.ts`、PR 模板与校验工作流。先把我们自己的包（示例战役等）当第一条跑通。
2. 官网 MOD 页（列表与每包一页，三语，GitHub 与网盘链接）。
3. 游戏内检查更新（第一阶段）。
4. 投稿说明（英文为主，中文一份）放 `web/src/data/mods/README.md` 与官网 MOD 页。
5. 每周重验链接的工作流。
6. 游戏内下载（第二阶段），看投稿量再定。
