# 剩余指令的语义确认

2026-09-12。当前 1,812 个事件都可解析到结束符，普通指令 73 槽、条件指令 30 种的边界与分发表已覆盖。普通指令的语义标记为：28 项 `code-confirmed`、26 项 `structure-confirmed`、19 项 `unknown`。这三个状态记录证据强度，`code-confirmed` 也不等于完成游戏运行验收。

目标是为剩余命令确认参数含义、状态变化、异步完成条件和游戏效果，再决定哪些可安全用于关卡 Mod。现阶段不写回原 ROM，也不把剧情查看器当成脚本解释器。

两次静音运行已分别核对女性超级系开场的全部 123 条及男性超级系开场的全部 56 条普通／对白指令。前者见[首次运行观察](script-runtime-observation.md)；后者确认 `3D3C` 第一参数为驾驶员编号，五次原参数移动有代码与连续帧相互支持，见[3D3C 运行观察](script-3d3c-runtime.md)。相对位置及逻辑坐标等边界仍待专项实验。

## 每条指令的确认流程

1. **选样并固定证据。** 从目录找出命令的全部出现位置，登记 ROM SHA、场景、事件地址、指令偏移、原参数、前后命令与分支条件。优先选容易重现且参数值有对比的两个实例；原脚本从未使用的命令单独标记。
2. **追到底层读写。** 从常驻 handler 进入正确 overlay，追踪状态机、参数消费、表项、名册或引擎字段的读写，以及后续消费这些字段的函数。处理函数可能每帧调用多次，必须区分首次进入、等待和完成，核对脚本 PC 推进时机。未读取的占位参数仍保留，不能擅自删掉。
3. **静音运行跟踪。** 在原生 recomp 中增加可关闭的定向 trace，记录命令开始／完成、帧号、场景、事件 PC、主角标记、条件 ACC、相关变量和单位状态的前后值。只过滤目标事件或命令，避免每帧输出淹没证据。用画面或录像对齐效果，确认一条指令的完成确实对应观测变化。
4. **单参数对照实验。** 在独立测试配置、存档副本和临时内存覆盖中，比较原值与一个改变值；先验证 baseline 能重现，再改变一个因素。至少两个原始上下文吻合后才泛化结论；检查演出后的单位、阵营、坐标、回合与存档状态。结束恢复原设置，测试运行保持静音。
5. **回填与复验。** 更新布局锁中的参数名、语义和证据窗口，补充真实实例测试、原始字节重组与边界检查，重新提取目录。在证据记录中分别保存静态结论、运行观测、反例及仍未解释的位，只有证据支持时才升级语义状态。

建议每项形成独立记录：`opcode / handler / overlay / source occurrences / parameter hypotheses / code evidence / runtime trace / changed parameter / observed effect / confidence / unresolved`。运行记录需包含 ROM、构建版本、测试入口与静音设置；不能只写“看起来是爆炸”。

## 对关卡编辑更关键的剩余项

- `3E06/3E0D`：名册字段 `+5`、`+0x14` 的实际意义。
- `3E16/3E17/3E19/3E1A`：交战角色与引擎字段的来源及条件含义（`3E18` 已确认读取当前场景索引），先查写入方，再对照事件触发。
- 类型 13：进入初期配置状态 `engine+4 = 0xC2` 的确切路径；类型 9：索引 `engine+0x992` 的写入点。
- 28 字节出击记录：`+8`、`+E`–`+13`、`+1A` 等未解释字段，以及没有对齐 999 结束符的 13 个块。不得为方便编辑补出猜测字段或终止符。
- 文本头剩余数字、共通段相对说话人、`3D4B 500` 恢复场景的运行时来源。

这些项目决定路线回放和 Mod 的可靠性，应与演出命令同级排期。静态解析已能支撑全文阅读；自动折叠真实路线需要上述条件语义和运行状态，脚本写回还需要独立的字节往返与游戏验收。

入口代码与机器码关系见[关卡脚本完整解析](stage-script-exploration.md)；阅读端能力见[剧情审阅站](story-reader.md)。

### 可以直接用生成的 C 分析

生成目录 `build/recomp/cpu-bound/generated/` 保留完整处理函数及 MIPS 地址注释，可直接追踪读写与调用关系。这里是寄存器级的 recomp C，常见 `ctx->rN`、`MEM_W/MEM_H/MEM_BU`、`LOOKUP_FUNC`，没有原开发者的变量名和结构体类型；应对照原 ROM 及生成锁，不修改这些生成文件。同一 VRAM 在不同 overlay 中可能对应不同函数，必须使用 `resident` / `load_000AB160` / `load_000A7EC0` 等前缀区分。

本轮抽查已看到可继续深入的明确线索，但没有据此批量升级语义状态：

- **3D69**：`load_000AB160_func_802128E4` 的第二参数取低字节，零值清除驾驶员 `+0x35`，非零把 `+0x34` 复制到 `+0x35`；还寻找所驾单位，处理其他驾驶员并调用 `801F94D0`。它不是任意数值直接写入的状态字节。下一步追两个字段的初始化、回合更新和菜单消费者，确认其游戏名称。
- **3D6F**：`resident_func_800ACF44` 扫描 700 个 36 字节记录，检查有效字节、匹配 `+2` 编号，然后清除第一个匹配记录 `+0x22` 的 `0x04` 位。剩余重点是该位的设置者和读取者；这项主要依靠静态交叉引用推进。
- **3D55**：`load_000AB160_func_80210490` 不只查主驾驶员，还按机体 `+0x34` 数量遍历 `+0x38` 起的驾驶员指针，找到后设置选中精灵和镜头。第二参数继续进入表 `80217D20` 及 `801D6A68`，必须沿下游分析，不能只用入口名称猜演出效果。
- **3D5E**：`load_000A7EC0_func_801C517C` 只有 14 条不同地址的指令，设置 `801C58C4=2`，调用 `80080188(6)` 与 `80099814(5,1,2)`。函数短并不表示游戏语义已经完整，下一步是解析状态字段的消费者。

后续以 C 静态分析为主：先处理 `3D69/3D6B/3D6E/3D6F/3D70` 与上述六个条件指令的结构体字段；随后追 `3D36/3D55` 等高频状态机。能够由完整读写链确认的语义直接登记代码证据；静音运行用于核对视觉效果、时序、特殊分支和写回兼容性。无需为每条普通赋值指令重复跑完整开场。
