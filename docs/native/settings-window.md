# 设置窗口规划：从热键和菜单走向「选项」

日期：2026-09-18。**第一版已实现，见 §6；其余仍是规划。** 目前玩家能调的东西分散在热键（F6 图像、F7 语言）、菜单栏的「规则」菜单、启动参数和 profile 文件里；规则已有七项、以后还会增加，需要一个集中的入口。本文定下入口结构、分类、每项的生效时机和验收要求，具体实现另排。

## 1. 现状盘点

| 现有入口 | 覆盖内容 | 问题 |
| --- | --- | --- |
| F6 | Original / HD 图像 | 只有循环切换，看不到当前值与可选值 |
| F7 | ja / zh-Hans / en 循环 | 同上 |
| 菜单栏「规则」 | 修正、难度调整两类规则与预设，实时生效并写回 `rules.json`（规划时的入口，已由 §6 的「选项」取代） | 条目会随规则增加一直变长，没有分组和说明文字 |
| 启动参数 | `--rules`／`--rule-fixes`、`--language`、`--images`、`--resolution-scale`、`--font-size` 等 | 只在启动时可用，普通玩家不会用命令行 |
| profile／设置文件 | `play-profile.json` 的 `presentation`（locale、images、model_5600、resolution_scale、font_size）、试玩目录下的 `rules.json` | 手工编辑，没有界面 |

## 2. 入口与结构

菜单栏改为**「选项」**一个顶层菜单，下面按分类给出子菜单，另有「设置…」打开弹出窗口。窗口与菜单共用同一份设置模型，任何一处改动立即反映到另一处。

```
选项
├─ 游戏性调整…      规则修正、难度调整（现在的「规则」菜单内容）
├─ 显示…            Original / HD、分辨率缩放、字号、减少闪白
├─ 语言与文本…      界面与剧情语言、阅读速度、已读跳过
├─ 存档…            历史会话、自动保存节点（M1 落地后）
└─ 设置…            打开完整设置窗口（以上分类为标签页）
```

- **「选项 → 游戏性调整」是本轮确定的路径**：现在的「规则」菜单整体搬到这里，内部再分「修正」（默认开启，修的是原版自相矛盾的地方）和「难度调整」（默认关闭，改变强弱）两组，组名之间用分隔线和不可点击的说明项。
- 默认生效、没有开关的[基础修复](../gameplay/base-fixes.md)不进入设置界面，只在文档和「关于」里说明。
- 窗口用标签页承载同样的分类，每项带一行说明、当前值、默认值，以及「恢复默认」。

## 3. 每项设置要写清的元数据

沿用规则目录的做法，把设置定义成数据，界面由它生成，新增一项不改 UI 代码：

| 字段 | 用途 |
| --- | --- |
| id、分类 | 稳定标识与归类 |
| 控件类型 | 开关、单选（原版／减半／关闭这种互斥组）、数值、下拉 |
| 标签键 | `content/locales/*.json` 的 UI 键，三种语言必须齐全（`profile.py` 的 `UI_KEYS` 已按规则目录派生，缺一项就拒绝启动） |
| 默认值 | 首次启动的取值；修正类默认开、难度类默认关 |
| 生效时机 | 立即／下次结算／下次登场／下次进关／下次启动——现在规则是「下次结算」，头目假身是「下次登场」，这类差异必须显示在界面上 |
| 写入位置 | `rules.json`、presentation 设置或 profile |
| 存档影响 | 是否改变持久玩法状态；改变的要进入存档兼容清单 |

互斥组（例如头目假身的原版／减半／关闭）在数据层仍可以是两个布尔开关，但界面按单选呈现，避免现在「两个都勾时以取消为准」这种需要解释的状态。

## 4. 技术方案

- 第一版做 **AppKit 弹窗**，和当时的菜单栏代码同层，能直接复用语言标签与实时切换机制，不影响游戏渲染。（后已整体改为 RmlUi 页面，见文末。）
- 游戏内叠加 UI（RT64 层）留到需要手柄操作或跨平台时再做；那时设置模型不变，只换呈现层。
- 设置模型放在宿主的一个头文件里（类似 `rule_fixes.hpp` 的 `catalog`），Python 侧继续从同一份定义派生启动参数与校验，保证两边不会漂移。

## 5. 验收要求

- 每个分类、每项控件在三种语言下都有标题与说明；切换语言时窗口和菜单同时重绘（菜单已有这条，窗口沿用）。
- 改动写入对应文件并追加事件日志（现有 `rule-fixes-events.jsonl` 的做法），运行报告能还原「这次运行用了什么设置」。
- 提供 QA 控制钩子：像 `rule-control.json` 那样按下某一项，写出控件状态，供有界运行核对。
- 「恢复默认」与「原版」预设分开：前者回到默认值（修正开、难度关），后者是全部关闭的原版行为。
- 窗口开启时游戏暂停与否要明确；改动的生效时机按 §3 显示，不能让玩家以为战斗中途的切换会影响这一次结算。

## 6. 第一版实现（2026-09-18）

| 部分 | 状态 |
| --- | --- |
| 菜单栏「选项」 | 第一版：「游戏性调整」子菜单与「设置…」（⌘,），AppKit。现只保留菜单栏入口（`macos/app_menu.mm`）。 |
| 设置窗口 | 第一版：规则（分组）、三个预设、语言单选、画面单选（HD 不可用时灰掉），每组一行说明，AppKit。现为 `src/native/ui/frontend.cpp` 的 RmlUi 设置页，另含「战前确认界面」与「场间画面」两个新版／原版单选（2026-09-23 加入后者，覆盖主菜单与改造画面，下一次打开画面时生效，写 `presentation.json` 的 `intermission_ui`）。 |
| 同步 | 窗口、菜单、F6／F7 与 QA 钩子共用同一份状态；窗口每帧回读当前值，语言变化时重取全部标题。 |
| 输入 | 窗口打开期间游戏收不到键盘输入，关闭后等按键全部松开（`ModalInputRelease`）。**游戏不暂停。** |
| 写回 | 规则写 `rules.json`；语言走原有的 presentation 设置（写 `presentation.json`）；画面不写文件，只影响本次运行。 |
| 分组来源 | 规则目录每项带 `Kind`（`correction`／`difficulty`），菜单、窗口和默认集合都由它派生；`tests/test_rule_fixes.py` 核对它与 `rule_settings.CORRECTIONS`／`DIFFICULTY` 一致。 |
| QA 钩子 | `SRW64_WINDOW_CONTROL=1`：`settings-control.json`（schema `srw64.settings-control.v1`，`action` 为 `open`／`close`／`press`，`id` 如 `rule:limit-cap`、`preset:rules_defaults`、`locale:zh-Hans`、`images:original`），结果与全部控件状态写入 `settings-window-events.jsonl`。 |
