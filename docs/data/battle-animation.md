# 战斗动画处理逻辑与自定义机体／武器可行性

更新：2026-09-19。静态分析（反汇编与 ROM 数据），没有运行游戏。图像资源、场景格式与导出见[战斗图像](battle-graphics.md)。“代码确认”指读到了读取／使用该数据的指令；“静态推断”指从使用方式推出的含义，尚需实机核对。

## 结论

1. **战斗动画不是字节码脚本。** 每件武器对应一条固定布局的记录：4 个头部字段、最多 8 个音效、最多 24 个 actor。每个 actor 指定一个战斗场景（图像）、一组坐标和一个**行为例程编号**。时序逻辑全部写在战斗 overlay 里约 270 个原生例程中，actor 之间靠一个共享的“相位”字节协作。
2. **自定义武器动画可以只靠数据完成**：新记录复用现有行为例程，把 actor 指向新的或现有的场景即可。全新的演出逻辑（现有例程做不到的动作）才需要写 C++ 原生例程。
3. **自定义美术的格式已完全读通。** 机体图集、调色板、场景（零件＋顶点＋步骤表）都可以由工具反向生成（PNG → 图集／调色板／场景），HD 替换沿用按纹理哈希的现有机制。
4. **加入机体／武器的难点在 ID，不在图像。** 所有表都是首尾相接的定长表，表基址和两个 ID 上限写死在代码里。
   - **占用现有的占位或重复槽位**：只需宿主层的数据覆盖和资源服务，不用重新生成 recomp 代码，是最短的路。
   - **真正新增 ID**：要在多处读取函数上挂钩子、重新生成代码，并处理存档兼容。

## 一次攻击的数据流

```text
武器 ID ─→ ROM 0x11FC80[id] (u32 偏移) ─→ 动画库 0x184990 + 偏移，DMA 0x3C0 字节
          │                                   │
          │                                   ├─ 头部：镜头模式、命中特效号、攻方动作、守方动作
          │                                   ├─ 音效表（≤8）
          │                                   └─ actor（≤24）：registry, x, y, z, h4, h5, h6, behavior
          │                                        │
          │                                        └─ 0x11E3D0[registry] = (场景, 图集, 调色板) ─→ 资源加载 ─→ 精灵槽
          ├─ ROM 0x119970[id]：规范武器 ID（机师台词用）、接触标志、伤害节拍模式、相位码
          └─ 命中特效号 ─→ 0x216150 / 0x2129F0（同格式，159 条；156–158 为击毁）
守方：反应代码 ─→ 0x216630 / 0x2163D0（同格式，28 条）；盾牌图 0x2166A0（24 条）或机体战斗记录
双方基本姿势：0x84E40[机体 ID]；机体战斗记录：0x118610[机体 ID]
```

- 攻击方 actor 使用的图像大多就在攻击方自己的战斗图集上（例如 registry 297 = ガンダムシュピーゲル 的 (2477, 1612, 1908)）；光束、爆炸等在特效图集上。

- 每个动画库后面都跟着一份没有被使用的偏移表拷贝（`0x19AA40`、`0x215ED0`、`0x2165B8`）。

## 动画记录格式

解析器 `801C3D38`／`801C4EF0`；残留的开发者编辑器（见文末）按同一格式编译，可作旁证。

```text
u16 camera          镜头／站位模式 0–3（801C67EC 选择每帧处理 801C63BC/64D8/6584/6678）
u16 hit_script      命中特效库条目
u16 action          攻方主精灵动作号（0–188，跳转表 0x80223990，经 801E4668）
u16 defender_action 普通命中时守方的动作号
s16 sounds[≤8], 0xFFFF     行为例程用 801C355C(n) 播放第 n 个；−2 = 静音
actor[≤24] { u16 registry; s16 x, y, z; u16 h4, h5, h6; s16 behavior }, 0xFFFF
```

| actor 字段 | 含义 | 可信度 |
| --- | --- | --- |
| registry | 战斗场景总表索引，载入到轮换精灵槽（`801C50D8`）；守方一侧 x 取反 | 代码确认 |
| x, y, z | 相对己方机体精灵的偏移；部分例程把它们当参数用 | 代码确认 |
| h4 | 由例程解释，多为起始延迟帧数或角色号；bit15 为标志 | 部分确认 |
| h5 | 每帧复制到精灵字节 +0x35（多为 0xFF，例程会渐变它，推测为不透明度） | 复制代码确认，含义推断 |
| h6 | 显示模式：1 = 永不自动隐藏，2 = 永不自动显示（控制用 actor） | 代码确认 |
| behavior | 行为例程 3–382，函数指针表 `0x80225030`（经 `80220C0C`）；4、5、370、371、380、381 为空 | 代码确认 |

全部 1,329 + 159 + 28 条记录都按此格式解析通过：最大 406 字节、正好 24 个 actor 的记录存在，registry 最大 1045，behavior 均在 3–382。

## 行为例程与相位字节（静态推断为主）

- `801C5BAC` 每帧在区块相位字节（B+0x25）带 0x40 时，依次调用所有活动 actor 的例程；主精灵与全部 actor 共享这个字节（E+0x48 指向它）。
- 已见相位码：0x41–0x46、0x48、0x49、0x4B、0x4C、0x50–0x57、0x5A。0x44 =“开火”：动作 88 让攻方前冲 21 帧后写入 0x44，142 个例程等待它。0x49 使 actor 停用。0x50–0x57 是 actor 之间串联的子步骤（如计时器 124 在 h4 帧后写 0x50）。0x43、0x45、0x46 的含义为推断。
- 例程可用的基本操作：换场景／图集／调色板（`801C5700`、`80098204`、`80098590`、`80098604`），显示／隐藏（`801C3840`／`801C37FC`），播放音效（`801C355C`），全屏闪白／黑（`801C9520`、`801C95CC` → `8009AC84`），精灵调色板效果 10 种（`801C963C` → `80099C88`），镜头跟随（`801C637C`／`801C63A8`），推进伤害节拍（`801C8DFC`），载入防御精灵（`801C4574`），背景隐藏／恢复（`801C3C40`／`801C3C64`，未确认），派生子例程（`80220C0C`、`801E4668`）。
- 每侧状态 `0x800F97E0 + side × 0x1074`，含武器区块（+0x2C）和反应区块（+0x848）各 0x81C 字节：0x4C 头部、主精灵伪 actor、24 个 0x50 字节 actor。
- 特效精灵槽 0xAA–0x107（94 个）轮换使用，没有溢出检查；三个区块 × 24 actor 放得下。
- 特殊武器 ID（`801C3C9C`）：−1 无动画；−2／−3（防御／回避而非反击）用内置空记录 `D_80222D40`；`0x1000` 读 RAM `0x80250010`（开发者编辑器写入处）。

## 资源加载与内存

- 资源表在 ROM `0xA20BD0`：u32 数量（6,436）＋ 8 字节描述符；每项是 u32 解压长度＋LZSS（`src/srw64_rom/resources.py`）。
- 载入函数 `80089E9C(id)`：
  - `80089EAC` 的 `sltiu 0x1924` 是唯一的资源 ID 上限（代码确认）。
  - 已载入的资源只加引用计数；槽表 `D_80160340` 有 200 项，首次适配分配。
  - 描述符由 `80089BBC` 直接 `osEPiStartDma` 读取，**不经过**宿主已挂钩的 `8007F704`；数据解压则经 `8007F704`。
- 堆为 `0x80277800–0x80400000`（1,607,680 字节），全部已载入资源共用，没有单项或单场战斗的额外上限。
  - 分配失败会打印 “ALLOCATE ERROR”，返回 −1，调用者随后得到空指针。
  - 最大资源 263,177 字节（1349），最大机体图集 201,609 字节。一台机体的战斗图是 3 个资源（场景约 1.4 KB、图集、264 字节调色板）。
  - 战斗中的实际余量没有测过。
- recomp 运行时有 8 MiB RAM，游戏只用到 4 MiB 以上的 `0x80400000–0x804152F0`（开发者编辑器）和宿主脚本注入区 `0x807F0000`，中间约 3.9 MiB 空闲。
- 图像约束：零件多为 32×32（最大见到 48×32、40×40），CI8 在 2 KB TMEM 中每零件最多 2,048 texel；图集尺寸为 32k+1（留 1 像素边供双线性过滤）；单帧最多见到 123 个零件；CI8 调色板 256 色。

一件武器：基础数值 ROM `0x74E90`（1,329 × 16，`800A642C`）；名称文本 1370＋ID 与菜单名 2699＋ID；武器战斗记录 `0x119970`；动画偏移 `0x11FC80`；出现在某台机体的武器列表行里；可选的改造继承映射 `D_800CB5E8`。

### 路线 A：占用现有槽位（推荐先做）

- **候选机体槽**：
  - 314 与 325 是字节完全相同的 νガンダム 记录（与 50 号也只差几个字节）；309 ゴッドガンダム 与 1、2 共用武器列表。部署、事件、变形／合体表里都没找到它们的引用，还需逐一复核。
  - 354–362 是占位记录，但没有机体战斗记录行（`0x118610` 只有 354 行），用它们要先解决战斗记录越界，适合放到路线 B。
- **候选武器槽**：147 个武器 ID 不在任何机体的武器列表里（如 10–14、1191–1198、1328）。其中不少是真实武器，例如 24 シャイニングフィンガー 有自己的 cut-in 动画，可能由代码按形态授予。只能作为候选，逐个排除代码引用后再用。
- **宿主要做的事**：
  - **数据覆盖**：把 `patch_copy` 字节补丁（`src/host/upgrade_rules.hpp`，目前用于改造规则修改机体 +0x20、武器 +0x0E）扩展为通用数据覆盖层。凡经 `8007F704` 读取的 ROM 表都能覆盖，包括所有 overlay 载入的数据和地图图标表。
  - **武器列表**：新的列表写进 0xFF 空隙并改指针，不动共用列表。
  - **动画记录**：`0x11FC80` 的偏移是 u32，新记录可以放进宿主已有的虚拟 ROM 窗口（`0x02400000`、`0x03000000` 机制）。
  - **新图像**：覆盖 `80089BBC`，让描述符读取指向虚拟窗口中的新资源（或用 5600 那样的数据型 ROM 变体）；同一机制也能替换现有资源。
  - **名称**：用现有的虚拟文本路径提供 527＋ID 等字符串。菜单只能画 ROM 字库里有的字形，菜单名要保留 格／射／P 标记。
- **风险**：已有存档若持有该 ID，会显示成新机体（上述候选预计没有）；战斗堆余量未测。

### 路线 B：真正新增 ID

- recomp 允许宿主接管函数（`tools/recomp/toolchain/generate_cpu.py` 的 `NATIVE_HOOKS` 把生成函数改名，宿主在 `src/host/game_hooks.cpp` 里提供原名）。N64Recomp 也支持指令补丁，但当前生成的 `recomp.toml` 没有用。
- **要做的**：
  - **读取函数**：接管小的读取函数（`8009C6E4`、`8009C864`、`801C30D0`、`801C3278`、`801C3128` 及 `load_00216730` 里的拷贝）。
  - **读表函数**：用指令补丁把 `800A6E68`、`800A5254`、`800A8CE8`、`800A642C`、`800A67C8`、`800A68BC` 的表基址改到包含原表加新行的虚拟窗口。
  - **地图图标**：5 处读取改到空闲 RAM 中的新表。
  - **ID 上限**：放开 `0x531` 和 `0x1924`。
  - **名称**：给名称调用点加钩子，映射到私有文本 ID。
- **存档**：据一个子代理对存档序列化代码的阅读，机体 ID 以 10 位保存（`id << 6 | 武器数`），每台最多 63 件武器，每个存档库有 140 台机体、100 名机师、700 件武器的池（待核对）。所以新机体 ID 应 ≤ 1022，而且存档会依赖 MOD——不带 MOD 读档会静默读到错误数据，需要指纹或伴随文件，`src/srw64_native/checkpoints.py` 目前拒绝额外字段。
- 漏掉任何一个读取点都会静默读错而不报错，这是这条路线的主要风险。

### 路线 C：ROM 扩容

宿主已支持数据型 ROM 变体（`config/recomp/rom-variants.json`），ROM 在 `0x1D8C000–0x2000000`（2.45 MiB）和 `0x86B000–0x89A000` 有空闲。但各表首尾相接、基址和上限都是代码常量，扩容本身只对路线 A 的资源重定向有帮助。overlay 代码字节必须与原版一致（recomp 代码由它生成），变体还带来单独的存档与哈希锁，需要以补丁形式分发。

### 新美术的制作流程

1. 画一张机体图（战斗姿势及武器动作零件），量化到 256 色以内。
2. 反向工具切成 32×32 零件、排入 32k+1 尺寸的图集，生成调色板和模式 0 场景（每零件 8 个顶点，第二组为镜像）。格式已由本次导出器和测试逐项验证，这个工具尚未编写。
3. 为每个动作写一条场景总表项和武器动画记录的 actor，行为例程从现有 270 个里挑选对应的（射击姿势 359、光束 118、斩击 43／44 等），`animations.json` 可当作现成的参考库。
4. HD 版本继续按纹理哈希替换。

### 需要实机验证的项目

战斗中堆的实际余量；一拍对应的 VI 数；相位码 0x43／0x45／0x46 的含义；`0x118610` 与 `0x7D980` 各字段；路线 A 替换一台机体后完整打一场战斗（攻击、反击、盾防御、击毁）。按项目惯例，这些运行前先确认。

## 残留的开发工具

- **`load_00089EA0`：ROBO VIEWER。** 调试用的机体图像查看器，自带一张 1,449 项的场景表（ROM `0x8AB58`）。
- **`load_00217FD0`：战斗动画编辑器。** 载入 `0x80400000`，编辑结果写到 `0x80250010`，并用特殊武器 ID `0x1000` 试播。
  - 它的名称表（`0x80402E3C`）给战斗场景总表的条目起了名字，例如 222「WepIanNet」、121「WepGndm00」、602「WepBSRedSwing1」。
  - 表尾的例程名（BtlProcShield、BtlProcCoverDiffence、BtlProcBeamShield 等）以 767 的偏移对应行为例程 ID。
  - 编辑限制为 registry < 0x41B、behavior ≤ 0x17F、h6 ≤ 4。
  - 这些名字是给场景和行为例程命名的最好来源，下一步可以一起导出。
