# HD 资产盘点：分类、地图动态效果与阿里云模型选择

日期：2026-09-23，2026-09-24 补上各类的现状。盘点本身来自静态分析，当时没有跑游戏，也没有调用收费接口。各类用哪条接入路径、做到哪一步，见 [HD 化规划](../design/hd-pipeline-plan.md)；以前的模型实测见 [阿里云基准](../design/hd-ai-benchmark.md)。

盘点工具是 [`asset_inventory.py`](../../tools/content/asset_inventory.py)。它解压 ROM 的全部资源，按头部判断种类和尺寸，再按资源号区间归类，结果写到 `build/content/asset-inventory.json`。对应测试是 [`test_asset_inventory.py`](../../tests/test_asset_inventory.py)，有 ROM 时会核对总数和各主要类别的图数。

**2026-09-23 范围决定**：战斗动画相关的类别（战斗精灵、武器精灵、盾、cut-in、特效、3D 战斗背景、战斗 HUD）暂缓；不训练 LoRA，风格一致靠参考图和逐批审阅。

区间的来源分两种。有绑定表或已有提取器的区间标为 `table`；其余是渲染成图后人工辨认的，标为 `inspected`，本文用「目测」表示。目测只能说明图的内容，不能说明它在哪个画面、由哪个函数绘制。

### 机体标识（地图单位图标）

战术地图上每台机体是一个 16×16 的 SD 头像，由 `801C60A4` 给每个单位建两个精灵子槽，都走模式 5：

- **子槽 0**：图标本身，优先级 0x91，调色板参数是 `1010 + 阵营`。
- **子槽 1**：阴影椭圆（资源 687），优先级 0x92，画在图标后面。

阵营颜色完全来自调色板：1010 蓝、1011 红、1012 黄、1013 灰。同一张图标换调色板就是另一个阵营。1013 对应的阵营含义，以及「已行动」是否也换成它，还没有确认。1015 不是这一组的配色，用途待查。

调色板的 1–6 号是阵营色阶，7–13 号是固定色（绿眼、粉色等），0 号透明。所以高清版必须继续跟着调色板换色，不能只做一套 RGB。

**不用 AI**：
- 9-08 实测里，16 像素的机体会被重构成新造型；
- 16×16 也低于所有服务的最小输入尺寸。

改用确定性的像素画放大算法。它们直接从本地 ROM 算出结果，可以在首次导入时生成，不需要分发美术文件。

| 做法 | 效果 | 调色板 | 结论 |
| --- | --- | --- | --- |
| 双线性（现状） | 4 倍内部分辨率下明显发虚 | — | 需要改 |
| 最近邻 ×4 | 像素方块清晰，与原作一模一样 | 只用原色 | 保底；也可以只让这类图改用点采样，不做替换图 |
| Scale4x（EPX 两次） | 斜线变顺，仍是像素风格 | **只用原色**：直接在色号图上运算，一张结果适用所有阵营 | 保留像素感时的首选 |
| hqx ×4 | 介于两者之间，保留较多细节，边缘仍有锯齿 | 会混出新颜色 | 备选 |
| xBR ×4 | 最平滑，最接近「高清化」，与高清地图最协调；个别细节会被合并 | 会混出新颜色 | 追求高清观感时的首选 |
| 人工重绘 64×64 | 质量最好 | 按色号图绘制即可 | 317 张工作量大，只作以后的选项 |

- **会混色的算法**要按调色板分别生成：317 张 × 4 个阵营，约 1,300 张 64×64 图。
- **接入**：沿用 RT64 纹理哈希替换。图标是单独上传的 16×16 纹理，哈希本身就区分调色板，正好对应「每个阵营一份」。
- **分辨率**：在内部倍率 4 下是一比一采样；更高倍率时提供 8× 版本或 mipmap。
- **MMPX（已试）**：一种只用原色的精灵放大算法（McGuire & Gagiu 2021，MIT 许可）。[`pixel_scale.py`](../../tools/hd_ai/pixel_scale.py) 按参考实现移植到色号图上（另有 Scale2x），试了 5 个图标，结果很保守，几乎保持最近邻的像素形状，只修掉少量孤立锯齿。对这类抖动很多的 16 像素头像，改善不如 Scale4x 明显。
- **AI 选项**：16×16 只有 256 个像素的信息，AI 做的其实是「重画」，不是「放大」。要补出真实细节，就得给它额外的信息来源。按这个思路，候选分三类，都要先用 5 个图标试：
  1. **像素画专用生成服务**：输出仍是像素画，只是尺寸更大、细节更多，适合「保留像素风」。
     - [PixelLab](https://www.pixellab.ai/docs/tools/resize) 的 Resize 用 AI 按新尺寸重画像素画，范围 16–200 px，建议每步最多放大 2 倍（16→32→64）。文档说它只在 Aseprite 插件里提供；另有 [API](https://api.pixellab.ai/v2/docs)，但是否有同等功能要确认。
     - [Retro Diffusion](https://retrodiffusion.ai/) 提供像素画模型，支持 img2img（可调强度）、透明背景，以及限定输出调色板。
     - 两家都是海外商业服务，要注册，价格要注册后确认。可以把输出限定在图标原来那 14 色，再映射回色号图，四个阵营色就都能自动生效。
  2. **通用图像编辑模型 + 参考图**：适合「高清平滑」。把 16×16 图标和同一机体的战斗精灵（ROM 里 97 px 以上、造型相同的像素画）一起送进去，让模型照精灵的造型重画图标。这里只是拿战斗精灵当参考，不涉及已暂缓的战斗动画 HD 化。
     - 9-08 的失败正是因为没有参考图。
     - 可用 `qwen-image-3.0`（3 张输入图）或 `wan2.7-image`（9 张参考图）。317 张每个候选约 63 元。
     - 输出缩到 64×64 后，同样按原调色板量化回色号。
  3. **社区像素超分模型**：本地运行，不收费，但都是 2020 年用动漫图训练的旧模型。
     - [4x PixelPerfectV4](https://openmodeldb.info/models/4x-PixelPerfectV4)：WTFPL 许可，可以随意使用。
     - [4x Fatal Pixels](https://openmodeldb.info/models/4x-Fatal-Pixels)：CC-BY-NC-SA 许可，不可商用。
     - `4x xbrz`、`4x scalenx`：只是用网络模仿同名算法。

     它们没有额外信息来源，效果接近一种学出来的 xBR，优先级最低。
- **矢量化**：Kopf–Lischinski 的 [Depixelizing Pixel Art](https://www.cs.jhu.edu/~misha/ReadingSeminar/Papers/Kopf11.pdf) 不是 AI，它把像素画转成平滑的矢量轮廓，可以任意放大，并保留原来的颜色区域。Inkscape 的「描摹位图 → 像素画」就是用的它（[libdepixelize](https://gitlab.com/inkscape/devel/libdepixelize)）。它忽略透明通道，要另外处理轮廓。本机没有安装，没有纳入对比。

## 3. 战术地图的动态效果

这一节来自对 `801C6EFC`、`800945D4`、`8009CB04`/`8009CC0C`、`800858DC` 和 3D34 实现 `8020A874` 的静态阅读。「跳」是战术主循环 `801DFBD0` 执行一次；1 跳约 2 VI 是推测，没有核对。

### 3.1 地图记录

每条记录 12 字节：

```text
u16 layout, atlas, palette, aux1, aux2; u8 模式; u8 参数
```

`group_count` 就是去重后的图块数，每组对应一个图块及其放置列表，与动画无关。运行中没有任何代码改写单格：布局的读者只有绘制、取地形和取尺寸，全部是只读的。放置标志 `0x2000` 出现在地图 43、45、47、119，共 444 处，没有代码读取它。

### 3.2 水面：调色板循环（代码确认）

- **装载**：非零的 aux1 / aux2 由 `8009CB04(通道, 资源)` 装载，通道记录在 `80178D50 + 通道×0x12`。
- **推进**：`801DFBD0` 每跳调用 `8009CC0C`。倒计时到 0 就把下一帧颜色直接写进地图调色板资源（槽 0x3B）。`800945D4` 每帧都重新载入 TLUT，所以写入会立即显示。门控条件是 `8010279D != 0` 且 `80178C6A & 0x81 == 0`，菜单或暂停时是否冻结还没有核对。
- **aux 资源格式**：先是 `u8 帧数 F, u8 起始色号 S, u8 颜色数 N`，接着是 F 个字节的每帧跳数，然后是 N×F 个 RGBA5551。第 c 色第 f 帧的偏移是 `3 + F + (c×F + f)×2`。16 份资源的长度都与此吻合。
- **水面参数**：6419–6424，色号 0xC0–0xD0，17 色 × 9 帧 × 每帧 9 跳，81 跳一轮。
  - 38 张地图引用，其中 36 张的图集里确实有这些色号的像素。
  - 水面面积很大：地图 56 有 1,489 / 2,700 格，约 20.5 万像素；地图 13 有 834 格。
- **其他循环**：
  - 6426：0xB0–0xBE，5 张地图
  - 6427：32 帧，地图 7
  - 6429 / 6430：0x15–0x17 红色脉动，地图 0、19、20
  - 6431：每跳换一帧的快闪，17 张地图
  - 另有 6428、6432–6435，用于灯光、熔岩和宇宙特效
- **合计**：67 张地图有可见的调色板动画。另有 28 张引用了 aux，但图集里没有对应色号的像素，属于无效引用（4、23、65、104、111、113–118、137、140–155）。逐张清单见 [战术地图清单](tactical-maps.md)。
- **例子**：女主第一话的地图 20，6422 是河流（66 格），6429 是 6 格红色脉动。

### 3.3 其他动态

| 动态 | 机制 | 规模 |
| --- | --- | --- |
| 殖民地旋转 | 模式字节为 1 的宇宙地图（图集 6229）每 27 跳把 6235 的下一帧（64×48，共 8 帧）拷进图集 (208,0) | 77 张宇宙地图启用；39 张含 1–5 个殖民地实例，每个 4×3 格，全部同步 |

| 同布局换调色板 | 同一布局配不同调色板 | 0 / 138 / 139 是夜景与白天；60→64 由红光变暗；157 全黑 |
| 震动（3D36） | 只让镜头 X 来回摆动，整个画面平移，边缘露出黑色清屏色 | — |
| 淡入淡出（3D3B） | 全屏色块叠加层，不改调色板 | — |
| 卷动 | 镜头按整数像素偏移，没有 UV 卷动 | — |
| 总览缩放 | `800943E0` 把整张地图缩到 266×200，跳过外圈 2 格边框（图块 1 / 2） | 标志 `801027DB` 的写入点没有找到 |
| 地形面板 | `801E2D54` 把光标所在格放大约 2.3 倍 | — |

绘制顺序：地图是战术场景的最底层（优先级 0x93），上面依次是范围高亮、单位、地图动画、窗口和全屏叠加。另外，`800945D4` 也用来画集中线 610–612。

### 3.4 对 HD 的影响

结论：纹理哈希替换在这里行不通。循环色和殖民地格的 TLUT 或图集内容每跳都在变，哈希也跟着变。战术地图要整张接管，实现和地图 20 样板的验证见 [HD 化规划 §3](../design/hd-pipeline-plan.md#3-战术地图)。

核心思路是「高清底图 + 高清色号图 + 游戏当帧的实时调色板」。好处是不用重新实现循环逻辑：游戏往调色板里写什么，高清画面就跟着显示什么。按这个思路，各类动态的处理如下：

| 动态 | 处理 | 需要的高清资产 |
| --- | --- | --- |
| 水面、灯光、熔岩、红色脉动、快闪（调色板循环） | 着色器按色号查当帧调色板，时序和暂停门控都与原版一致 | 每张地图一张色号图，不需要逐帧资产 |
| 夜景、白天、变暗、全黑（3D34 同布局换调色板） | 同一机制自动生效 | 无 |
| 连环画式换图、局部变体（3D34 换布局） | 当作另一张地图 | 以前一步为基础，只重画变化的 18–29 格 |
| 殖民地旋转 | 叠加一个 8 帧精灵，帧号读 `80178C6D` | 8 帧；放在一次请求里一起生成，保证帧间一致 |
| 震动、卷动 | 每帧读镜头偏移，自动跟随 | 无 |
| 淡入淡出 | 叠加层画在地图上面，不受影响 | 无 |
| 总览缩放 | 计划同一套纹理缩小绘制，靠 mipmap 保证画质；样板里仍画原版 | 无 |
| 地形面板 | 第一版保留原版绘制，以后再采样高清图的子矩形 | 无 |

其他要点：

- **按资源筛选**：`800945D4` 也用来画集中线 610–612，接管时要按地图布局资源号识别，避免误接管。
- **资产键**：高清资产按布局号做键，调色板不进键，由运行时决定颜色。
- **动画区域不交给 AI 重画**：水面等区域的色号图用只复制原色号的算法放大（样板用 MMPX，与机体标识同一套工具），做法与世界地图的海岸保护相同。这样水纹的形状更顺，动起来与原版一样。AI 只负责静态区域的细节。
- **可选的增强水面**：着色器里叠加缓慢移动的细节纹理，颜色仍取自当帧调色板。这是新增表现，要单独开关。

### 3.5 世界地图

世界地图底下没有动画海面。透明的海域显示的就是清屏色 RGB(0,55,90)，由 `801C3490` 设置。HD 版如果要画海面，属于新增内容，要单独开关，不能算作还原。只有区域 5599 会在槽 0 画星空 5582。

- **透明通道**：生成式模型都不接收也不输出透明。Alpha 继续取自原图遮罩（头像用 [`portrait_matte.py`](../../tools/hd_ai/portrait_matte.py)）。只有普通超分能直接保留 RGBA。

- **9-08 超分失败**：403 可能与临时桶的上传路径前缀有关，没有确认。以后改用 SDK 的本地上传，或自建上海地域 OSS。
- **自动 QA**：以确定性指标为主（遮罩 IoU、缩回原尺寸后的色差）。视觉模型只做第二道判断，不作为唯一验收。

头像是最大的一项，但原因不在分辨率：`qwen-image-3.0` 按张计价，1K 和 2K 同价，都是 0.20 元。花费来自数量和候选数：304 张 × 2 个候选。按路线分：

| 头像路线 | 单价 | 304 张合计 | 效果 |
| --- | ---: | ---: | --- |

也可以混合：全部头像先用超分打底，只有主要角色走生成式重绘。

阿里云上没有比 0.20 元更便宜的可用编辑模型（2026-09-23 查官方页）：

- [`z-image-turbo`](https://help.aliyun.com/zh/model-studio/z-image-turbo) 0.10 元，但只能文生图，不能输入原图。
- `wanx2.1-imageedit` 0.14 元，是旧版，其中的超分功能不比 VIAPI 超分强。
- 新人免费额度在这几页上都没写，要在控制台确认。

**拼图批处理**：`qwen-image-3.0` 按张计价，1K 和 2K 输出同价，输出面积最大 2048²。所以可以把几张头像按网格拼成一张输入，一次请求出一张 2048² 的图，再切开。

| 拼法 | 每格输出 | 每张头像单价 | 304 张合计 |
| --- | --- | ---: | ---: |
| 单张（现在的做法） | 最大 2048² | 0.20 | 61（1 个候选） |
| 2×2 | 约 1024² | 0.05 | 约 15 |
| 3×3 | 约 680² | 0.022 | 约 7 |
| 4×4 | 约 512² | 0.013 | 约 4 |

目标是 384²（4 倍），所以 3×3 也够用。风险是模型可能把相邻格的特征混到一起，或者各格处理得不一致。缓解办法：
- 格子之间留中性色间隔；
- 同一作品的角色放在同一张；
- 提示词写明各格独立。

同一张里的角色风格会自然一致，这反倒是好处。2×2 已经试过并采用：`portrait_batch.py` 用 75 次请求出了全部 300 张。

金额本身不是瓶颈，主要成本在审阅和一致性控制上。批量请求前按 [基准](../design/hd-ai-benchmark.md) 的规矩冻结输入与提示词，已有请求记录的不重复提交。
