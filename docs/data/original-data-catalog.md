# 原始游戏数据目录与解析进度

更新：2026-09-12。

这批实现把日版原 ROM 转成可重复生成、可追溯的只读目录，供后续多语言、数据 Mod 和关卡分析使用。输出包含原始字节、稳定身份、来源地址、哈希、跨表引用和字段置信度。**它还不是可写的游戏数据 ABI；关卡脚本已完成静态指令解析，但尚未做运行比对与写回。**

## 运行

在仓库根目录执行：

```sh
.venv/bin/python -B tools/content/extract_original.py
python3 -B tools/data_viewer/serve.py --port 59110
```

浏览 `http://127.0.0.1:59110/`。服务器仅监听 loopback，并且只提供 `assets/original-data/`，没有写入 API。停止该终端即可关闭服务。同一目录下的 `story.html` 是按章节阅读日文原文的剧情查看器，数据来自 `story/index.json` 与 `story/NNNN.json`，见[关卡脚本完整解析](../script/stage-script-exploration.md#剧情查看器)。

可选加入已有女性超级系第一话快照：

```sh
.venv/bin/python -B tools/content/extract_original.py \
  --snapshot build/recomp/gfx-probes/female-map-audio-1/latest-gfx-rdram.bin
```

不提供快照时，提取不依赖历史运行目录，也不会生成“第一话观察”分类。提供快照时要求同目录有 `report.json` 和 `scene-evidence.json`，并核对原 ROM 身份和场景标识。目录中的观察记录另存快照、报告和场景说明的哈希。场景说明的截图与最终 RDRAM 不一定是同一帧；不能把截图帧号赋给快照。

依据不是数值看起来合理，而是原记录→运行时字段→显示坐标与文本标签的关联。resident 标签表 ROM `0x518C0`（机体）、`0x51968`（驾驶员）、`0x51A80`（武器）均保留字节锁。状态显示消费者在 `load_000AB160:801E517C / 801E6410 / 801E6C5C`；成长循环在 resident `800A6238`。驾驶员的基础命中／回避与界面合计值要分开，界面还会加入机体数值。

驾驶员 `+F` 的七种已解释技能位：`01` 切り払い、`02` S 防御、`04` 底力、`08` NT、`10` 強化人間、`20` 聖戦士、`40` 超能力；`80` 未解释。技能阈值的三组各占 10 字节，但 `800A80F0` 每组只读前 9 项，计算满足 `0 < 阈值 <= 当前等级` 的项数。第一组对应掩码 `7C`，名称按 `04→08→10→20→40` 的优先级选择；第二、三组分别对应 `01`、`02`。每组末字节在所有 256 条原记录中均为 0，本工具仍保留它，不能解释成第 10 级。名称原文链接保留现有字表解码结果；字表中的个别疑似误识别字形没有在本批擅自改写。

第三批场景与地图关联：

- `load_000AB160:80209D6C` 用 `8010F5F0` 的场景索引读取 ROM `0x102110`，步长 2，将第一字节写到当前地图索引 `8010F5EE`。相邻符号边界容纳 144 个槽；末尾 `00 00` 可能为填充，不能据此宣称有 144 关。
- `load_000AB160:801C6EFC` 以地图索引读取 ROM `0x10267C`，步长 12，至 `0x102DE4` 共 158 条。五个 u16 由资源加载链消费，两个辅助编号为 0 时跳过；两个尾字节的完整含义暂未解释。
- 女性第一话历史快照的场景索引为 1，地图索引为 20；对应资源为 **6284、6228、6243、6422、6429**。快照中的整张地图资源表与 ROM 字节一致。这确认的是索引和资源关系，尚不是地图格子、事件与编成的完整解释。
- 战术场景入口由 resident `800801A4` 选择 `load_000AB160` 中的 `801E022C / 801E0268 / 801E028C / 801E0350`，后续进入 `801E00AC`。另有 resident `8009DD58 → 8009DBE4 / 8009DC58` 加载 ROM `0x1E3FE0` 与 `0x19BF10` 的数据，保留为下一步事件流分析入口，尚未当作已反编译脚本输出。

目前保留三类边界问题：

1. 名称区有 361 项，两个映射表各 360 项。人物 360 的名称可显示，但不会越界读取下一张表来虚构驾驶员数据。
2. 人物 284 映射基础记录 256。阈值加载公式 `0x7B1B0 + 256*30` 正好落到精神表 `0x7CFB0`。保留此异常；后续需要追控制流确认该路径是否可达，不能仅据此断言原游戏有 bug。
3. 武器指针区到首个 payload 的距离是 `0x5B0`，相当于 364 个 u32。当前按 363 个机体读取；最后一个边界字和机体表末尾间隙还未解释，记录数是当前物理区间划分结果。

## 机体／机师整合档案

浏览首页以「机体」「机师」为主要入口；场景、资源和各张原始表收纳在可展开的辅助分类中。现有 `base:units:NNNN`、`base:actors:NNNN` 和原始表深链接保持有效。

- **机体档案**：基础能力卡片、带名称与参数的武器表、共用武器列表里的关联形态。按原始五个形态槽区分当前形态匹配武器与其他形态武器；后者折叠显示。匹配仍不等于满足全部使用条件。
- **机师档案**：简称／全名、六项能力及精神点、每级成长、六项精神习得、各项已启用技能的 L1–L9 习得等级。人物通过自己的映射关联基础、精神和阈值记录，不能直接用 actor ID 当这些表的索引。
- **同名与空映射**：361 个名称身份各自保留；其中 264 个关联了固定能力记录，可以用「仅显示已关联能力的机师」筛选。负数映射、人物 284 的阈值边界异常和人物 360 的缺失映射仍显式保留，不补零或猜测能力。
- **搜索**：机体支持按引用的武器名与形态名查找；机师支持全名、精神名和技能名。仍可按稳定 ID 搜索。
- **原始依据**：每个整合档案下方保留原表入口，详细字段、字节与证据默认折叠。武器／精神／能力／阈值等原表也提供返回相关整合档案的链接。
- **搭乘关系**：仅在提供历史快照时汇总双向机体／机师关系，明确标为该时点的观察并链接快照来源；没有将它当作全游戏固定配对规则。

整合由 `src/srw64_native/original_profiles.py` 生成，结果附在原记录的 `profile` 中，属于只读展示数据，不改变原始 `fields`、`raw_hex`、映射与身份。`search_terms`、`summary`、`has_stats` 进入轻量索引，页面不需要逐条请求其他数据表来拼接档案。生成代码加入 manifest 的生产者字节锁。

技能等级不是简单按原数组槽位标注。原程序计数所有满足 `0 < 阈值 <= 当前等级` 的项；展示时对九项里的有效阈值排序，因此能正确处理无效零槽、非递增阈值和相同等级同时增加多个技能等级。原始顺序仍保留在阈值记录中。

## 输出、模块与后续架构

- `src/srw64_native/original_data.py`：ROM 表解析、边界检查、引用关系和可选快照观察；不写 ROM，不导入 UI。
- `src/srw64_native/original_abilities.py`：机体能力／装备定义、人物技能持有者索引、双向档案链接和完整覆盖审计；未知位不丢弃。
- `tools/content/extract_original.py`：锁校验、统一生成目录、原始资源解压、全引用检查。
- `tools/data_viewer/web/`：无第三方网络依赖的只读 HTML/CSS/JS；`app.js` 管理分类与导航，`profiles.js` 展示整合档案，`ui.js` 提供共用安全 DOM 组件。支持搜索、能力筛选、分页、相邻记录、稳定 hash 链接和资源下载。
- `tools/data_viewer/web/abilities.js`：能力／技能全体持有者、习得分类及覆盖说明。
- `assets/original-data/manifest.json`：源 ROM、布局、生产代码及输出文件哈希、计数、校验范围和未确认事项。
- `records/*.jsonl`：供工具消费的完整记录；文本的 `text_ir` 保留无损记录 schema。`indexes/` 和每 256 条一份的 `details/` 是页面缓存格式。
- `raw/resources/*.bin`：全部解压数据。`raw/resource-spans.bin`：顺序拼接原压缩 span；每个资源记录保留 pack 偏移、span 长度和原 ROM 地址。

生成目录只允许位于独立的 `build/` 子目录。已有目录必须带匹配的 manifest schema 才可替换；先完成解析和引用检查，再发布输出。原始内容留在被 Git 忽略的 build 目录中。

后续 Mod 层应消费另一个经过语义确认的定义 schema；不要把本次 `raw_hex` 或候选字段直接作为可写配置。推荐顺序：

1. 继续确认地形适应、位标志、成长的特殊条件、改造／变形和武器可用条件；主要数值与单位换算已完成本批解释。
2. 关卡 IR 已完整读出（事件流、文本引用、增援组、胜败与路线命令均有静态解释）；下一步是运行时脚本跟踪与静态解读的比对，以及地图内部结构（地形、辅助层）。
3. 用一项机体参数、一个精神习得等级和一条事件做最小可恢复替换，在静音原生运行中核对；通过后再开放对应 Mod schema。

语言包继续使用 `base:tNN_NNNNN` 与原文 hash，人物／机体定义通过 TextKey 引用名称。图片与 3D 替换属于独立资源轴，不把语言、画质开关和游戏数值绑在一起。

## “解析完成”的验收范围

目标是让原版内容可重建、可翻译、可做人物／机体／关卡 Mod。recomp 保留原程序的执行逻辑，能够提供加载与消费证据，但不会自动恢复字段名、数据模型或事件指令含义。

| 领域 | 已有基础 | 完成前必须补齐 |
| --- | --- | --- |
| 文本与语言 | 20 表无损文本 IR、名称 TextKey 关联 | 控制字与调用上下文覆盖、字库与图片文字清单、日文／中文切换和回退的场景验收。提取原文不等于完成翻译。 |
| 人物、机体、武器、精神 | 固定表、名称、主要基础数值、线性等级成长、技能分组和跨表关系 | 其余字段与位标志、特殊成长／改造／变形条件、负值和异常索引控制流，逐项形成可写定义。 |
| 关卡 | 章节标题候选、场景→地图→资源、静态战场底图、第一话历史内存关系、完整事件指令 IR（条件块、主角段落、说话人、触发类型、`3D4B` 路线流向、出击记录） | 标题与场景 ID 的完整对应、地形属性与辅助层、地图演出类命令的游戏效果、运行时脚本跟踪与静态解读的比对、无改动重建与单条事件替换验证。 |
| 图像、模型与其他资源 | descriptor、全量解压与字节锁、361 人物头像／363 机体地图图标／158 底图关联 | 战斗大图及其他资源类型和使用位置、替换规范，以及 origin／HD 切换验证。 |
| Mod 写入链路 | 只读目录与稳定身份 | 定义 schema、引用与范围检查、无改动回写一致性、单项修改和还原、静音游戏验证。 |

各域按“无损提取 → 字段与指令解释 → 引用闭合 → 无改动重建 → 修改并运行验证”验收。未知字节／opcode 必须保留并显式标记，不能把它们伪装成已解析字段。关卡脚本和剩余字段语义仍有实质工作；目前不能宣称全游戏解析完成，也不以没有分母的百分比报告进度。
