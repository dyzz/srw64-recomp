# 改造继承：换机时段数如何搬运，以及哪些是真的漏项

日期：2026-09-18。范围：日版 Rev 0 ROM 与本项目的静态反汇编（`build/recomp/cpu-scan`）、已提取的机体／武器目录（`assets/original-data/records`）。**本文全部结论来自静态分析，没有运行游戏复现**；需要运行才能定论的条目集中列在第 7 节。对照[原版 Bug 登记](original-bug-register.md)的 BUG07／BUG08／LEAD01／WATCH01／WATCH02。

## 1. 结论摘要

| 结论 | 依据 |
| --- | --- |
| 换机的“继承”完全由两张 ROM 固定表驱动：前任表 `D_800CA3A0`（30 对）决定从哪台机体继承，武器映射表 `D_800CB5E8`（114 条）决定哪件武器的段数搬到哪件武器 | `800AA814`、`800AA8F4` |
| 继承来源**不是**脚本里写的旧机体编号。脚本的旧机体只用于删除；继承来源是前任表按**新机体**反查出来的那一台，且必须此刻仍在名册中 | `800AAD28` 第 4、5 步 |
| 机体五项段数整块复制，并传播到变形／合体的其他形态 | `800AA8C0`、`800AAB5C` |
| 武器段数逐件按映射表搬运；表里没有条目的武器一律停在 0，哪怕新机有同名同数值的后继武器 | `800AA8F4` 的武器循环 |
| 三处疑似数据漏项：レイズナー 的火炎放射器与グレネードランチャー、アルトロンガンダム 的ドラゴンファイヤー（EW 换装）。新旧机的这几件武器同名，且除基础攻击力外所有数值相同，却没有映射条目 | 第 4 节 |
| `800AA8C0` 连改造上限（`+0x51`）一起复制，但紧接着的 `800AAB5C → 800A5254` 重载新机自己的 ROM 记录并把上限改写回去，**没有实际影响**；同一次调用也按继承到的段数重算五项数值与每件武器的威力 | 第 5 节 |
| Akurasu “Lost upgrades” 里的多数条目不是继承代码的问题：剧本先用 `3D5A …,4000` 连人带机删除，回归时重新登记，前任已不存在，自然没有继承 | 第 6 节 |

## 2. 代码路径

### 2.1 入口

| 触发 | 位置 | 调用形式 |
| --- | --- | --- |
| 脚本 `3D5A`（第 3 字 < 2000，含“无旧机”的 500） | `800A0BA8` → `800AAD28` | `(角色, 参数, 新机, 旧机)` |
| Endless Waltz 自动换装 | `load_0008F4B0:801CF890` 循环表 `D_801DC6E4`（5 对），当五项段数**都**达到实例 `+0x51` 时 | `800AAD28(驾驶员或 999, 目标机, 0, 旧机)` |
| ガンダムmkⅡ 343 → 56 的特例 | `load_000AB160:802116CC` | 同一函数 |
| 只登记机体（角色 999） | `800AAD28` → `800A9A70` | 保存／回写逻辑与主路径相同 |

`D_801DC6E4`（5 对，与攻略记载一致）：ウイングゼロ→ウイングゼロカスタム、ヘビーアームズ改→ヘビーアームズカスタム、デスサイズH→デスサイズHカスタム、アルトロン→アルトロンカスタム、サンドロック改→サンドロックカスタム。触发条件只看五项机体改造，不看武器改造。

### 2.2 `800AAD28` 的执行顺序

1. 名册里已有「该角色＋该机体」→ 直接返回（重复调用是幂等的，原脚本多处重复登记靠的就是这一步）。
2. 新机是 224 ダンクーガ → 交给 `800ACB74`：把在用的 223 实例**原地改号**为 224 并卸下各形态部件，返回非 0 后主函数直接结束。因此 Dancouga 不走继承表。
3. 角色 999（只登记机体）或机体 999（只登记驾驶员）各有一条单边分支。
4. **取前任**：`800AA814` 用新机体编号在 `D_800CA3A0` 里查出前任机体编号，再扫描 140 项机体实例表，取**第一台**该编号的在用实例（不检查驾驶员是谁），把它的 `+0x4C..+0x51` 六字节和全部武器（编号、段数、标志三元组）存到栈上。查不到前任 → 后面不做任何继承。
5. `800AA464(角色, 新机, 脚本给的旧机)`：解除该驾驶员与当前机体的关系，并删除编号等于**脚本旧机**的实例。模式 500 时旧机编号是 500，因此旧机体会**留在名册里变成无人机**。
6. 新机实例：名册里已有就复用（若其上还有驾驶员先解除），否则按默认驾驶员表 `D_800CA418` 新建。
7. 若第 4 步取到了前任：`800A5C18` 重算基础值 → `800AA8F4` 回写继承 → `800AAB5C` 把五项段数传播到变形／合体的其他形态。

第 4 步在第 5、6 步之前，所以“先保存后删除”的顺序本身没有问题；出问题的是前任在更早的剧本事件里就已经被删除的情况（第 6 节）。

### 2.3 `800AA8F4`：继承的全部规则

- `800AA8C0`：把保存的六个字节写回新机 `+0x4C..+0x51`，即五项段数**和改造上限**。
- 变形族（`D_800CB40C` / `D_800CB5A4`）与合体族（`D_800CAC94` / `D_800CAEF0`）里的其他形态，同样整块写入同一份六字节。
- 武器：对保存下来的每一件武器，在 `D_800CB5E8` 中查“旧武器编号”，命中后在新机武器实例数组（`+0x2C` 数量、`+0x30` 指针、步进 0x24）里找“新武器编号”，把段数写入 `+0x16`。表里查不到，或新机没有该目标武器 → 新机这件武器留在 0。
- 该表是全局的，不区分机体对；命中第一条后就不再往下找。当前 114 条的源编号没有重复，所以这条“只取第一条”暂时不产生影响。
- 唯一的额外处理：武器 314 ファンネルMAP 会把 `+0x22` 的位 2（解锁位）一并继承。

## 5. 改造上限：复制了，但随即被重置

`800AA8C0` 复制的是六个字节，第六个是上限 `+0x51`；`800A9A70` 的单边路径也先把前任的上限写进新机。**但这两条路径随后都会调用 `800AAB5C`**，而 `800AAB5C` 的第一件事就是 `800A5254(新机, 1)`：该函数用机体编号回读自己的 36 字节 ROM 记录，把 `+0x20` 写进 `+0x51`（`800A5330`），同时按 `+0x4C..+0x50` 重算 HP／EN／运动性／装甲／限界，并逐件重算武器威力（`800A55F4` 起的循环：回读武器 ROM 记录得到基础攻击力，再按该武器的 `+0x16` 段数从 `D_800CA590` 累加）。`800AAB5C` 的形态传播循环对每个在用形态同样调用 `800A5254`。

因此上限复制是瞬态的：从 `800AA8C0` 到 `800AAB5C` 之间没有任何代码读 `+0x51`，最终每台机体用的都是自己 ROM 记录里的上限。**这一条不构成 Bug，也不需要修正。**

顺带留档两个数据孤例（与继承无关，只影响机体自身）：全表 363 台机体中上限为 6 的只有 124 ガンダムサンドロック 一台，为 12 的只有 262 マジンガーZ 一台；它们的后继机分别是 7 和 13，其余 W 系 TV 机体一律是 7。上限同时约束五项和每一件武器（`801CFA78`、`801D130C`），也决定 EW 换装的触发点（`801CF8AC` 起逐项与 `+0x51` 比较）。

这一节同时说明了修正继承漏项时的落点：段数写进 `+0x16` 之后，威力由游戏自己在 `800AAB5C` 里重算，所以修正必须发生在 `800AA8F4` 返回之后、`800AAB5C` 之前。

## 8. 可选的调整方案（8.1 与 B0 已实现，其余尚未实现）

三类问题的成因不同，改法和代价差别很大，按代价从小到大列。共同前提：按[可选规则修正](rule-fixes.md)的约定，修正类默认开启、难度类默认关闭，关闭时宿主只调用原函数；不改 ROM，不改存档格式。

### 8.1 修正 A：补三条武器映射（2026-09-18 已实现，未实机验证）

### 8.2 不需要改：改造上限

第 5 节已确认 `800AA8C0` 复制的上限会被 `800A5254` 重置，原先设想的 `upgrade-cap-keep` 开关没有必要。

### 8.3 修正 B：剧本级丢失

Akurasu “Lost upgrades” 里的大多数（W 系中期机、施皮格尔、ミデア／アウドムラ、ガイヤー）都不是表的问题，而是剧本用 `3D5A …,4000` 连人带机删除，玩家投进去的资金随机体一起消失。三种改法，**退款是其中最克制的一种**：

#### B0：删除时退回改造资金（2026-09-18 已实现为难度调整 `upgrade-refund`，见[可选规则修正](rule-fixes.md) §2.6）

不改变任何机体的强弱曲线，也不会让 EW 换装提前触发，只把“白花的钱”还回去，玩家可以重新决定投在哪台机体上。可行性已核到价格模型：

| 项 | 原版数据 |
| --- | --- |
| 机体五项单价 | 五张 15 段表 `D_801DC36C`(HP)／`3AC`(EN)／`3EC`(运动性)／`42C`(装甲)／`46C`(限界)，按**当前段数**取价，**与机体无关**。例：HP 每段 2000、4000 … 30000；运动性 5000、8000 … 65000 |
| 武器单价 | 按武器改造类型（武器记录 `+0x0E` → 实例 `+0x15`）选四张 16 项表之一，再按当前段数取价（如类型 4 用 `D_801DC6FC[段数]`），**与机体上限无关**。2026-09-18 订正：原文写的 `D_801DC340[上限−5]` 是刻度条字符串表，不是价格表，见[改造段数](upgrade-limits.md) 第 3 节 |
| 已花费金额 | 对每项／每件武器把 0…当前段数−1 的单价求和即可，完全可由宿主算出 |
| 资金 | `D_8010F5F4`（u32） |

落地时解决的三件事（实现细节见[可选规则修正](rule-fixes.md) §2.6）：

1. **退哪些删除**：只退“不会被继承”的那一次。`800AA3C4` 是删除机体实例的唯一出口（调用者 `800AA464` 两处、`800AB808`、`800A7DEC`，另有出售画面 `801C3678`），但它本身不知道调用上下文。实现包装了 `800AA464`、`800AB808` 作为退款范围（`800A7DEC` 与出售不在其中），并包装 `800AAD28`：按前任表找出本次会被继承的那台实例，删除的若正是这一台就不退款。另外只退我方实例池（`800A6E68` 的第 0 池），剧情赠送的 `3D6C` 段数也不退。
2. ~~**武器类别字段**：武器价格表按类别分支，类别取自武器记录的哪一字节尚未确认。~~ 已确认是武器记录 `+0x0E`（2026-09-18）。
3. **和 8.1 的分工**：逐件武器的表漏项由 8.1 精确修好；退款只负责整机被删除这种粗粒度损失，两者不重叠。

#### B1／B2：保留或回填改造段数（代价更高）

- **方案 B1（窄）**：对指定的“临时离队后回归”的角色＋机体＋场景白名单，把 `4000` 降级为 `2000`（只删驾驶员，机体留在名册）。改动集中，但需要逐条确认剧情上该机体确实应该保留，否则会在名册里留下本该消失的机体；而且回归时的 `3D5A …,500` 会复用留下的旧实例，其后的 `3D6C 机体,3` 仍会**覆盖**段数。
- **方案 B2（宽）**：在宿主侧按机体编号记住被删除实例的五项段数与各武器段数，同一机体编号重新登记时回填。不改原版结构，但这份记忆必须进入保存集合（[路线图](../design/mod-roadmap.md) M2），否则读档即失效；并且要决定 `3D6C` 的覆盖是照旧还是改成取较大值——照旧的话 W 系中期机仍然固定 3 段，回填等于没用。
- 两个方案都明显改变资源与强弱，属于规则包而不是 QoL，需要单独的效果说明与旧档兼容验收。

## 9. 旁证与其他发现

- **`3D6F` 是“解锁武器”，不是部件操作**：它清的是武器实例 `+0x22` 的位 2，原脚本的 11 个参数全部是剧情解禁的必杀技武器编号（19 石破天驚拳、1215 ダブルゴッドフィンガー、53／62／71／76 シャッフル同盟各机、770／773／775／777 コン・バトラーV、874 対空光牙剣）。该位正是 `800AA8F4` 里为 314 ファンネルMAP 特意继承的那一位。布局锁 `config/data/original-jp-v1.json` 的 `3d6f` 条目已随本次分析就地订正（原为“清除部件记录标志（部件编号）”）。
- 由此，状态探针 `src/host/state_probe.hpp` 里名为 `part_instances` 的区域（`0x80178F80` 起），其开头的 700 项 × 36 字节是**武器实例池**：机体实例 `+0x30` 指向其中，`+0x2C` 是件数。强化部件是另一套结构（机体实例 `+0x21`／`+0x23` 槽位与 `D_8015E990` 库存，见 `800A9D60`）。该区域名称尚未订正。
- 前任查找不看驾驶员，只取第一台编号匹配的在用实例。
- 保存武器用的栈缓冲是 50 项，全表最大武器数为 28（ランドライガーH），不会溢出。
- 变形形态共用同一个武器实例数组（如ゲッター1/2/3 共用 12 件），所以各形态的武器改造是同一份数据。
