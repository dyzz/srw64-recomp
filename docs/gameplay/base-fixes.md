# 基础修复：默认生效、没有开关

日期：2026-09-18。这里记录**默认生效**的原版缺陷修复：游戏与自己的数据自相矛盾、修好之后没有任何原版玩法被改掉，因此不做成玩家选项。需要玩家自己决定强弱取舍的改动在[可选规则修正](rule-fixes.md)，外部报告的原始线索在[原版 Bug 登记](original-bug-register.md)。

| ID | 修复 | 实现 |
| --- | --- | --- |
| BUG05 | 五飞等 W 驾驶员敌对时不再带假身 | 宿主包装 `resident_func_800A5054`（`src/host/base_fixes.hpp`、`game_hooks.cpp`），无条件生效 |
| BUG06 | 真实系 OZ 路线在剧情加入点登记万丈／泰坦3，补入缺失旧档 | `resident_func_800A158C` 的原事件匹配与场间 `801CE19C` 的受限迁移；调用原版 `800AAD28`，不覆盖已有记录，保留后期分队限制。2026-11-01 本地实现，尚未发布 |

判断标准：原版的部署记录明确写着这些单位没有假身（行为字位 14 未置位、附加值 0），代码却因为一处缺少阵营判断把我方击坠数写了进去。恢复成记录本身要求的状态不需要玩家选择，也不改变任何头目原有的假身次数。

## 1. BUG05：五飞敌对时的假身次数等于他在我方的击坠数

地址分布在常驻代码（`800A…`、`8009…`）和战术 overlay（`801E…`–`8020…`）两处。

**原版的假身机制**

- `801E0410` 放置单位时，阵营 1、2 的名册槽（`8015E100 + 阵营×0x258 + 槽×0x14`）`+1` 置位 `0x80`；部署记录原始阵营非 0（含放到我方的记录值 3）时，`8020B324`／`8020BE34` 也会置位。它表示「非玩家操控」。
- 对这类单位，驾驶员记录 `+0x14`（u16）是**假身次数**；我方单位的同一字段是击坠数，`801FB374` 只在阵营 0 且名册无 `0x80` 时加 1（上限 999）。
- 部署记录（28 字节）行为字 `+0x16` 位 14 置位且阵营非 0 时，`8020ABB4` 把 `+0x18` 写入 `+0x14`。原版共 42 条这样的记录，全部属于ハマーン、シャア、シロッコ、グレミー、ミリアルド、ギュネイ、ガトー、ル・カイン，次数为 2、3、5、7。
- 结算顺序（`801F7204`）：先按参战表 `+0x12` 的命中率（钳到 0–100）与 1–100 的随机数掷命中，**只有本该命中的攻击**才依次检查分身类能力（`801F6C44`）、切り払い（`801F6D10`）、假身（`801F6E3C`）。假身的条件是阵营非 0、名册 `0x80` 置位且 `+0x14 ≠ 0`，成立时结果为 `0x15`，攻击无效，随后 `801FCA78`（普通战斗）或 `801FE068`（地图兵器）把 `+0x14` 减 1。游戏内不显示剩余次数。

**原因**

- W 系五人另有持久击坠表 `801614E0`（5 个 u16），下标 0 ヒイロ（角色 95）、1 デュオ（92）、2 トロワ（93）、3 カトル（89）、4 五飛（91）。`801FB374` 给我方记录加击坠后调用 `800A4FBC` 同步加 1；`80091ED0`／`800920B4` 随中间存档保存读取，`800A4F94` 在新游戏清零。
- `3D5A … 4000` 离队时 `800AA62C` 调用 `800A7E88` 清空整条驾驶员记录，`+0x14` 归零；重新登记时 `800A84F8` 新建记录后由 `800A5054` 把 `+0x14` 抬回表中的值。这是为「离队再加入保留击坠数」准备的。
- 但 `800A84F8` 为**任何阵营**新建具名驾驶员（角色编号 < 287）都会调用 `800A5054`，而 `800A5054` 只看角色编号，不看阵营。五飞的两条敌方记录本身没有假身：「決戦宙域 前」`00202a0c`（阵营 1）与「生と死の未来」`00208568`（阵营 2）的行为字和附加值都是 0。于是他以敌方身份新建记录时，`+0x14` 被写成此前在我方的击坠数，敌方单位又把该字段读作假身次数。
- 备份在离队后不再增加，所以假身次数等于**到离队为止**的累计击坠数（上限 999），不是固定的 21。消耗假身只改敌方记录，不动备份，因此他重新加入（`3D5A 91,0,115,500`）时击坠数照常恢复。
- 另外四人走同一条路径。ヒイロ在「OZ分裂 前」「その名はエピオン」「トレーズ暗殺指令」以第三方（记录值 4）登场，若此前在我方有击坠，同样会带上假身。这几关在各路线中是否都排在他有击坠之后，本轮没有核实。

### 修正

`800A5054` 改为只在驾驶员记录位于我方表（`80172F40`–`80174CEF`，100 条 × 0x4C）时执行。敌方与第三方的新记录保持部署时的值（五飞 0，头目仍按记录的次数），离队再加入恢复击坠数的行为不变。`800A5054` 的另一个调用者 `80210758`（在场单位转为我方）只在目标阵营为 0 时调用，传入的也是我方表内的指针，不受影响。

## 2. 实机复现与对照

原版这段流程跨越多话（加入 → 击坠 → 离队 → 敌对 → 再加入），所以做了一个把它压进一关的迷你关卡 [`wufei-dummy.json`](../../config/recomp/mini-stages/wufei-dummy.json)，输入脚本 `wufei-dummy-input.json`，运行方式（日文、Original、`--original-name-entry`、静音、`SRW64_STATE_PROBE=1` 与 `SRW64_MINI_STAGE_CAPTURE=1`），20,000 VI。

关卡流程与对照设置：

- 第 1 回合：五飛（アルトロンガンダム、等级偏移 60）在我方，身边三台ドール；结束我方回合后，敌方阶段里他反击击坠这三台。タケル（同样等级偏移 60）站在远处当镜头锚点，也是后面攻击五飛的人。
- 第 2 回合事件：`3D46 91,1` 让他退场，`3D5A 91,0,115,4000` 清掉驾驶员与机体记录，再用 `3D45 2` 按他自己的「決戦宙域 前」记录（阵营 1、行为字 0、附加值 0）以敌方身份登场；同组还有グレミー的「アクシズの攻固 前」记录（行为字 `0x4000`、附加值 3）作为**设计值对照**。
- 第 2 回合结束后的敌方阶段：敌方五飛攻击タケル，タケル反击。
- 第 3 回合事件：读数后 `3D5A 91,0,115,500` 让他重新加入，再读一次，检查修正没有破坏「再加入保留击坠数」。

每个观察点由 `3D38` 后的命令边界快照给出，读的是名册槽（`8015E100`）、机体实例（`8016A210`）和驾驶员实例（`80172F40`）。

## 5. BUG06：真实系 OZ 万丈／泰坦3漏加入（2026-11-01）

原因与原版对照见[调查记录](daitarn-oz-investigation.md)。S55「その拳に心宿して」结束时共通执行 `3D6B 165,216,0`，它只能解除已有单位的分队限制。真实系从未登记该单位，应照完全和平 S69 的正确分支调用 `800AAD28(165,216,0,500)`。

实现：

- 新流程：包装 `3D6B` 处理函数 `800A158C`，只匹配场景 55、真实系主角和原结束事件尾部的完整指令序列。在原指令前补登记；随后原指令照常执行，后续エイジ／レイン登记与下一场景不变。
- 旧档：在空闲的场间菜单补入。要求真实系、var10=1（OZ）、下一场景属于原版加入点之后的显式白名单；GB Link 的下一场景从原版保存的主线返回场景判断。加入前、其他路线、超级系不补。
- 分队：下一场景为 S103／S134（地球支线）或 S104（合流前）时，登记后调用原版 `800AC6C4(165,216,1)`，保持万丈在宇宙分队；S104 开场的原版 `3D74` 正常解除。
- 已有万丈驾驶员记录（含隐藏）、或泰坦3任一形态的有效记录时不登记，保护旧档等级、击坠、改造和部件。部分存在的异常记录也不强行覆盖。自定义战役／迷你关不应用这条原剧情修复。
- 使用原版登记分配驾驶员与三个机体形态，没有新增存档字段。它是始终生效的基础修复，与可选规则开关无关。

验证：

```sh
make recomp-base-fixes-test
PYTHONPATH=src python -m unittest discover -s tests -p test_daitarn_oz.py -v
PYTHONPATH=src python tools/recomp/gameplay/check_daitarn_oz.py --machine-code --repair-checks
```

原生策略测试覆盖全部场景编号的白名单与反例、四名主角、OZ旗标、转场、Link返回、脚本签名、隐藏／变形／已有记录及重复调用。ROM测试独立核对白名单与原始场景图一致、原地球分队名单含万丈、合流开场确实解除分队。

最后一项用编译后的实际 C++ 策略调用原版 MIPS 登记／分队函数：两名真实系都得到万丈和 216／217／218 三个形态；S56／S103／S104／S105 旧档补入与重复调用正确，地球分队保持隐藏、原合流函数解除隐藏。只有同步 ROM 读取的 I/O 边界替换成相同字节的拷贝，登记、数值、武器和形态逻辑均执行原机器码。这是受控 RAM 回归，尚未替代完整 Android 路线通关与真实旧档验收。发布的 0.5.2 不含此修复。

## BUG10：移动力超过 15 时越界

日期：2026-11-09。原版没有超过 15 的单位，这条路径是数值 MOD（移动力上限 30）和强化部件叠上去才打开的；以下是静态分析和单元测试的结论，实机验证见最后一节。

**原版的结构**

移动范围是以单位为中心、31×31 的一组表，每格 15 层「走到这里还剩多少」的记忆，刚好够移动力 15：

| 表 | 地址 | 大小 | 用途 |
| --- | --- | --- | --- |
| 可达 | `80227BD0` | 961 | 0 不可、1 菱形内未走到、2 可停、3 只能穿过（友军） |
| 代价 | `80227328` | 961 | 进入该格的移动消耗 |
| 寻路 visited / 路径掩码 | `8021F0A0` / `8021F470` | 各 961 | 填范围时 `8021F470` 暂存地形号 |
| 每格层数 | `80223170` | 961 | |
| 剩余值层 / 路径层 | `8021F910` / `80223800` | 各 15×961 | |

这些表后面紧贴着正在使用的变量，所以不能原地放大；`801C3E50`、`801C3B0C`、`801E0C68`、`801C58E0`、`801C5C48` 等约 16 个函数写死了 31、15、`0x3C1`。移动力超过 15 时，菱形和递归都会写出表外。

**做法**

- 判定在 `801C3E50` 入口。移动力 ≤15 一次比较后原样调用原版，所以这段范围和原版不可能有差别；超过 15 但被 EN 压到 15 以内的情况也走原版，原版自己会做同样的压缩。
- 超过 15 时宿主按移动力开网格（`move_range.hpp` 的 `Grid`）：调用原版的 `801E213C` / `801EB4C0` / `801EEA14` 取地形和占位，保持原版的菱形、地图可玩边界（x、y ∈ [32, W−48]）、占位判定和 `801EA3C8` / `801EA498` 前后括号；范围用最短路代替带记忆的深搜，结果相同（下面的对照测试验证）。
- 算完只把以单位为中心的 31×31 窗口写回 `80227BD0`、`80227328`、`8021F470`，任何窗口外的地址都不碰。没有接管的读者（`80202E70` 只看四邻等）因此看到的就是自己熟悉的数据。
- 下列函数在大网格生效时走宿主，否则仍是原版：`801E0B94` 确认选格（再加「状态 0xC、查询值 2」的守卫，攻击选格问的是另一张表）、`801E0C68` / `801C5810` 寻路与走格、`80202848` / `80202A84` 敌方选落点、`801F3268`（`801F9590` 判断哪些单位在范围内）。
- 画范围 `801E4760` 不重写：调用前临时把窗口滑到屏幕上的那部分（±240 像素盖得住 16:9），并临时改锚点，原版画完立刻还原。
- `801C3D34` 是一切范围的开头（武器射程也是），它一运行就结束大网格，所以后面的攻击逻辑不会读到旧数据。
- 单位走路时读的相对坐标是有符号字节、以 15 为中心（`801CC290`、`801C264C` 经 `801FFE00`），因此网格半径内部上限是 112，实际用不到。

**寻路的结果怎么保证和原版一致**

原版在所有路径里取总代价最小、其中按「左上右下」最先搜到的一条。宿主先求最短路，再沿「只走在某条最短路上」的格子按同样的方向顺序走，结果相同。

**原版留下的一个问题（≤15 也存在，未修）**

`801C3B0C` 把「剩余值」存成有符号字节。进入代价 0xFF 的不可通行格时，`剩余 − 255` 放不进字节，下次比较找不到自己，于是这一格每被走到一次就多占一层，超过 15 层后会写到 `80223160` 之后（每格层数表）。需要同一格被 16 次以上不同状态走到，没有实机验证过这种情况是否出现。这里只记录，≤15 的行为保持与原版一致。

**武器射程**

`801C4560` 不搜索，只在同一张表上盖形状：普通武器（类型字节 `+4` 位 0 为 0）是半径等于射程的菱形，写 1；有最小射程时再用「最小射程−1」的菱形写 0，挖空中间。然后清掉单位自身格，清掉站着单位且 `801EB4C0`（模式 0）或 `801EB65C` 拒绝的格子，最后清掉地形号为 0x3F 的格子。原版只查地图边界，射程超过 15 时列号越界写到相邻行，行号越界写到表外。

- 普通武器在 `801C4560` 入口判定：半径 ≤15 且大网格未生效时走原版；否则宿主在大网格上做同样的盖章，再回写 31×31 窗口。两次盖章之间大网格一直生效，直到下一次 `801C3D34`。
- 接管的读者：`801E0B94`（选目标）、`801E49A4`（模式 0 画射程，同样滑动窗口）、`801F3268`（判断单位是否在射程内，包括 `801F9590` 和各处武器判定）。`801F3268` 收到大于 15 的半径时，原版窗口下限是负数，会直接答「不在」，这也是必须接管的原因。
- 地图武器不接管：它的形状来自 ROM 里 51 条武器号的表（`801C55C0`），流程另有 `80223170` 等表（`801D35B0` 起）。ROM 里地图武器最大射程是 8，所以数值 MOD 把地图武器的 `range_max` 限在 15（`mod_data.hpp` 校验），万一仍有超过 15 的数据，运行时夹到 15，不越界。
- 只有站着单位的格子才调用两个占位判定（它们本来就只比较单位坐标），所以盖章时的占位查询次数不随射程增长。

**验证**

- `tests/native_move_range.cpp`（`make recomp-move-range-test`，地址消毒器下运行）：按反汇编逐行抄写原版 `801C3B0C`、`801C58E0`、`801C5C48`，在随机地形、占位、地图边缘和角落上，移动力 1–15 逐格比较范围和路径，含代价为 0 的格子；超过 15 时与全图 Bellman-Ford 比较，检查走路相对坐标不超出有符号字节，并用哨兵字节确认写回只落在 31×31 内。
- 武器射程：同一测试里按反汇编抄写 `801C4560` 的菱形分支，射程 1–15、含最小射程挖空，在随机单位和地图边缘上逐格比较；射程 16–45 与「曼哈顿距离＋地图边界＋拒绝格＋0x3F」的直接判定逐格比较。
- `tests/test_move_range_wiring.py` 检查每个入口都能回落原版、`801C3D34` 结束大网格、画范围后还原。
- Windows 实机（2026-11-09，真实数值 MOD 把移动力和射程拉到 30，最大地图之一地图 100）：
  - 射程 30：距目标 26 格时「攻击」可选、武器列表可用，范围画到远端，选中目标发起战斗；敌方在原地隔 26 格开火，击毁我方单位。
  - 移动 30：网格 61×61，R 跳到 28 格外，走到目标格分毫不差；取消回原位；单位贴地图左缘时范围被边界截断正常。
  - 敌方移动 30：一回合走 25 格贴上去攻击。移动力 10：网格 31×31（走原版），最远距离 10。
- 性能：≤15 只多一次比较。超过 15 时，移动力 30 的宿主计算约 25 微秒，主要开销是逐格调用原版的占位判定，上限约为原版的 4 倍，且只在选中单位和敌方单位决策时各发生一次；绘制沿用原版函数，显示列表最多 961 格，和原版上限相同。
