2026-09-12 规划更新：后续优先级和首发边界以 [MOD 产品路线图](mod-roadmap.md)为准。
安全节点保存、多槽与备份现已纳入首发；下文“五个方向”和不单列存档管理的描述属于当时范围。
本文保留早期技术取舍与实验背景，不能用于判断新路线图中的任务已完成。
当前 MOD 范围仅为项目维护的内置功能模块；下文外部包接入相关设想暂缓，不作为首发依赖。

日期：2026-09-09。T0 已完成固定场景系统文字渲染原型；随后已接入实时标准对白、字号与分页、回看、剧情速度和窗口缩放。最新实施范围及运行证据见[实时苹方 UI](native-dialogue-ui.md)。本文保留整体实施规划；全流程、分支和真实显示器 DPI 组合仍需逐项验证。

用户选定五个方向：中文文字系统、战斗节奏控制、战术信息面板、宽屏与美术提升、联动与内容 Mod。本轮交付详细方案和优先顺序；文字渲染优先采用 macOS 系统文字技术。现有存读档的正确性继续作为各阶段验收条件，存档管理产品功能不单独列入此次五项范围。

## 1. 实施顺序与交付边界

| 顺序 | 阶段 | 可交付结果 | 依赖与相对难度 |
| --- | --- | --- | --- |
| 1 | T0：系统文字画质验证 | Core Text / Core Graphics 生成文字，在真实 RT64 场景的最终画面合成；验证字号与像素密度 | 中；先证明渲染接入和色彩正确 |
| 2 | T1：实时对白识别 | 带文本 ID、说话者、显示进度和控制事件的运行时记录 | 中到高；需要识别解释器与场景状态 |
| 3 | T2：完整对白系统 | 女主第一话可调字号、自动换行/分页、完整译文、对话回看 | 高；依赖 T0/T1，范围先限于对白 |
| 4 | B1：战斗节奏 | 指定战斗演出的加速；随后扩展敌方移动及结算等待 | 中到高；先定位演出与逻辑的边界 |
| 5 | U1：信息面板与 W1：宽屏容器 | 4:3 游戏区旁显示当前单位/武器信息，共用原生文字后端 | 中到高；先完成字段与选择状态映射 |
| 6 | B2 / W2 | 快速战斗结算；扩大实际地图视野、逐场景宽屏与美术完善 | 高；分别通过战斗状态和绘制范围验证后推进 |
| 7 | M1 / M2 | 数据 Mod 包；Link Battler 兼容专项 | 数据包中到高、协议兼容高；联动勘测可以提前，但实现另设门槛 |

文字系统是首要交付；战斗提速随后；信息面板和宽屏容器一起设计。完整快速结算、扩大实际地图视野和联动留到相关运行时边界明确后。以上是工作顺序与相对难度，尚未用端到端原型校准，不能换算成可靠的日历工期。

“完整译文”在文字系统验收中指已提供的译文不因原框容量被截断、强行缩短。全游戏翻译、审校和路线覆盖是内容工作，需要另计；现有 153 条中文测试稿不代表全量完成。文本规模口径见 [原始数据目录](original-data-catalog.md)。

## 3. 中文文字系统：采用 OS 原生文字渲染

### 3.1 决策与画面效果

macOS 首选 **Core Text 排版 + Core Graphics 光栅化 + Metal 最终画面合成**。这会实际调用系统文字技术处理字体度量、字形选择、排版和绘制。Apple 对两者关系与字体回退的说明见 [Core Text 概览](https://developer.apple.com/library/archive/documentation/StringsTextFonts/Conceptual/CoreText_Programming/Overview/Overview.html)。

字体来源与渲染器独立：可选择系统中文字体，也可通过同一系统渲染后端使用 HarmonyOS Sans SC。第一版提供“系统中文”和当前字体两个候选，按相同文本、尺寸、字重和背景比较，确定默认值。跟随系统的字体选择使用语言感知 API，实际解析到的字体和回退字体写入证据，不假定某个字体名称在所有机器上存在。

文字按最终 drawable 的像素密度生成，字号用界面逻辑单位表达；游戏内部渲染倍率与文字大小分开。窗口调整大小或跨显示器移动时重新布局/栅格化。目标是桌面文字质量；系统版本、字体版本、抗锯齿和合成设置会影响像素，不承诺与任意 macOS 应用逐像素相同。

Core Text 提供框内排版与自动断行；游戏的分页、逐字显示、历史记录和脚本同步仍由本项目实现。中文标点禁则、连续省略号、混排与特殊符号需通过样例验证，不能把调用排版 API 当作验收。参考 [Apple 文字布局操作](https://developer.apple.com/library/archive/documentation/StringsTextFonts/Conceptual/CoreText_Programming/LayoutOperations/LayoutOperations.html)。

### 3.2 建议结构

```text
原游戏对白解释器 / 场景与文本 ID
              ↓
DialogueSnapshot：完整片段、说话者、控制边界、显示进度、事件序号
              ↓
翻译覆盖层 + 动态姓名 + 专用符号
              ↓
Core Text：字形选择、度量、行布局、分页所需范围
              ↓
Core Graphics：按最终像素密度绘制可见字形
              ↓
Metal：游戏画面完成后合成 → GPU 完成后截图
              ↓
已显示片段进入对话历史
```

共享逻辑使用 C++；macOS 后端放入独立 `.mm` 文件，构建时链接 CoreText、CoreGraphics 和所需系统框架。接口围绕布局输入、字形簇范围和可合成的像素输出定义，不把 macOS 类型传播到游戏解释器。其他平台后端留作后续移植点，本轮不承诺跨平台字体像素一致。

初期按对白片段缓存布局，只在文本、字体、字重、宽度或 DPI 改变时重新排版。逐字显示使用已经排好的字形位置，按可见范围更新绘制；先测量 CPU 栅格化和纹理上传耗时，再决定是否引入更复杂的字形图集。

### 3.3 T0：先证明系统渲染能正确进入游戏画面

1. 使用已记录身份的真实场景快照，以及固定的中文、日文、拉丁字母和数字样例；包含引号、括号、省略号和较长姓名。
2. 用 Core Text / Core Graphics 生成透明背景文字；显式规定色彩空间、预乘 Alpha 和纹理像素格式。
3. 在最终帧 draw hook 合成文字。已核对固定 RT64 的 `rt64_present_queue.cpp`：hook 位于 `viRenderer->render` 之后、提交呈现之前；现有 GPU 截图也使用此入口。新增合成应在截图 blit 前完成。
4. 先以独立区域对照字形质量，再只对已明确归属的原字形绘制做替换。必须保留框线、背景、头像、光标和专用图标；不能笼统隐藏同类纹理。
5. 验证三档字号、窄/宽文本框、窗口缩放、可用的 1×/2×像素密度；记录窗口逻辑尺寸与实际 drawable 尺寸。未接入的真实显示器组合保留为待测。

T0 通过条件：没有双重文字、偏色、暗边、裁切或额外缩放模糊；最终 GPU 图片包含新文字。输出包括可复现命令、场景/字体身份、布局参数和 GPU 帧。此阶段只证明渲染，不宣称实时对白系统完成。

### 3.4 T1：对白语义与事件识别

文本读取入口只用来关联 ID 与数据，不能把每次 ROM 读取记成一句历史对白。需要定位实际显示函数和文本解释器，识别两个对话框各自的说话者、当前片段、显字位置、等待确认以及结束状态。

游戏线程在明确的时机发布不可变快照；渲染线程使用与该显示任务关联的快照。事件带单调序号和场景世代，防止重复绘制产生重复日志，或 overlay 切换后出现上一个场景的文字。线程间传递有边界检查，禁止渲染线程随意修改游戏的文字指针。

先保持原画面不变，采集女性超级系姓名确认、开场双框对白、地图对白、战后对白等路径。用实际画面和控制事件证明同一文本可以多次出现，而每次出现都只产生对应的一组显示事件。

### 3.5 T2：字号、完整译文、分页与历史

- **Unicode 文本**：按现有稳定 ID 加载外部译文；动态姓名保留插入语义。暂未识别的专用符号保留显式占位/原图能力，不静默删掉。翻译内容可逐段推进，不受 ROM 字库容量约束。
- **控制标记**：保留 `END=FFFF`、`BR=FFFE`、`STOP=FFFD` 及特殊 glyph 的原始序列。第一轮保留显式换行；自动换行仅增加呈现层断点，不改写 ROM 控制流。`STOP` 的实际等待/推进语义须由 T1 运行时证据确认。
- **长译文**：在对应控制片段内重新排版，需要时增加阅读页。新增页面先在宿主层消费确认输入，页面读完后才向游戏交付该片段对应的确认；不可提前消费下一条脚本事件。具体拦截点由 T1 决定。
- **逐字显示**：翻译片段长度独立于原文；设置按字形簇显字的速度，明确 UTF-16 范围、Unicode 字形簇与游戏 token 的映射。每页先完整排版再揭示内容，避免每加一个字整行跳动。
- **对话回看**：保存已经呈现的内容、当时的姓名与说话者、发生序号；重复帧不新增记录，也不提前展示尚未揭示的后文。首版保存当前会话的有界历史，读档和新游戏建立新分段。跨进程历史恢复另行设计存档关联。
- **输入与暂停**：历史窗口消费自己的滚动、确认与返回输入。仅在已经验证的对白等待点打开；回看期间不向游戏发送操作。若存在自动推进对白，必须建立安全的场景暂停机制后才能开放该路径。
- **尺寸与颜色**：字号/行距/边距可调。随游戏原有的文字颜色、淡入淡出和对话框可见性同步；最终画面合成时要单独处理这些效果，避免跨场景悬浮文字。

T2 首个交付范围：女性超级系第一话涉及的剧情对白；姓名页、战术菜单、武器菜单和图片内烘焙文字分别登记覆盖状态。完整第一话译文与分支审校随运行覆盖核对，不能仅按 ID 连续范围宣布全关覆盖。

验收覆盖：长译文、姓名插入、双对话框、显式停顿、跨页、历史开关、缺字回退、字号切换、窗口/DPI 变化、场景切换和读档。执行新游戏至战后保存，并在新进程读取继续；比较对应游戏状态和事件顺序。静态布局测试、单帧回放和实时游戏验收分别记录。

## 4. 战斗节奏控制

**B0 勘测**：通过实际交战定位攻击/反击选择、伤害计算、资源消耗、动画、击坠、经验/资金和返回地图的边界；记录每个阶段的游戏状态。当前尚未证明有可直接复用的原版跳过入口。

**B1 首版**：对一个已验证的演出路径提供正常/加速及按住临时加速。优先审查演出等待和动画步进；若采用模拟时钟加速，必须同时处理 VI、音频反馈、输入采样和线程时序，不能只更改 `get_display_framerate()`。背景音乐与音效采用何种变速策略在原型中明确，并人工试听。

随后覆盖敌方移动、重复提示和结算等待；在需要玩家选择或剧情触发时恢复交互节奏。使用场景状态判断，绝对 VI 输入脚本和截图模板不能成为产品状态机。

**B2 快速结算**：在证明规则执行与演出可以分离后，增加“普通动画 / 快速演出 / 简洁结果”。各模式都必须使资源消耗、HP、击坠、奖励、触发器和随机数推进与同一条件下的普通模式一致。不能直接设置结果变量来假装完成了战斗。

验证从相同存档和可控状态出发；随机状态可固定时精确比较，否则明确比较范围。覆盖命中、未命中、反击、击坠、升级、触发剧情及返回地图，分别测量流程耗时和音频队列。

## 5. 战术信息面板与宽屏

**U0 数据勘测**：建立当前选中单位、驾驶员、HP/EN、气力、行动状态、地形、武器和弹药/消耗字段的映射。每项记录来源 overlay/地址或函数、类型、有效条件、实测对照。先只展示能和原菜单核对的信息。

**U1 + W1 首版**：将窗口设计成原有 4:3 游戏区加侧栏。选中单位时显示单位状态；进入攻击选择后显示双方和所选武器。侧栏使用 T0/T2 的文字能力，字号与窗口宽度联动；空间不足时可收起。首版只读，不改变选中单位或战斗决定。

这一步提供宽屏界面容器，不声称地图视野已经扩大。面板更新使用安全快照，与游戏实际选中状态核对；未知或当前无效字段明确不显示，不能从旧场景缓存沿用。

**W2 实際地图/战斗宽屏**：分别恢复地图摄像机、tile 提交范围、可见性剔除、光标坐标和边缘滚动；战斗另查背景覆盖、精灵/特效、镜头与裁剪。先验证 16:9，再扩大比例，不拉伸原 4:3 内容。

**美术**：按完整场景准备字形以外的头像、地图、界面和战斗素材清单；统一风格、轮廓、透明度、颜色和原图回退。RT64 替换包记录原始纹理身份及覆盖场景，已知有源哈希歧义的素材需要上下文方案后再替换。既有 AI 图像可作为候选，新素材生成属于后续美术工作。

## 6. 联动与内容 Mod

**M1 数据 Mod 先行**：先支持已理解格式的翻译和纹理包，清单记录包版本、适用 ROM、依赖、冲突与数据哈希。随后才开放已核验结构的单位/武器数值；更改范围与默认值可审查，关闭 Mod 能恢复基础配置。重启生效可作为首版边界，暂不设计任意热加载。

原生函数补丁与数据包分别管理。函数 patch 必须绑定版本、overlay 身份和符号；可评估 N64Recomp 的补丁输出方式，主体继续分组生成。当前静态库每个对象包含多个函数，采用同名符号覆盖前需验证链接粒度与重复定义，不能仅添加 `single_file_output=true` 就假定覆盖机制成立。

**M2 Link Battler 专项**分两个明确产品方向：

1. **兼容原联动流程**：调查游戏使用的 Pak/GB cartridge 调用和协议、识别数据格式、校验与读写行为。固定运行库尚无可启用的 Transfer Pak 实现，需要补充接口和兼容层。先用独立数据副本对照正确输入、无设备、错误输入和重复联动；若需要真实 GB ROM/存档参考，其来源和可用性作为实施依赖。
2. **可选内容开放 Mod**：明确说明直接开放的内容及条件，先核实内容标记、资源与后续事件依赖，再实现可关闭的规则。此模式独立标识，不作为 Transfer Pak 协议兼容证据。

关卡脚本、路线改写、随机化和新增机体需要更完整的格式与事件模型，放在 M1 数据层和场景覆盖扩展之后。

## 7. 第一轮开发任务与验证

第一轮开发只承担 T0/T1 的可行性验证，交付后再按证据细化 T2 的工作量：

1. 添加独立 macOS 文字后端与测试工具，输出系统字体/当前字体的三档字号、长句和混排对照。
2. 接入最终帧合成并调整截图顺序，完成色彩、Alpha、DPI 和窗口变化检查。
3. 为一个已验证开场对白场景采集文本 ID、说话者和控制进度，形成显式事件模型及证据。
4. 明确原字形抑制范围与对白推进接口；只有这两项成立后，开始 T2 的实时替换与分页。

建议新增模块放在 `src/host/text/`，以平台后端、布局/分页、游戏事件适配和历史模型为独立边界；具体文件名在开发时确定。配置归入 `config/recomp/`，真实 ROM 派生数据、字体、图片、会话记录继续留在 `build/`。

提交按“文字后端 → 场景识别 → 实时分页与输入 → 历史 → 运行验收”分开；后续战斗、面板、宽屏与联动各自独立。开始代码工作时重新盘点工作树，当前已有的未提交内容不能被整包混入新提交。

静态测试重点覆盖控制事件顺序、Unicode 边界、分页完整性、历史去重与场景失效；原生测试覆盖资源生命周期、布局范围及线程快照。GPU 结果记录字体、平台、配置和场景身份；系统升级可能改变字形像素，不把跨系统 PNG 哈希相等设为通用条件。正式提交前执行仓库要求的检查，运行时证据按实际完成范围记录。

方案建立时完成了源码入口与官方接口核对；随后按用户要求实施了 T0 的固定场景 Core Text 渲染验证。该实验使用独立图形重放目标，没有启动新的游戏流程或改变存档；当前完成范围以 [验证记录](native-coretext-probe.md) 为准。
