# 迷你关卡：自制关卡作为指令验证载体

更新：2026-09-16。目标是用一个自己编写的迷你关卡（开场、对白、战场、战场事件、结束）在真实游戏流程里验证剩余脚本指令。本页记录第一版：宿主把编译好的关卡镜像替换给原引擎，从标题主菜单按 F8 走原版的“新游戏 → 主角选择 → 姓名 → 开场”路径进入。

## 原版如何开始一话

- 世界地图 overlay `load_000A7EC0:801C2B9C` 或读档路径（`800801A4` 三处）算出场景索引 `8010F5F0`，调用常驻 `8009DD58(场景, 加载模式)`。
- `8009DD58` → `8009DBE4(场景)` DMA 本场景的出击记录块（≤ 0x2000 字节）到 `80199400`；`8009DC58(栈表, 场景)` DMA 本场景的事件（≤ 0x1A00 字节）到 `8019B400`，并把事件指针表写到 `8009DD58` 的栈缓冲（0x100 字节，−1 结束）。
- `8009DE7C(模式, 引擎, 指针表, 出击记录块)` 清空 12 组 × 16 槽，按事件头第 0 字类型登记 0–11，类型 12–14 存到 `engine+8/+C/+10`，把出击记录块指针存到 `engine+0`（`3D45` 从这里按 14 个半字扫描）。
- 战术 overlay `load_000AB160:80209D6C` 用 `8010F5F0` 查表 `802195B0` 得到地图索引并写入 `8010F5EE`。

因此替换一话只需要在 `8009DE7C` 入口换掉指针表与两块缓冲的内容，并在 `80209D6C` 之后改写地图索引。ROM、目录数据和其他场景都不动。

## 关卡定义与编译

`config/recomp/mini-stages/*.json`（schema `srw64.mini-stage.v1`）：

- `map`：地图索引（`base:map_assets`）；`slot`：可选，固定替换的场景索引；缺省时替换宿主启用后登记的第一话。
- `events`：事件列表，每项 `type`（0–14）、`header`（四个参数，含义见[事件登记类型](stage-script-exploration.md#事件登记类型与触发条件)）和 `commands`（与[脚本注入调试](script-debug-injection.md)相同的指令写法）。也可以写 `copy_from`（`base:stage_events:*`），按指令流原样复制一个原版事件到结束符为止；同时给 `header` 时只替换四个触发参数、指令字节不变，用来让有界运行到不了的触发条件（较晚的回合、通关次数）也能触发。
- `deployments_from`：整块复制某个原版出击记录块（`base:stage_auxiliary:*`，到 999 为止）；`deployments`：追加的 28 字节记录，字段名 `group/x/y/actor/level_offset/unit/upgrade/faction/behavior/extra`，未解释的字节用 `byte8/raw14/raw16/raw18/raw26`，可用 `template` 指定一条原版记录（`base:stage_deployments:*`）作为底板。

`tools/recomp/mini_stage.py compile 关卡.json --out 镜像.json` 生成 `srw64.mini-stage-image.v1`：事件按 4 字节对齐拼接（指针 = `8019B400` + 偏移），出击记录块末尾补 `03E7 0000`；超过 63 个事件、0x1A00 字节事件或 0x2000 字节记录时拒绝。

## 宿主端

- 开关 `SRW64_MINI_STAGE=<镜像路径>`；`tools/recomp/native-host/mini_stage.hpp`，由 `game_hooks.cpp` 的两个包装调用：`resident_func_8009DE7C`（先替换再调用原函数）和 `load_000AB160_func_80209D6C`（原函数之后改写 `8010F5EE`）。两个钩子通过 `generate_cpu.py` 的 `NATIVE_HOOKS` 绑定，需要 `make recomp-cpu` 重新生成。
- 启动时读镜像并校验（schema、长度、对齐、事件数）；非法镜像让宿主直接失败。
- 事件文件 `mini-stage-events.jsonl`（schema `srw64.mini-stage-event.v1`）：`loaded / applied / skipped / map`，`applied` 记录场景索引、加载模式、指针表地址与原出击记录块地址。
- `run_host_probe.py` 要求日版 profile 与 `--graphics`；有界运行还要 `SRW64_SCRIPT_TRACE=1`，开 `--audio` 的有界运行必须用 `SRW64_AUDIO_CAPTURE_FROM/_TO` 给出采集窗口；`--interactive` 不受这两条限制。报告写 `mini_stage`。
- `mini_stage.py report 运行目录 --image 镜像.json` 把脚本轮询按 PC 关联到每个事件：是否触发、首末 VI、逐条命令的开始／结束 VI 与采样帧、未执行的命令。

## 主菜单入口

- 交互试玩：`play_native.py --profile … --mini-stage config/recomp/mini-stages/flow.json` 编译镜像并把路径交给宿主；窗口标题追加“F8: mini stage <名称>”。在标题主菜单（开场 overlay 状态 3，即“ニューゲーム／コンティニュー…”菜单）按 **F8**：宿主替玩家按下 START 选择新游戏，序章文本序列出现时自动请求原生跳过（等价于 R+START），主角选择与姓名页照常由玩家操作；第一话登记时替换为迷你关卡，记录 `armed / skip-requested / entered`。不在主菜单时按 F8 只记录 `hotkey-ignored`。原版菜单代码与菜单项不改。
- 有界验证：`SRW64_MINI_STAGE_ARM_VI=<vi>` 让宿主在该 VI 之后一到主菜单就自动武装，输入脚本只需两次 START 到达主菜单，再提供主角选择与姓名格的按键（`entry-input.json`）。
- 单元测试 `tests/native_mini_stage.cpp`（`make recomp-mini-stage-test`，并入 `recomp-native-check`）：镜像校验、登记替换、地图钩子只作用于绑定场景、热键只在主菜单武装、START 保持四次轮询、序章跳过计数与进入记录。

## 冒烟关卡 `smoke.json`

以第一话（场景索引 1「出撃!スイームルグ」）为底板：同一张地图（20）、整块复制它的出击记录（20 条，5 组），开场事件裁剪为 6 句对白并保留全部结构性命令（BGM、世界地图 `3D32`、淡入淡出、`3D4D` 切换战场、`3D65`、三组 `3D45` 登场、`3D35` 卷动），另加一个原话没有的“第 1 回合我方阶段开始”事件（类型 0），保留增援（类型 7，敌 ≤ 6）、胜利（类型 7，敌 = 0 → `3D4A`）、败北（类型 2，マナミ被击破 → `3D4C`）和结束事件（类型 14 → `3D4B 4`）。

输入脚本 `smoke-input.json`：冷启动跳过共通序章、女性超级系默认姓名、跳过路线序章，然后每 120 VI 按一次 A。

## 指令验证关卡

第 3 项“用迷你关卡逐条验证剩余指令”已经开始。两个关卡按指令所需的 overlay 分工，参数一律取自原脚本实例；每条探针后跟一个 `3D38` 等待，使采样帧和状态快照能归属到单条指令。

### 逐条命令状态快照

开关 `SRW64_MINI_STAGE_CAPTURE=1`（需同时 `SRW64_STATE_PROBE=1`）。`mini_stage.hpp` 的 `poll_hook` 由 `game_hooks.cpp` 的脚本轮询包装调用：脚本 PC 落在被替换事件块内且与上次不同时，存一份区域快照 `state-N-mini-stage-command.json`，`argument` 为该 PC 相对事件块的偏移，并记 `capture` 事件。0 VI 完成、没有画面变化的字段写入类指令因此也有前后对照。宿主只读 PC，不写回任何内容。

### `worldmap.json` — 世界地图 overlay

开场事件在 `3D4D` 之前运行，是 `load_000A7EC0` 世界地图 overlay 唯一可达的上下文；脚本注入的空闲判定要求战术地图，到不了这里。见[运行结果 worldmap-1](#worldmap-1buildrecompmini-stageworldmap-119000-vi静音)。

### `tactical.json` — 战术地图 overlay

全部探针放在开场事件中 `3D4D` 与 `3D45` 之后。第一轮 `tactical-1` 把探针放在“第 1 回合我方阶段”事件里，结果整轮没有触发：该事件要玩家走完一回合，而有界输入脚本只按 A，运行一直停在单位选择界面。开场事件无须玩家推进，是有界运行里唯一可靠的位置。

`3D49` 单独放在 `duel.json`：它会启动一段脚本战斗，可能吃掉整个 VI 预算。实际结果见下。

### duel-2 → duel-3：`3D49` 需要角色在场，不需要进战斗

duel-2 中 `3D49 15,16` 一开始宿主就崩溃（`native-run-failed`、退出码 −10）。系统崩溃报告给出了准确位置：faulting thread 停在 `load_000AB160_func_80211BD0`，由 `80211DA4`（`3D49` 处理函数）调用，`EXC_BAD_ACCESS / SIGBUS`，地址 `0x708000002F`。

读 `80211BD0` 可知原因：它取名册槽的机体实例指针（基址 `8015E10C`，侧步进 `0x258`、槽步进 `0x14`、字段 `+0x0C`），再按 `+0x2C` 数量／`+0x30` 指针、步进 `0x24` 遍历该单位的列表，**且不校验这个指针**。duel-2 用的是原版出击记录块，表 `800C9A18` 项 15／16 指名的レイン与アレンビー都不在名册里，读到未初始化指针即崩溃。

**结论：`3D49` 需要两名角色出现在地图名册上，并不需要先进入战斗流程。** duel-3 把两组四名角色都部署后，两条 `3D49` 分别用 1572／972 VI 全部正常完成，`exit 0`。

### targets-1（`build/recomp/mini-stage/targets-1`）：给空操作补上作用对象

同一条思路（“空操作 = 缺作用对象”）推进了另外三条。关卡 [`targets.json`](../config/recomp/mini-stages/targets.json) 专门为它们准备目标。

- **`3D6F`** 升为 `code-confirmed`。改用本关部件表里确实存在且已置位的原脚本参数（19／773／775，由 tactical-3 的 `part_instances` 快照挑出；此前用的 53／874 根本不在表内）：`3D6F 773`／`3D6F 775` 把部件记录 31／32 的 `+0x22` 由 `0x0C` 改为 `0x08`，即清除位 2，与静态分析 `800ACF44` 完全吻合。匹配的是记录 `+2` 的编号，不是索引。
- **`3D70`** 升为 `code-confirmed`，改名为“挂载同乘角色”。原脚本 10 处实例里它**全部紧跟 `3D5A`**，而同乘角色（183 チャム／182 シルキー）在全部 6,223 条出击记录中都不出现、由 `3D5A` 以机体 999 登记。照此写法先 `3D5A 183,0,999,500` 建立驾驶员记录 7，再 `3D70 181,183`：该记录 `+0x37` 置 1、`+0x38` 写入机体实例指针；同时 ショウ 所驾 **ビルバイン 的 `+0x34` 由 1 变 2、`+0x3C` 写入驾驶员记录 7 的地址**——即 `+0x34` 是同乘人数、`+0x38` 起是驾驶员指针数组（与 `3D55` 的 basis 一致）。
- **`3D69`** 仍为 `unknown`，但作用范围已确认：在 豹馬 出击的关卡里 `3D69 145,0` 把**驾驶员记录 1–5 的 `+0x35` 全部清零**，即该角色所驾单位的全部同乘驾驶员（コン・バトラーV 五人），不是单条记录。缺的只是这两个字段的游戏名称。

## 开音频的运行（audio-1 / audio-2）

`3D67` 的语义是听得见而看不见的，因此放开了迷你关卡对静音的要求：有界运行仍须开脚本轨迹，但可以加 `--audio`，并且**必须**用 `SRW64_AUDIO_CAPTURE_FROM/_TO` 指定采集的 VI 窗口。原本的采集固定保留开声后的前 30 秒，而要听的命令往往在运行几分钟后才出现；窗口逻辑抽到 `audio_timing.hpp` 的 `Srw64AudioCaptureWindow`，由 `tests/native_audio_queue.cpp` 覆盖（窗口前跳过、窗口内写入、越界时关闭一次、之后不再写，以及 `to <= from` 的退化窗口按“无窗口”处理，避免打错边界导致整个采集丢失）。

关卡 [`audio.json`](../config/recomp/mini-stages/audio.json) 把每条探针夹在 `3D3A 0`（停 BGM）之间，开头用 `3D3A 49` 作正对照；[`audio-tail.json`](../config/recomp/mini-stages/audio-tail.json) 只是把靠后的几条提前，好让它们落进同一个窗口。

### `3D67` 是登场 cut-in 演出（升为 `code-confirmed`）

四个原脚本值全部发声，RMS 2301–3092、峰值 1.5–1.8 万，而相邻静音段只有 RMS 84–139，且**比对照 BGM（RMS 1328）更响**。画面给出了确切含义：屏幕中央出现一台机体穿过同一条光速隧道背景——0 为蓝红车型、1 为灰红、3 为绿、4 为橙红，**各不相同**。

1/3/4 的频谱与包络高度相似（余弦 0.96–0.99、包络相关 0.93–0.99，因为共用隧道背景），但采样级相关仅 **+0.007** 且找不到对齐位移，是不同机体的不同音频；时长 10.87／13.93／14.93 秒。0 的频谱明显不同（对其余三者余弦 0.42–0.46）、无 0.75 秒前奏、时长 16.03 秒。

这与原脚本仅有的两种写法完全吻合：`3D4E → 3D67 n → 3D38 → 3D45 <组>`（增援登场前）和 `3D54 145 → 3D35 → 3D67 0 → 3D5C 145,1`（合体前）。

## 从原调用点反推（stage_script.py）

最有效的一轮不是构造场景，而是**读原脚本怎么用**。`tools/recomp/stage_script.py` 两个子命令：`show <场景>` 按阅读顺序打印一话的全部事件（指令、参数、对白原文与说话人都已解析），`usage <操作码>` 列出该指令在全部 1,812 个事件中的每一处调用并带前后各三条上下文。按真实调用点复现，比自造参数可靠得多——下面五条都是这样定案的。

### `3D5E` = 打开部队名输入界面

原脚本 3 处调用形状完全相同：マナミ 说「マーチウィンド? うーん、もう少し別の名称がいいわね」，アムロ 问「なら、君はどんな呼び名がいいんだい?」，随即 `3D5E`。照此复现后采样帧直接给出答案——画面是「部隊名を入力してください」，部隊名 栏预填 アーチウィンド，下方是假名输入盘与「決定」。事件在此挂起等待玩家输入，有界运行无输入故永不继续。

**同时更正一处旧结论**：此前记载「`3D68` 在世界地图下永不完成」不成立。worldmap-1 的开场事件其实停在更早的 `3D5E`（命名界面挂起），`3D68` 根本没执行到。

### `3D69` = 设定单位行动状态

调用点先给出方向：值 0 出现在 豹馬 被制住的场面（紧接台词「うぅ……しまった……体が……」与敌方「とどめを、さしておやり!!」）和把 NPC 用 `3D3C` 移到位后定住；值 1 出现在 ヒイロ 即将发动精神、大作 退场之后。

镜头锁在单位上逐像素测量给出定案：精灵所在的 12×12 区域亮度 **97.12 →（值 0）91.23 →（值 1）97.12**，每个状态连续 12 帧 min = max（无待机动画噪声），而全帧亮度几乎不变——变化只限于该单位精灵，即本作中「已行动」单位的变暗表现。同时置名册 `+0x0B` 位 7 并清驾驶员 `+0x35`，作用于该单位全部同乘驾驶员。

### `3D36` = 画面震动

逐帧采样定案：命令期间 `mean_delta` 由 0 跳到 23.65 并**保持恒定**，同时 `mean_rgb` 在 56.53 与 50.37 之间**逐帧交替**（静止时 54.23，即在静止位两侧摆动）。恒定帧间差配合两值交替，正是画面在两个位置间逐帧往复。原脚本 196 处几乎全是「`3D39` 音效 → `3D36 n` → 角色惊讶台词」。参数决定时长：5 → 18 VI、6 → 22 VI，二者占 161 次。

### `3D6B` = 选定标记开关

按原调用点复现（事件 001AB86C：`3D6B 124,171,0` 紧接 `3D5A 124,0,174,171`，リョウ 由 ゲッター1 换乘 ゲッタードラゴン）。逐条快照给出分工：`3D6B` 执行后名册机体编号**不变**，换乘完全由随后的 `3D5A` 完成；同理 `3D6B 165,216,1` 之后 万丈 仍在名册，是随后的 `3D46` 让他消失。

静态交叉引用补齐消费者：`resident_func_800AD990`——`3D73`「按固定角色列表分组」调用的同一函数——先遍历清除驾驶员 `+0` 的位 7（`andi 0x7F`）与位 6（`andi 0xBF`），再对名单中编号匹配的条目置位 7（`ori 0x80`）。这一对位是「被选定／已登记」标记：`3D73` 整批标记，`3D6B` 针对单个组合置位或清除。

### 排除项

`3D69` 不是合体分离：同一角色、同一镜头背靠背执行，`3D69 145,0` 前后我方槽数不变（2 → 2），随后的 `3D5C 145,0` 才让四台分体出现在本体周围（2 → 6）。也不是换机体：在 アルベルト／シュバルツ（两人都另有以自己名字命名的机体条目）上五次调用，名册机体编号一个都没变。

## 提高测试效率

两项开销以前占满了每一轮：走完标题流程，以及跑完整个 VI 预算。

### 不经标题 F8 进入（`--save-from` 并不读档）

不必从标题按 F8 与跳过序章。带 `--save-from` 与输入脚本运行，迷你关卡在第一次场景登记时照样替换：

```sh
SRW64_MINI_STAGE=<镜像> SRW64_SCRIPT_TRACE=1 \
  .venv/bin/python tools/recomp/run_host_probe.py --graphics --profile config/recomp/play-profile.json \
  --language ja --images original --resolution-scale 2 --original-name-entry --input <输入脚本> \
  --save-from build/recomp/save-recovery-check/intermission-cold-1.source.sram \
  --save-sha256 0c6ded15fdf60c6b0064b2260a335d17a4ff77386d14d634bfd7d3bcb8de7484 \
  --output <运行目录> --vis 19000
```

这样不需要 `SRW64_MINI_STAGE_ARM_VI`，事件文件里也不会出现 `armed`／`skip-requested`／`entered`。好处只是省掉标题 F8 和序章：

- 这条路径**并没有读取那份存档**（2026-09-18 更正；早先以为会读档并跳过命名），`--save-from` 只是把 SRAM 复制进运行目录。`dense-input.json` 的标题按键选的是ニューゲーム，替换的是**场景 1**（若真读了第一话通关档，下一话应是场景 4），运行中也不会出现 `intermission-restored`／`tactical-restored` 状态快照。
- 运行仍会经过姓名页，现有的 `dense-input.json` 等脚本靠原版假名盘的按键通过它，所以要加 `--original-name-entry`。不加时现代姓名页接管输入，运行会一直停在姓名 overlay（`001090A0`）上，场景不会登记（rules-2 即如此）。
- **存档里的持久数据（击坠数、旗标、资金、编成）在这种运行里都是新游戏的初值**：新游戏会调用 `800A4F94` 等初始化，`wufei-dummy-original-1` 就是这样，改过备份的存档完全没有生效。需要存档内容时，要用真正走 Load 菜单的输入脚本（如 `config/recomp/load-intermission-check.json` 的路径），或者像 `wufei-dummy.json` 那样在关卡内自己造出所需状态。

### 指令触发后就退出

`SRW64_MINI_STAGE_EXIT_AFTER=<操作码>`（十六进制）让运行在该操作码到达后的 `SRW64_MINI_STAGE_EXIT_GRACE` 个 VI（默认 300）结束。宽限期是为了让该指令的效果和其后若干帧仍然被采到。

实测：scene78-turn 关卡验证 `3D75`／`3D46`，原先跑满 19,000 VI，改为 `EXIT_AFTER=3D46 EXIT_GRACE=400` 后在 **7,416 VI** 结束（事件文件记 `exit-armed` 于 VI 7016、`exit` 于 7416），少跑 61%。报告照常生成，只是后续未执行的指令会如实列在 `commands_not_executed` 里。

退出观察与逐条快照各自独立去重：观察器用 `exit_seen` 自锁，不共用采集的边界去重——否则中途打开采集会丢掉观察器已经走过的那一条边界。单元测试覆盖了这一点，以及「只在指定操作码上退出」和「只触发一次」。

### 探针补上了引擎块

状态探针原先覆盖名册、驾驶员、机体、部件等区域，但**引擎自身的块不在其中**——它正好落在名册（到 `0x8015E808`）与机体实例（从 `0x8016A210`）之间的空隙里。于是只写引擎字段的指令在所有快照里都毫无痕迹，读起来像什么都没做。

补上 `script_engine`（`0x8015F950`，0xA00 字节）后，`3D66` 立刻显形：`3D66 1` 使 `engine+0x997` 由 `0x1F` 变 `0x9F`（置位 7），`3D66 0` 变回 `0x1F`，完全对称，与静态描述吻合。同一时刻另有 6 个字节变化，但两次转换里完全相同，是引擎每条命令都会动的轮询簿记。

画面侧用区域差分图验证：「关→开」与对照组「关→再关」的差异同为 2.8／3.1（同一条对角带，属待机动画噪声），即这个开关本身不改变画面。该位的消费者仍未确认，故保持 `structure-confirmed`。

这个盲区也意味着：此前所有「探针全区域零变化」的结论，对**只写引擎字段**的指令并不成立，因此已重看。

#### 区分簿记与指令效果

引擎块里有一段（约 `+0x966`–`+0x97B`）是脚本虚拟机自己的工作状态，几乎每条命令都会动：scene78t-3 全程 90 个转换中 `+0x967` 变了 100%、`+0x96D` 74%、`+0x97A/+0x97B` 51%。把「出现率超过 20% 的字节」当作簿记排除，剩下的才是指令效果。这个判据有交叉验证：同一轮里 `+0x997`（`3D66` 的位 7）只变 5 次，恰是场景里那几处 `3D66`；`+0x9B0` 只变 4 次，正是 `3D46` 递减的单位计数——都稀有且专一。

#### 重测结果

- `3D75`（scene78t-3，真实上下文）：跨度内引擎块只动了 `+0x96D`（74% 簿记）。**覆盖全部区域后仍无任何专属写入**，前六轮的结论成立。
- `3D63`（scene80-2，真实上下文）：唯一专属写入仍是名册该槽 `+0x001`（2 → 5 → 1），引擎块无变化。排除了隐藏的引擎侧效果。
- 同一轮里紧接的 `3D69 145,0` 再次得到与 act-1 一致的写入，可作交叉验证。

- **`3D51` 的原名是错的**。结构层只看到它「查找角色＋机体的地图槽并驱动移动」，但第 2 字的取值一查武器表就全是 MAP 兵器。
- **`3D71` 放错 overlay 会让宿主中止**。它调用的 `801C51B4` 只存在于世界地图 overlay，在战术地图上执行时函数查找失败（`get_function` 断言）。这和早先 `3D68` 的情况同类：**指令要在它所属的 overlay 里测**。

### `3D66`：读取方藏在虚拟机上下文的指针里

直接搜 `0x996` 偏移找不到位 7 的读取方，原因是脚本虚拟机上下文 `+0xC` 存着 `&engine+0x994`，读取走的是 `(ctx->[+0xC])[+2]`。按这个形状再搜，得到 `800A3530`（返回 `& 0x80`），唯一调用者是对白指令 `3D3E`／`3D40` 的前置步骤 `8009F4B4`：


`800A2C18` 以 `0x80` 为模式时永远返回 0，所以位 7 置位就是「对白不跟随说话者」。focus-0／focus-1 只差 `3D66` 的参数：两个说话者分处地图左上与右下，镜头先停在二者之间。

### `3D59`／`3D3D`：出击选择

## `3D75`：从母舰放出搭载单位（2026-09-17）

前七轮一直测不出效果。读 `80213758`／`80213AAC` 才知道原因：它处理的是**母舰里搭载的单位**，而前七轮的母舰里一台都没有。

```c
// 3D75 actor
if (actor == 999) actor = 46;
if (actor in captains /*8021E398: ブライト シーラ エレ 葉月博士 エマリー ヘンケン ハワード*/)
    select every unit aboard that captain's ship;          // 母舰表 8015E85C/60，搭载表 8015E864
```

搭载只由玩家的移动指令完成（`801CD0E4 → 801EAF88`），没有脚本指令能让单位上舰，所以 launch-1 头一次用按键驱动了玩家操作（`config/recomp/mini-stages/launch-input.json`）：

1. 开场：`3D5A` 登记 ブライト＋アウドムラ 与 ドモン，`3D3D …,0,3` 让 アウドムラ 进母舰表并登场于 (5,10)，`3D3D …,200,2` 让 ドモン 站在它右边。

3. 地图菜单「フェイズ終了」→「はい」。
4. 第 1 回合敌方阶段开始的事件（类型 0，头部 `[0,2]`）执行 `3D75 999`。

| | 执行前（VI 6495） | 执行后（VI 6751） |
| --- | --- | --- |
| 我方地图槽 | 只有 アウドムラ (5,10) | 多出 ドモン (5,8)，组号 2 |
| 搭载数 | 1 | 0 |
| 我方单位数 | 1 | 2 |
| 画面 | — | 镜头移到母舰，上方出现紫色发进特效，ドモン 出现在母舰上方 |

原脚本里 `3D75` 总在舰长或角色离场之前：シーラ、エレ 返回バイストンウェル、ブライト 离开ラー・カイラム，都要先把舰里的单位放出来，免得跟着母舰一起离场。实机视频里看到的「消失、离开战场」是紧随其后的 `3D46`；舰里没有单位、或非舰长角色没有搭载在母舰上时，`3D75` 什么也不做——前七轮与多数视频里都是这种情况。

两个顺带弄清的坑：

- **类型 0 事件头的回合数和 `8010F5EA` 比较，它从 0 开始**：第 1 回合是 0，画面上的「ターン数 2」才是 1。头部 `[1,2]`（第 2 回合敌方阶段）、`[2,1]`（第 3 回合我方阶段）在第 1、2 回合都不会触发。
- **（2026-09-18 补）对仍在地图上的单位直接 `3D5A … 4000`**：驾驶员与机体记录被清空，但名册槽还指着它们；本关卡随后如果继续交给玩家操作，遍历名册时就会 SIGBUS（`801FD020`→`801EB344`，见 `wufei-dummy-original-3`）。先用 `3D46 角色,1` 让它退场再 `4000`。原脚本里这类移除都在关卡结束事件或开场，不会在同一关里回到操作状态。
- **此前「回合事件在有界运行里不触发」的真正原因**：那些关卡的回合事件头部写的是 `[0,0,0,0]`，阶段 0 永远不等于 1／2。场景 78 那一轮改成 `[0,1]` 后就在第 1 回合我方阶段触发了。
